# 复制、下载与分享

> **这是产品的价值所在，也是 Web 形态约束最强的地方。本端最重要的一份规则。**

背景与完整论证见 [SPEC §9.2](../../../spec/09-decisions.md)。

## 1. 能力边界

浏览器的 `ClipboardItem` 规范**只保证** `text/plain`、`text/html`、`image/png` 三种类型。

| 场景 | 能力 | 体验 |
|---|---|---|
| 桌面 · 静态图（PNG/JPG/WebP） | 写入剪贴板 | ✅ 点击即复制，切回微信 Ctrl+V |
| 桌面 · 动图（GIF/APNG） | **写不进剪贴板** | ⚠️ 退化为下载后拖入，或直接拖进聊天窗口 |
| 手机 · 任意格式 | `navigator.share({files})` | ✅ 直接分享到微信，动图也可以 |

**手机端是体验最好的一端**，不是需要适配的次要端。见 [styling.md](styling.md)。

## 2. 分流唯一依据是 `isAnimated`

```tsx
// 动图写不进剪贴板，只能走下载。见 SPEC §9.2
if (meme.isAnimated) return downloadFlow(meme)
```

**不能从 `mime` 推断。** WebP 和 APNG 都可能是动图也可能是静图，`image/webp` 说明不了任何事。服务端已经真的解析过容器了，用它给的答案。

见 [SPEC §5.2.2](../../../spec/05-data-models.md)。

## 3. UI 必须诚实

> ⚠️ **不能让用户点了 GIF 之后发现没反应。**

这是本文存在的全部理由。要求：

- 动图卡片有**明显角标**，在点击之前就能看出来
- 动图的主操作按钮文案是「下载」或「拖到聊天窗口」，**不是「复制」**
- 静图和动图的按钮长得不一样，不是同一个按钮点了之后行为不同

**一个按钮两种行为是最糟糕的设计**——用户会形成「点这个能复制」的预期，然后在某些图上落空，而且不知道为什么。

### 发送入口总共有四个，其中**首页图墙那枚是明写偏离**

| 入口 | 在哪 | 形态 |
|---|---|---|
| 卡片「⋯」菜单里那一项 | 浏览页（合并后那条列表） | 菜单项 |
| 首页图墙卡片右上角那枚 | `features/discover/CardSendButton.tsx` | **直接一枚按钮** |
| 阅览器里那枚 | 全屏阅览左上角 | 按钮 + 文案 |
| `Ctrl+C` / `Cmd+C` | 全屏阅览 | 快捷键（按钮旁边写着） |

裁定 4 的原话是「一个动作只出现一处」、发送统一走「⋯」菜单。**首页图墙那枚是对它的明写偏离**
（2026-09-26，任务《2026-09-26-首页改版》§5.1）：那条裁定的语境是**合并后的列表**，
那里卡片同时需要编辑、删除、发送，所以菜单是对的；而图墙**没有编辑也没有删除**
（它是「随便看看」，不是管理面），为了一枚按钮挂一个只有一项的菜单是净负担，
发送又是这个产品的核心动作、要一击可达。

**偏离只覆盖图墙那一屏**：首页两条 rail 的卡片上**一枚浮层按钮都没有**（连收藏也不给），
要发送就点开（阅览器里有）或者去 `/browse`。「哪一屏该有」的判据是*那一屏有没有管理面*，
不是「卡片都长得一样」。

## 4. 三条路径

### 4.1 桌面静图 → 剪贴板

```
fetch 原图 → 转成 PNG Blob → ClipboardItem → navigator.clipboard.write
```

JPG / WebP 静图**必须先转 PNG**（canvas 转一道），因为规范只保证 `image/png`。

⚠️ **取原图必须绕过 HTTP 缓存：`fetch(url, { cache: 'reload' })`。这不是性能取舍，是正确性开关**
（2026-09-25 实测）。页面里有几处把**同一张原图**当 `<img>` 渲染（全屏阅览器 `toSlide`、编辑面板、
动图 hover 播放），这些请求**不带 `Origin`**；而跨域对象存储只在请求带 `Origin` 时才回
`Access-Control-Allow-Origin`、也只在那种时候才回 `Vary: Origin`（r2.dev 实测如此）。于是缓存里
落的是一份**既没有 ACAO、又没有 `Vary`** 的响应，它匹配之后**任何**请求，包括这次 cors 模式的
`fetch` → CORS 检查失败 → 报「取不到原图」，**而 bucket 的 CORS 其实是好的**。

症状因此是「**图看得见、右键能复制，点「复制」每次都失败**」，且**只要这张原图被显示过一次就长期
如此**（缓存条目会被 304 续命）。别读成部署配错了——那正是这条坑误导人的地方，
[部署手册 §8.3](../../../docs/deployment.md) 已按此更正排查顺序。

`cache: 'no-cache'` 顶不了这一条：它拿着缓存里那份**本身就缺 ACAO** 的条目去问 304，合并后谁赢说不清。
代价是每次取图真的下一次网络（不再吃缓存），错的字节没法用，这个代价必须付。
验收脚本 `scripts/verify-copy-original-cache.mjs`——**去掉 `reload` 它会变红**（跨域媒体源 + 真剪贴板读回）。
⚠️ 它和 `mock-api.mjs`、其余 `verify-*.mjs` 一样**不进版本库**（根 `.gitignore`），是联调期的一次性
断言脚本、不是常驻回归套件（要常驻得等「测试设施与 CI」那条任务，见 `joint-tasks/`）。**所以这条不变量的
保障是它写在本文里，不是那个脚本会一直有人跑。**

**必须在用户手势的同步调用栈里发起。** Safari 对剪贴板写入的用户激活要求最严格，`await fetch` 之后再 `write` 会失败。用 `ClipboardItem` 接受 Promise 的形式：

```ts
new ClipboardItem({ 'image/png': fetchAsPng(url) })  // 传 Promise，不 await
```

成功后给明确反馈（「已复制」）。**没有反馈的复制等于没复制**——剪贴板是不可见的。

反馈**怎么显示**归 [feedback.md](feedback.md)：2026-09-24 起是右上角 toast（`lib/toast.tsx`
的 `notifySend`），页面里不再有那一行裸文字。文案仍由 `lib/clipboard.ts` 的 `sendNote`
定，两页对同一个动作说同一句话。

⚠️ 那句话**只说「已复制」**。此前是「已复制，去微信 Ctrl+V」，2026-09-24 按产品负责人
的裁定砍掉了后半句：这个产品要发的不只有微信（还有 Telegram / Discord / 钉钉……），
指名一个应用会让用别的人以为没成；而「复制之后粘到哪」是用户本来就知道的事。

### 4.2 桌面动图 → 下载 / 拖拽

主路径是下载到本地再拖进聊天窗口。

拖拽路径（Chrome 的 `DownloadURL` 机制，从网页直接拖进微信）**尚未验证**，见 [SPEC §9.12](../../../spec/09-decisions.md)。验证可行之前不要在 UI 上承诺它。

### 4.3 手机 → 系统分享

```ts
if (navigator.canShare?.({ files: [file] })) {
  await navigator.share({ files: [file] })
}
```

**先 `canShare` 再 `share`。** 不是所有移动浏览器都支持文件分享，不检查会抛异常。

不支持时降级到下载，**不要显示一个点了报错的分享按钮**。

## 5. 能力探测，不做 UA 判断

```ts
// ✗ UA 判断永远追不上现实
if (/iPhone|Android/.test(navigator.userAgent)) { ... }

// ✓ 分享要先过一道「这是触屏优先设备吗」
if (touchPrimary() && navigator.canShare?.({ files: [f] })) { ... }
else if (navigator.clipboard?.write) { ... }
else { downloadFlow() }
```

**这和 [api 端不按 baseUrl 猜供应商](../../../api/agents/rules/ai-providers.md)是同一条原则**：能力靠探测，不靠猜。

**`touchPrimary()` 那一道是 2026-09-24 补上的，不能省。** 桌面 Windows Chrome 的 `navigator.canShare({ files })` 返回 `true`（系统分享面板确实存在），所以只按 `canShare` 分流的话，**桌面静图会走分享路径**——而 §3 要求它的按钮写「复制」、[SPEC §9.2](../../../spec/09-decisions.md) 说桌面主路径是「点一下切回微信 `Ctrl+V`」。**探测顺序不能推翻这两条**，`touchPrimary()` 就是那道闸：

```ts
matchMedia('(pointer: coarse)').matches
```

**它不是 UA 判断**，是和 `prefers-color-scheme` 同类的平台能力查询，符合本节的原则。`lib/clipboard.ts` 里叫 `touchPrimary()`，代码里写了理由。

探测结果决定按钮长什么样，**在渲染时就决定，不是点击后才发现**。

## 6. 失败要有出路

剪贴板写入失败（权限被拒、非安全上下文、Safari 的用户激活判定）时，**自动降级到下载**，并告诉用户发生了什么。

不要只弹一个「复制失败」。用户的目标是把图发出去，复制只是手段——手段失败了就给另一个手段。

**文案里不要点名一个猜测的原因。** 这里原来写的是「取不到原图（**可能是 R2 的 CORS 没放行 GET**）」，
而 2026-09-25 那次的毛病根本不在 R2（见 §4.1）——**猜错的原因比不说更坏**：读的人拿着它去翻部署
配置，越翻越远。取图失败的原因不止一种（被拦下、断网、对象不在），说得清的是 HTTP 状态码那种
（`原图返回 HTTP 404`），说不清的就只说「取不到原图（请求被拦下或网络不通）」，把判断留给能看到
日志的人。同理，**同一句失败不要说两遍**：降级到下载时，原因由「为什么发起下载」那半句负责，
下载再失败只补结果（「下载也没成」），否则用户看到的是「取不到原图（…），取不到原图（…）」——
2026-09-25 之前线上就是这个样子。

## 7. 键盘路径

> ⚠️ **2026-09-26 起，列表页那条键盘路径不存在了。** 这一节此前写的是
> 「`↑` `↓` 选择、`Enter` 打开全屏阅览、`Esc` 取消选中」——那是首页结果区的东西，
> 首页改版之后首页不渲染结果（SPEC §9.30），整条路径（`features/search/use-search.ts` 的
> `focusedOptionIndex` 与那个整页 `onKeyDown`）随之删除。**不是漏了，是明确不做**
> （任务 2026-09-26-首页改版 §5.2）：搬到浏览页要做网格里的二维方向键，是另一个量级的改动。
> **代价照实认下**：键盘用户只能 Tab 进卡片、再按卡片自己的按钮（图片帧 / 发送 / 收藏）；
> 首页因此**不能有**「只有键盘到得了」或「只有键盘到不了」的入口。
> 走查遗留的那条「浏览页 Tab 23 步才进第一张卡」**不因本次裁定消失**，它另条处理。

**今天还在的键盘路径只剩两处**（都挨着发送，这是本节的主题）：

1. **卡片上的按钮**——图片帧、发送键、收藏、浏览页的「⋯」，都能 Tab 到、能回车 / 空格触发。
   它们是普通 `<button>`，走的是浏览器原生路，没有一层页面级键盘状态机。
2. **全屏阅览里**——`Ctrl+C` / `Cmd+C` 发送当前这一张，以及下一节那枚**看得见的**按钮。

⚠️ **2026-09-26（裁定 4）起 `Enter` 不再是「复制 / 发送」。** 卡片图片下方那枚全宽发送按钮撤掉了，`Enter` 打开全屏阅览（焦点在图片帧上时）——**它指向的行为必须在界面上看得见**，一个只有按下去才知道发生了什么的键比没有这个键更坏。发送的入口在可见的地方：卡片「⋯」菜单里那一项、阅览器里那枚按钮、以及首页图墙卡片上那枚（§3 那张表）。裁定原文见任务《2026-09-26-检索筛选合一》§3。

**动图与静图在这条路径上不再有行为差别**（都是打开阅览）；差别整个移到「发送」那一击上，仍由 `detectSendPath` 在**渲染时**分流，判断依据一个字没变。

### 全屏阅览里的两个发送入口：`Ctrl+C` / `Cmd+C`，和那枚**看得见的**按钮

```text
桌面 / 手机   ← 那枚按钮（左上角，文案随 isAnimated 变，「复制」或「下载」或「分享」）
桌面         ← 也可以按 Ctrl+C / Cmd+C，按钮旁边写着一句提示
```

**两者调的是同一个函数**（`LightboxViewer.tsx` 的 `sendImage` → `sendMeme` → `sendNote` →
`notifySend`），也就是和卡片「⋯」菜单里那一项**完全同一个**：分流不看「用户点的是按钮还是
按的键」，看的是 `isAnimated` 与能力探测，所以动图在两者上都落到下载、都说「动图写不进
剪贴板」。三条平台也一样——触屏设备上走的是系统分享。

- `Ctrl+C`（2026-09-24 加，产品负责人提的：阅览器里按下去没反应），四条不能少：
  `ctrlKey || metaKey`（macOS 是 `Cmd`）、挡掉 `Shift` / `Alt` 组合（`Ctrl+Shift+C` 是开发者
  工具）、挡掉 `e.repeat`（按住不放会连着下载好几个文件）、`preventDefault()`（浏览器默认
  动作是复制选区，而 `.yarl__container` 是 `user-select: none`，没东西可复制，不挡的话它会
  抢在异步写入之前落一次空内容）。
- **那枚按钮（2026-09-26 加）是这一面上唯一看得见的入口**，而且它同时是**搜索流里鼠标用户
  的实际出口**——同一批裁定把卡片上那枚全宽按钮撤了。所以它有三个不能挪的性质：
  1. **哪个尺寸都在**。宽屏右栏与缩略图轨道都是 `lg` 起才显形，把按钮摆进那一支等于
     手机上阅览器里发不出去，且不报错；
  2. **文案与图标一起随 `detectSendPath` 变**，渲染时定下来——动图上写「下载」配下载图标；
  3. **落点在左上角**：窄屏底部中间是信息卡、宽屏底部整条是缩略图轨道，左下角两种版式都被占。
- `Ctrl+C` 那句提示**按指针分档**（触屏那一档没有 Ctrl 键）：基线可见、藏在
  `pointer-coarse` 下面，闸门与 `lib/touch.ts` 同一条，不是宽度断点。

⚠️ **`Ctrl+C` 那条把 toast 抬到了 `10000`**（高于阅览器的 `9999`）。这不是顺手的层级调整：
`.yarl__container` 是不透明黑底、铺满视口，toast 在它下面屏幕上什么都没有，
而「已复制」只从 toast 出来——没有反馈的复制等于没复制（§4.1）。见
[styling.md](styling.md)「层级 10000」。

⚠️ **但「看得见」和「点得到」是两件事，这次只解决了前者。** 验收里读像素实测：toast 确实
画在黑底之上（底 `255,255,255`，它下面 40px `10,10,10`），可它的**指针事件仍然收不到**——
YARL 进阅览器时给 `#root` 挂了 `inert`，Toaster 就在里面，于是「关闭提示」按钮、
降级提示里那条「在新标签页打开原图」的链接在阅览器开着时都是死的（`aria-hidden` 那一半
就是一直记着的「读屏听不见」）。换个层级解决不了，移出 `#root` 也只解决一半，推导与后续
写在这里不要重复：[styling.md](styling.md)「已知缺口」。**「已复制」那条本身没有可点的
东西**（只剩一个关闭按钮，4 秒后自己会走），所以这条路径的反馈是够用的——但别顺口说成
「toast 在阅览器上面都是可用的」。

⚠️ 还有一条踩过的坑：**别拿 `elementFromPoint` 判「画没画在上面」。** 上面那个 `inert`
会让命中测试整个跳过 toast，而它照画不误——那条路会得出反的结论。

⚠️ 曾经有一条踩过的坑：**结果项靠 `[data-index]` 找，而 toast 的 `<li>` 也带这个属性**，
裸的 `document.querySelector` 会在有提示时把焦点交给一条 toast。**今天产品代码里已经没有
按这个属性找回结果项的地方了**（那套键盘路径 2026-09-26 随首页改版删除，见本节开头），
但 Sonner 的 `<li data-index>` 还在，规矩照旧、验收脚本改不动：**从 `document` 出发查
`[data-index]` 必须先限定范围**（见 `styling.md`「toast 的 `<li>` 也带 `data-index`」）。

## 8. 改了这里必须两端实测

桌面和手机行为完全不同，且都无法靠单测覆盖。

交付时说明**在哪些浏览器 / 设备上测了什么**。「本地看起来没问题」不算测过——本地通常是 Chrome 桌面，那恰好是三条路径里限制最少的一条。
