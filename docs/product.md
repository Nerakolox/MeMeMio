# 产品

> 一个能理解表情包含义的共享表情语言库。
> 不需要记得那张图叫什么、放在哪，只需要描述自己想说什么。

## 1. 要解决的问题

表情包收藏到几百张之后，就进入一个尴尬状态：**你知道自己有那张图，但找不到它。**

现有的存放方式全都以「图片在哪里」为索引：微信收藏按时间倒序、相册按文件夹、硬盘按文件名。可人在聊天时的检索方式恰恰相反——是从「我现在想表达什么」出发的：

- 想发一个「可爱一点的滚」
- 想发一个「看到逆天发言时用的」
- 想发一个「礼貌但很阴阳怪气」
- 想发一个「别人说了一大堆但我没听懂」

这些意图和图片的文件名、上传时间、所在文件夹之间没有任何关系，也往往和图上的文字无关。所以传统图库的三种索引方式全部失效，结果就是：收藏了几千张，实际反复用的只有那十几张。

本项目要做的不是「存更多图片」，而是**在存储和意图之间补上一层语义索引**。

## 2. 定位

一个邀请制的**共享**表情包检索服务：所有人的上传进同一个库、所有人都能搜到，编辑对全员开放，删除限上传者本人或管理员。

核心是四步闭环：

```
导入  →  自动理解  →  语义搜索  →  一键使用
```

其中「自动理解」在入库时一次性完成，搜索时只查索引、不再调用 AI。这是延迟和成本能同时压下来的关键——**AI 的开销发生在入库，不发生在每次搜索**。

**视觉模型由用户自行配置，Embedding 模型全站统一由部署方配置**，系统不锁定任何供应商。两者待遇不同是「库共享」这个前提的直接后果，见 [SPEC §9.3](../spec/09-decisions.md) 与 [§9.6](../spec/09-decisions.md)。

## 3. 功能清单

### 3.1 导入

不区分来源，统一走文件上传：

- 多选文件上传
- 拖拽文件夹（递归扫描）
- 剪贴板 Ctrl+V 粘贴
- ZIP 包解压导入
- 手机端从相册选择

**去重在调 AI 之前，且作用域是全局的。** 表情包库重复率极高，先去重能直接省掉相应比例的 AI 调用——用户自带 key 之后，这是在省用户自己的钱。共享库里还多一层意义：两个人传了同一张图，公共库里不该出现两条记录。

导入是异步的，通过 SSE 向前端推送进度。上千张图的处理过程中，应用应当保持可用。

**未配置模型时的行为：** 部署方的默认视觉配置在正常情况下总是存在，所以这属于边缘场景。但若默认值也没设，导入仍然允许——图片正常入库、生成缩略图和哈希，但 `tagStatus = pending`，等配置好之后一键批量补打标。**不能因为没配模型就拒绝上传。**

### 3.2 自动理解

**单次视觉调用产出全部结构化信息**，不做独立的 OCR 链路。

理由：本地 Tesseract 对表情包的艺术字体中文基本不可用，白搭一套基础设施；而多模态模型本来就能在同一次调用里顺带完成 OCR。

单次调用产出 `ocrText` / `description` / `emotions[]` / `scenes[]` / `tags[]` 五个字段，后三个从固定词表中选。字段定义见 [SPEC §5.2.3](../spec/05-data-models.md)，词表规则见 [SPEC §4](../spec/04-vocabulary.md)。

### 3.3 搜索

- 自然语言语义搜索（主要入口）
- OCR 文字精确搜索
- 标签筛选
- 三路结果 RRF 融合排序
- 按情绪 / 场景 / 标签 / 是否动图 / 收藏状态 / 上传者 浏览

**搜索范围始终是全库**，不按上传者过滤。「只看我上传的」和「只看我收藏的」是浏览侧的可选筛选项，不是默认，更不是安全边界。**收藏状态是每人独立的**，A 的收藏不会出现在 B 的界面上。

### 3.4 使用

按 [SPEC §9.2](../spec/09-decisions.md) 的能力边界分流：

- 桌面静态图 → 点击即复制
- 桌面动图 → 下载 / 拖拽
- 手机端 → 系统分享面板
- 键盘操作：`↑` `↓` 选择、`Enter` 复制、`Esc` 关闭

### 3.5 管理

| 功能 | 谁可以 |
|---|---|
| 编辑 / 增删标签与描述 | **所有人** |
| 收藏 | 所有人（写自己的） |
| 删除（软删） | 上传者本人或管理员 |
| `needs_manual` 待处理列表 | 自己的；管理员看全部 |
| 批量补打标 / 重新打标 | 自己上传的；管理员可对任意图执行 |

**编辑对全员开放**——标签在共享库里是公共品，谁发现标错了都顺手改掉对所有人都是净收益。防滥用靠记录 `editedBy` / `editedAt`，MVP 不做完整修改历史表，出滥用再加。

**删除是软删，不是物理删除。** 别人可能已经收藏了这张图，硬删会在别人的收藏夹里留下空洞。完整的权限与实施约束见 [SPEC §3](../spec/03-auth-permission.md)。

### 3.6 去重

两层，性质完全不同：SHA-256 精确去重是机器判断、零误判、静默跳过；pHash 近似去重会误判、必须让人来判断，走待确认队列。

**这是最容易设计错的一处**——完整论证见 [SPEC §9.7](../spec/09-decisions.md)，流程见 [SPEC §6.2](../spec/06-endpoints.md)。

还提供「扫描重复」的主动查重入口，用于导入前就存在的历史库：找出 Hamming 距离在阈值内的图片对，按相似度分组展示，优先展示分辨率更高的那张，用户确认后才删。异步跑，结果存临时表，**不直接删除任何东西**。

> **注意：动图抽帧里也用到 pHash，但那是另一回事。** 抽帧流程里 pHash 用于去掉动图内部的重复帧（长静止段），作用域是同一个文件的帧集合；这里讲的是跨文件的入库去重。二者计算对象不同，不要混用。

### 3.7 配置页

**用户设置页**：视觉主 / 副通道（收在「高级选项」里）、每组独立的「测试连接」、API Key 只显示后四位、显示当前用的是默认还是自己的配置、显示**自己上传的**那部分的打标状态统计。

**管理页（仅管理员）**：Embedding 配置 + 测试连接、重建索引入口与进度、全站打标状态统计、用户与邀请码管理、对任意图片重新打标 / 删除。

提示文案是契约的一部分，见 [SPEC §9.9](../spec/09-decisions.md)。

## 4. 明确不做（MVP 阶段）

| 不做 | 原因 |
|---|---|
| 微信 / QQ / TG 导出工具 | 第一公里问题独立且工作量可能超过搜索本身，拆成独立子项目 |
| 模型能力自动路由 | 「测试连接」探测能力就够了，不做按图片内容自动选模型这类智能调度 |
| 每用户独立的 Embedding 模型 | 共享库下跨模型向量不可比，这不是妥协是硬约束，见 SPEC §9.6 |
| 完整的编辑历史表 | 记 `editedBy` / `editedAt` 就够了，出滥用再加 |
| 细粒度权限 / 分组可见性 | 一个圈子一个库，全员可见，见 SPEC §9.1 |
| `useCount` / `lastUsedAt` 参与排序 | 新库没有使用历史，排序项形同虚设 |
| 独立 OCR 链路 | 并入单次视觉调用 |
| Batch API 五折 | 兼容层用不了，且成本基数本就可忽略 |
| Reranker 精排 | 架构留位，MVP 后再加 |
| 合集 / 统计页 / 社交 / 公开市场 / 好友分享 | 与核心闭环无关 |
| 独立向量数据库 | pgvector 在这个量级绰绰有余 |

**这张表是用来挡需求的。** 有人提「加个合集功能吧」时，先看它在不在这里；在的话，讨论的应该是「推翻这条的理由是什么」，而不是「做起来难不难」。

## 5. 后续扩展

按价值排序：

1. **Qwen3-Reranker 精排** — 用户只看前几个结果，`precision@5` 就是一切。在混合检索的前 50 条上过一遍 reranker，是打标质量之外提升最大的杠杆。**放在管理员配置里，不开放给用户**，理由见 [SPEC §9.10](../spec/09-decisions.md)。
2. **导出工具** — 独立的命令行脚本，扫描微信 / QQ 缓存目录导出成普通文件夹，再拖进 Web 端。与主项目解耦，可单独迭代。
3. **浏览器扩展 / 桌面端** — 补上 Web 形态在「发送」上的短板，实现全局快捷键唤起。
4. 相似表情聚类、图片反向搜索、表情包 Pack 分享。
