# 评测集

**这是本项目投入产出比最高的一件事，也是写核心代码之前必须先做的。**

成本几毛钱，但能省掉后面推倒重来——没有它，「换个模型效果好不好」「改了提示词有没有变好」这两个问题只能靠看几张图拍脑袋。

## 1. 为什么它比想象中重要

在模型可配置 + 库共享之后，评测集的价值不只是「测一下准不准」：

1. 验证提示词质量——尤其是「阴阳怪气」「摆烂」「表面同意」这类判断准不准
2. **横向对比不同视觉供应商**——既然用户能随便换模型，这就是唯一客观的比较工具，也是设置页推荐值的依据
3. 对比 0.6B / 4B / 8B 三档 embedding 的实际命中差异（通用榜单不代表「中文梗图语义」这个具体任务）
4. 对比「HyDE 不加 instruct」与「原始查询加 instruct」两种组合
5. **验证固定标签词表在不同模型下是否真的能对齐**——这一条决定 [SPEC §4](../spec/04-vocabulary.md) 的词表能否从 `proposed` 转 `accepted`

第 2 条是共享库带来的：用户配了什么模型会影响所有人，而「这个模型够不够格」需要一个客观答案，不能靠感觉。

## 2. 怎么做

从自己库里挑 **30 张**有代表性的表情包，手工标注期望结果，做成一个可重复运行的小评测。

**30 张不是随便挑的 30 张**，覆盖面比数量重要：

| 类型 | 至少几张 | 为什么必须有 |
|---|---|---|
| 动图 | 5 | 验证抽帧方案——尤其是「文字在后几帧才出现」的那种 |
| 纯文字（截图梗） | 5 | OCR 通路的主要用户 |
| 无文字（纯表情 / 动物） | 5 | 向量通路的主要用户，OCR 完全帮不上忙 |
| 语气微妙（阴阳怪气 / 表面同意） | 5 | 产品命门，也是模型之间差距最大的地方 |
| 擦边 | 3 | 验证双通道降级真的会触发 |
| 同模板不同字 | 2 对 | 验证 pHash **不会**误判成重复 |

最后一项容易漏：它测的不是「能不能查出重复」，是「**会不会把不该判为重复的判成重复**」——那才是 [SPEC §9.7](../spec/09-decisions.md) 把判断权交给人的原因。

## 3. 标注什么

每张图标注三样：

```
{
  file: "...",
  expect: {
    ocrText: "图上的字，人工抄一遍",       // 精确匹配不现实，看包含关系
    emotions: ["无语"],                   // 期望命中的，允许模型多标
    scenes: ["回复长篇大论"],
    tags: ["猫"]
  },
  queries: [                              // 这张图应该被哪些查询搜到
    "今天真的不想上班",
    "可爱一点的滚"
  ]
}
```

**`queries` 是最有价值的部分。** 标签准不准是中间指标，「我描述了意图，这张图有没有排进前几」才是产品真正的指标。

## 4. 指标

| 指标 | 怎么算 | 目标 |
|---|---|---|
| 标签命中率 | 期望标签 ∩ 实际标签 / 期望标签 | 越高越好，但别追 100% |
| 标签污染率 | 实际标签中明显不相关的比例 | **这个更重要**，脏标签会污染全库搜索 |
| OCR 包含率 | 期望文字是否是实际 `ocrText` 的子串 | 纯文字类应接近 1 |
| `recall@5` | 每条 query 的目标图有没有进前 5 | 主指标 |
| 词表合规率 | 输出标签落在词表内的比例 | 必须接近 1，否则词表设计有问题 |

**`precision@5` 比 `recall@50` 重要得多。** 用户只看前几个结果，第 30 位和没搜到没有区别。

## 5. 什么时候必须重跑

- 改打标提示词
- 改 `shared/vocab/vocab.json`（[SPEC §4.4](../spec/04-vocabulary.md) 强制要求）
- 换 embedding 模型或改截断 / 归一化逻辑
- 改 RRF 参数或任一通路的召回条数
- 评估一个新的视觉供应商要不要进推荐列表

前四项属于「改了之后不跑就不知道有没有变坏」的改动。**这不是建议，是 [`agents/rules/collaboration.md`](../agents/rules/INDEX.md) 里的要求。**
