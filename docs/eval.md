# 评测集

**这是本项目投入产出比最高的一件事，也是写核心代码之前必须先做的。**

成本几毛钱，但能省掉后面推倒重来——没有它，「换个模型效果好不好」「改了提示词有没有变好」这两个问题只能靠看几张图拍脑袋。

## 1. 为什么它比想象中重要

在模型可配置 + 库共享之后，评测集的价值不只是「测一下准不准」：

1. 验证提示词质量——尤其是「阴阳怪气」「摆烂」「表面同意」这类判断准不准
2. **横向对比不同视觉供应商**——既然用户能随便换模型，这就是唯一客观的比较工具，也是设置页推荐值的依据
3. 对比 0.6B / 4B / 8B 三档 embedding 的实际命中差异（通用榜单不代表「中文梗图语义」这个具体任务）
4. 对比「HyDE 不加 instruct」与「原始查询加 instruct」两种组合
5. **验证固定标签词表在不同模型下是否真的能对齐**——这一条决定 [SPEC §4](../spec/04-vocabulary.md) 的词表能否从 `proposed` 转 `accepted`

第 2 条是共享库带来的：用户配了什么模型会影响所有人，而「这个模型够不够格」需要一个客观答案，不能靠感觉。

## 2. 怎么做

从自己库里挑 **30 张**有代表性的表情包，手工标注期望结果，做成一个可重复运行的小评测。

**30 张不是随便挑的 30 张**，覆盖面比数量重要。

### 2.1 覆盖面必须照着真实库来，不是照着「表情包」这个词的刻板印象

下表的配比来自对本项目首个真实库的实测（2026-09-13，989 张 QQ 收藏）：

| 实测项 | 值 |
|---|---|
| 总数 / 其中 GIF | 989 / 252（25%） |
| 长边 中位 / p10 / 最小 / 最大 | 512 / 240 / **50** / 1920 |
| 长边 ≤ 256 的张数 | **133（13%）** |
| 近正方形（宽高比 < 1.3） | **822（83%）** |
| 单帧伪 GIF | 252 个里 13 个 |
| 主体 | 绝大多数是**二次元角色**，且多数**无文字** |

> ⚠️ **这一条比配比本身更重要：这个库里几乎没有「中文梗图」那种表情包。**
>
> 没有截图对话梗、没有明星鬼畜。它是一个二次元贴纸库——主体高度同质，一眼看去几乎都是「一个动漫角色的脸」。
>
> 两个直接后果，不要在实现里假设反面：
>
> 1. **`tags.subject` 在这个库里几乎没有区分度。** 选出来的 30 张评测图，`subject` 是「动漫角色」的有 **30/30**；`style` 是「动漫」的有 25/30。标签过滤那一路基本废掉，检索重担全压在 `description` 向量和 OCR 上。这动摇的是 [§9.10](../spec/09-decisions.md) 三路混合的前提，交给[词表任务](../joint-tasks/2026-09-13-vocab-v1.md)。
> 2. **[§9.18](../spec/09-decisions.md) 的别名层不是长尾锦上添花，是主路径。** 用户搜的是角色名和梗名，而模型只会说「一个粉色头发的女孩」。
>
> `tags` 里唯一还有区分度的是 `无文字` / `带字幕` 这一对（15 / 9）——它直接指明这张图该走哪条检索通路，精简词表时不要连它一起砍。

### 2.2 配比

| 类型 | 至少几张 | 为什么必须有 |
|---|---|---|
| 无文字 · 纯角色表情 | 8 | **全库主力**。向量通路的唯一用户，OCR 完全帮不上忙 |
| 动图 | 6 | 验证抽帧；其中 1 张必须是**单帧伪 GIF** |
| 有文字 | 5 | 见下面的排版拆分，别都挑同一种 |
| 语气微妙（阴阳怪气 / 表面同意 / 假哭） | 4 | 产品命门，也是模型之间差距最大的地方 |
| 擦边 | 3 | 验证双通道降级真的会触发 |

合计大于 30 是正常的——**一张图会同时算进好几行**（例如一张带底部字幕条的语气微妙动图同时占三行）。挑的时候按行凑满，不按行相加。

### 2.3 必须单独挑的七个坑

这七类不是「类型」，是**已知会让实现出错的输入**。每类哪怕只有 1–2 张也必须在评测集里，否则对应的 bug 只会在线上被用户发现。

选图不要靠肉眼找相似——**先跑一遍全库 pHash 两两比对，按 Hamming 距离升序看**。实测 989 张里 Hamming ≤ 8 的有 **40 对**，全是人工翻不出来的：

| 坑 | 至少几张 | 它测的是什么 | 实测样本 |
|---|---|---|---|
| **同模板不同字** | 1 组 | pHash **不能**判成重复 | 同一张「摸头」底图配三条不同字幕，三张互相 Hamming 2–6 |
| **同角色不同表情** | 2 对 | 同上。同一角色的两张特写构图几乎一致，是本库里误判的头号来源 | 两组同角色特写，Hamming 3 |
| **大留白小主体** | 2 | 同上，但更阴险：主体只占中间一小块、其余纯白，**两张毫不相干的图 pHash 也会很近** | 两张不同角色的白底全身图，Hamming 3 |
| **同图不同画质 / 带水印** | 1 对 | 反方向：这两张**大概率该判为重复**，但 OCR 结果会完全不同 | 同一张漫画分镜，一张干净、一张被平铺水印盖满，Hamming **1** |
| **极小图**（长边 ≤ 160） | 2 | 实测 21 张，最小 50px。**放大不会凭空生出信息**，OCR 必失败、视觉模型也看不清——要的是它别报错、别把糊掉的笔画瞎猜成文本 | — |
| **非正方形**（竖长 / 横长） | 2 | 实测 167 张。缩放和拼图兜底最容易在这里出比例问题 | — |
| **倒装 / 打乱字序** | 1 | **文本通路必然失效。** `ocrText` 存的是乱序原文，用户搜的是正序，pg_trgm 匹配不上——只能靠向量或别名层兜 | 一张性暗示打乱字序写成的大字图 |

它测的不是「能不能查出重复」，是「**会不会把不该判为重复的判成重复**」——那才是 [SPEC §9.7](../spec/09-decisions.md) 把判断权交给人的原因。

> ⚠️ **「同模板不同字」那一组顺带是擦边降级的最佳测试，别浪费它。**
>
> 三张图的**画面完全相同**，只有字幕条不同，其中一条明显擦边、另外两条不是。也就是说：**是否触发内容拒绝只可能取决于文字，不可能取决于画面。** 这是唯一能把「模型到底是看图拒绝还是看字拒绝」这个问题问干净的样本，直接服务于 [§9.15](../spec/09-decisions.md) 的拒绝形态探测。
>
> 顺带也是 pHash 的极端情形：三张的差别只有底部一行字，Hamming 距离比很多**无关图之间**的距离还小。

> ⚠️ **「同图不同画质」和上面几类方向相反，不要混为一谈。**
>
> 前几类是「**不该**判重却判了」，这一类是「**该**判重，但判重之后要留哪张」。带水印那张的 `ocrText` 会被水印文字塞满，如果保留了它、丢掉干净的那张，检索质量是净损失。**去重保留哪张的策略需要一个依据，这对图就是。**

> ⚠️ **「倒装」这一坑是校对时才发现的，起草版把它标错了。**
>
> 起草标注时把那张图读成了「催人起床」，标了暴躁、催促，query 写的是「快出来」——**全错**。正序才是原意，而字面看过去毫无破绽。
>
> 它同时打中两处，不要只当成一个 OCR case：
>
> - **检索**——`ocrText` 只能存乱序原文（不能替用户「修正」成正序，那是在编造图上没有的东西）。于是用户用正序搜，pg_trgm 那一路必然落空，[§9.10](../spec/09-decisions.md) 三路只剩两路管用。这是文本通路在真实输入上失效的第一个实证样本
> - **拒绝形态**——它是第二根轴。「同模板不同字」那组测的是**明着擦边的文字**会不会触发拒绝；这张测的是**打乱字序之后模型还解不解得开**。两者都不可省
>
> 附带一条给打标提示词的约束：模型把乱序强行解释成一个通顺但错误的意思，算**污染**，不算努力。宁可它照抄不解释。

### 2.4 有文字的 5 张要覆盖三种排版

OCR 的难度不在「有没有字」，在**字长在哪、怎么排**。这三种在库里都真实存在，不要 5 张全挑第一种：

| 排版 | 样子 | 难点 |
|---|---|---|
| 底部字幕条 | 图下方一条白底黑字，如「我是fw，对不起」 | 最容易，基准线 |
| 对话气泡 | 气泡里竖排或横排，常带日文假名、颜文字、`w` | 版面切分，且**不是纯中文** |
| 画面内嵌大字 | 手写体压在画面上、描边、与背景纠缠，如「猫想要」 | 最难，也最常见 |

> 至少 1 张要**含日文或英文**。本库大量图带日文台词，而 `ocrText` 的期望值里如果一句日文都没有，OCR 通路的实际表现就没被测到。

## 3. 标注什么

每张图标注三样：

```
{
  file: "...",
  expect: {
    ocrText: "图上的字，人工抄一遍",       // 精确匹配不现实，看包含关系
    emotions: ["无语"],                   // 期望命中的，允许模型多标
    scenes: ["回复长篇大论"],
    tags: ["猫"]
  },
  acceptAlso: {                           // 可空。人工判定「两种读法都对」时才有
    emotions: ["开心"]                    // 模型标了既不算命中也不算污染
  },
  queries: [                              // 这张图应该被哪些查询搜到
    "今天真的不想上班",
    "可爱一点的滚"
  ],
  humanName: ["白圣女与黑牧师", "塞西莉亚"]  // 作品名 + 角色名 + 社群叫法，可空数组；见下
}
```

**`queries` 是最有价值的部分。** 标签准不准是中间指标，「我描述了意图，这张图有没有排进前几」才是产品真正的指标。

> ⚠️ **上面这个格式还是词表 v0.1.0 的三个标签字段，已经落下两次变更了**：[语义维度拆分](../joint-tasks/2026-09-22-语义维度拆分.md)（v0.2.0，六个数组）与 [内容分级](../joint-tasks/2026-09-22-r18-ratings-dimension.md)（v0.3.0，第七维 `ratings`）。
> 连示例本身都过期了——`scenes: ["回复长篇大论"]` 里那个词已经从词表里删掉，且没有 alias 可去。
>
> 好消息是**标签不用重标**。对着 v0.2.0 核过 `docs/fixtures/eval/manifest.json` 的 30 条：
> 23 条的标签按现在的维度写是不合法的，涉及 27 个「词还在、只是换了维度」的移动
> （`嘲讽` 从 `emotions` 去了 `purposes`、`坏笑` 去了 `expressions`……），
> **词表里彻底没有的词是 0 个**。也就是说这是一次**机械迁移**，不是重新标注。
> 人工校对过的那 3 条（`reviewed: true`）和 `humanName` / 那部分由库主人填写的 `queries`
> 都不涉及维度，**不受影响**。
>
> 迁移前跑评测集会把「维度拆对了」误判成「模型变差了」——模型把「嘲讽」标进 `purposes` 是**对的**，
> 而期望值还写在 `emotions` 里。这件事属于[评测集任务](../joint-tasks/2026-09-13-eval-set.md)。

> **`acceptAlso` 是给「人也要想一下」的图留的，不是给模棱两可的标注开后门。**
>
> 只在**人工判定两种读法都成立**时填，里面的词从命中率和污染率两个分母里同时剔除。全集目前只有一条（`698`：抿嘴微笑配爱心，「假笑/得逞」和「开心」都讲得通）。
>
> 两个方向都会坏事：一张连人都要想一下的图当成非黑即白的判据，量出来的是噪声不是能力；但什么都往这里塞，「语气微妙」这一档就等于没测。**它必须由人来填，AI 不能自己给自己开这个口子。**

> **`humanName` 的用法是反的：它是期望模型「说不出」的东西。**
>
> 这一栏填库主人自己看图就能叫出的名字，**作品名、角色名、社群叫法一律平铺进同一个数组**——它们在检索里是同一种东西（用户可能打的字），区分留给[别名层](../joint-tasks/2026-09-13-meme-lexicon.md)的数据模型去做。评测时它有两个用途，方向相反：
>
> - 对**打标**——模型输出里出现它算**污染**，不算命中。[§9.18](../spec/09-decisions.md) 的结论是不让模型命名，逼它猜只会得到自信的错名字
> - 对**检索**——把每一条当一条 query 跑。现在必然搜不到，这正是别名层要补的缺口，也是衡量补了之后收益多大的基线
>
> **它只记身份，不记梗短语。** 起草时给「我是fw，对不起」填了 `fw`，被库主人删掉了——`fw` 已经在 `ocrText` 里，文本通路本来就能搜到，塞进这一栏只会把别名层的收益虚报一遍。

### 3.1 实测：这一栏填出来什么样（2026-09-13）

库主人逐条填完 30 张的结果，**三个数字都不是当初预估的样子**：

| | 实测 | 起草时的预估 |
|---|---|---|
| 有名字的图 | **14 / 30** | 「会填得很满」 |
| 去重后的名字条数 | 29 | — |
| 库主人自己也认不出的 | **16 / 30** | 没预料到 |

三条必须写进实现的结论：

1. **名字查询不是一对一召回。** 6 条名字对应多张图——`塞西莉亚` → 3 张，`kipfel` → 2 张，`魔裁` → 2 张。评测脚本算 `recall@5` 时**每条名字 query 的正确答案是一个集合**，按单目标写会算错。

2. **别名会和普通词撞车，而且撞得很狠。** 填出来的名字里有 `本`、`教授`、`BA`、`猫娘`、`猫`。`本` 是单个常用汉字，`教授` 是普通名词——如果别名层把 `教授` 直接映射到某张图，全站所有正经搜 `教授` 的请求都会被劫持。这是 [`meme-lexicon`](../joint-tasks/2026-09-13-meme-lexicon.md) 里「耄耋 → 一堆老年人的图」的反方向，**而且更常见**。

3. **作品名本身也有别名，别名层是两层不是一层。** `GIRLS BAND CRY` = `闺泣`，`蔚蓝档案` = `BA`，`魔法少女的魔女审判` = `魔裁`。除了「角色 → 作品」，还得有「作品别名 → 作品」。

> **16/30 认不出，这个数字是上限不是待办。** 库主人认不出的图，别名层再怎么做也补不了——那部分的检索只能靠 `description` 向量。所以别名层的收益天花板在这个库上是 **47% 的图**，不是全部。立项时按这个数算。

## 4. 指标

| 指标 | 怎么算 | 目标 |
|---|---|---|
| 标签命中率 | 期望标签 ∩ 实际标签 / 期望标签 | 越高越好，但别追 100% |
| 标签污染率 | 实际标签中明显不相关的比例 | **这个更重要**，脏标签会污染全库搜索 |
| OCR 包含率 | 期望文字是否是实际 `ocrText` 的子串 | 纯文字类应接近 1 |
| `recall@5` | 每条 query 的目标图有没有进前 5 | 主指标 |
| 词表合规率 | 输出标签落在词表内的比例 | 必须接近 1，否则词表设计有问题 |

**`precision@5` 比 `recall@50` 重要得多。** 用户只看前几个结果，第 30 位和没搜到没有区别。

## 5. 什么时候必须重跑

- 改打标提示词
- 改 `shared/vocab/vocab.json`（[SPEC §4.4](../spec/04-vocabulary.md) 强制要求）
- 换 embedding 模型或改截断 / 归一化逻辑
- 改 RRF 参数或任一通路的召回条数
- 评估一个新的视觉供应商要不要进推荐列表

前四项属于「改了之后不跑就不知道有没有变坏」的改动。**这不是建议，是 [`agents/rules/collaboration.md`](../agents/rules/INDEX.md) 里的要求。**
