# Mememio — 个人表情包语义检索系统

> 一个能理解表情包含义的共享表情语言库。
> 不需要记得那张图叫什么、放在哪，只需要描述自己想说什么。

---

## 一、要解决的问题

表情包收藏到几百张之后，就进入一个尴尬状态：**你知道自己有那张图，但找不到它。**

现有的存放方式全都以「图片在哪里」为索引：微信收藏按时间倒序、相册按文件夹、硬盘按文件名。可人在聊天时的检索方式恰恰相反——是从「我现在想表达什么」出发的：

- 想发一个「可爱一点的滚」
- 想发一个「看到逆天发言时用的」
- 想发一个「礼貌但很阴阳怪气」
- 想发一个「别人说了一大堆但我没听懂」

这些意图和图片的文件名、上传时间、所在文件夹之间没有任何关系，也往往和图上的文字无关。所以传统图库的三种索引方式全部失效，结果就是：收藏了几千张，实际反复用的只有那十几张。

本项目要做的不是「存更多图片」，而是**在存储和意图之间补上一层语义索引**。

---

## 二、产品定位

一个邀请制的**共享**表情包检索服务：所有人的上传进同一个库、所有人都能搜到，编辑对全员开放，删除限上传者本人或管理员。

核心是四步闭环：

```
导入  →  自动理解  →  语义搜索  →  一键使用
```

其中「自动理解」在入库时一次性完成，搜索时只查索引、不再调用 AI。这是延迟和成本能同时压下来的关键——**AI 的开销发生在入库，不发生在每次搜索**。

**视觉模型由用户自行配置，Embedding 模型全站统一由部署方配置**，系统不锁定任何供应商（见 3.3）。两者待遇不同是「库共享」这个前提的直接后果，理由见 3.7。

---

## 三、关键决策与取舍

这一节是整个文档最重要的部分。功能清单谁都写得出来，真正决定项目成不成立的是下面这些选择。

### 3.0 前提：库是共享的

**决定：所有人的上传进同一个库，所有登录用户都能搜到全部内容。编辑描述与标签对全员开放，删除和重新打标限上传者本人或管理员。**

这一条编号为 0，因为它不是并列的一项取舍，而是下面所有取舍的前提 —— 3.3 和 3.7 的形态完全由它决定。

| 维度 | 归属 |
|---|---|
| 图片内容、描述、标签 | 共享，全员可搜可用 |
| 编辑描述与标签 | 全员可改（见 4.5） |
| 删除、重新打标 | 上传者本人或管理员 |
| 收藏 | 每人独立 |
| 视觉模型配置 | 每人独立 |
| Embedding 模型配置 | 全站一份，仅管理员（见 3.7） |

**为什么共享：** 表情包的价值随库的规模增长，而好图是稀缺的 —— 同一个圈子里，别人收藏的那张正好是你想要的，概率相当高。每人一个隔离库等于把 N 个人的贡献切成 N 份，每份都很小，而这个项目的整个前提就是「库大到自己找不着了」。

**为什么编辑不设限、删除设限：** 标签在共享库里是**公共品** —— 谁发现标错了都顺手改掉，对所有人都是净收益，拦住反而降低质量。删除是不可逆的破坏性操作，两者的风险不对称，所以待遇不同。记一个 `edited_by` 防滥用就够了。

**换来的代价有三个，都必须正视：**

1. **Embedding 模型不能再各用各的** —— 硬性技术后果，见 3.7
2. **打标质量从私事变成公共品** —— 一个人配了烂模型，污染的是所有人的搜索结果，见 3.3
3. **私密性消失** —— 3.6 说个人库里必然有擦边内容，那些内容现在默认对所有被邀请的人可见。这不是代码问题，是邀请谁之前要先想清楚的事

### 3.1 形态：Web SPA，不是桌面端

**决定：** 标准单页应用（Vite + React），前后端同域部署，不用 Next.js。

**取舍：** 桌面端（Tauri/Electron）在「发送」这一步明显更强——能把**文件**放进系统剪贴板，GIF 可以直接 Ctrl+V 发进微信；还能读本地缓存目录、做全局快捷键唤起。Web 端做不到这些。

选 Web 的理由：部署一次所有人可用、跨设备、手机端天然支持。而手机端恰恰能绕开 Web 最大的短板（见 3.2）。

**它不是 Next.js 的理由：** 这东西是登录后才能用的工具，没有 SEO 需求、没有首屏压力、不需要 SSR。Next.js 在这里只增加心智负担。SPA + 独立 API 更合身。

### 3.2 「发送」这一步的真实能力边界

这是整个产品的价值所在，也是 Web 形态最大的约束，必须说清楚。

浏览器的 `ClipboardItem` 规范只保证 `text/plain`、`text/html`、`image/png` 三种类型。这意味着：

| 场景 | 能力 | 体验 |
|---|---|---|
| 桌面 · 静态图（PNG/JPG/WebP） | 写入剪贴板 | ✅ 点击即复制，切回微信 Ctrl+V |
| 桌面 · 动图（GIF/APNG） | **写不进剪贴板** | ⚠️ 退化为下载后拖入，或从网页直接拖进聊天窗口 |
| 手机 · 任意格式 | `navigator.share({files})` | ✅ 直接分享到微信，动图也可以 |

**手机端反而是体验最好的一端。** 这也是选 Web 形态的重要依据。

UI 上必须诚实区分这两类，不能让用户点了 GIF 之后发现没反应。因此每条记录要存 `is_animated` 字段，前端据此决定走哪条路径。

> **待验证：** 从浏览器直接拖拽图片到微信窗口（Chrome 的 `DownloadURL` 机制）是否可行。如果可行，桌面端 GIF 的体验会好很多。

### 3.3 视觉模型用户可配，Embedding 归部署方

**决定：** 视觉模型由用户在设置页自行填写；Embedding 模型全站一份，仅管理员可改。两者都只要求接口兼容 OpenAI 规范。

**为什么两者待遇不同：** 视觉模型的产出是**文本**（描述、标签、OCR），跨模型天然可比，只要固定标签词表执行到位（见 3.6）。Embedding 的产出是**向量**，跨模型完全不可比 —— 而库是共享的，A 的查询要和 B 上传的图放在一起比。完整论证见 3.7。

| 配置组 | 字段 | 谁来配 |
|---|---|---|
| 视觉打标 · 主通道 | Base URL / API Key / Model | 用户（不填则用部署方默认） |
| 视觉打标 · 副通道（降级用，可留空） | Base URL / API Key / Model | 用户 |
| 向量 Embedding | Base URL / API Key / Model | **仅管理员，全站一份** |

接口约定固定为 OpenAI 兼容的 `/v1/chat/completions` 和 `/v1/embeddings`——这是事实标准，几乎所有供应商和中转服务都支持。

**视觉模型默认就用部署方的配置，用户设置页里这一组收进「高级选项」。** 旁边必须写明一句：你的打标结果会进入公共库。这是共享带来的新问题 —— 原来配了烂模型只有自己搜不准，现在会污染所有人的搜索结果，而打标质量恰恰是这个项目的命门（见第十一节）。因此还需要给管理员一个「对任意图片重新打标」的兜底入口（见 4.5）。

**成本模型基本不变。** 贵的是视觉打标，仍由上传者自己的 key 承担；Embedding 转由部署方承担，但那部分本来就可以忽略 —— 入库时每条一次、搜索时每次一次，量级在单张图打标成本的百分之一以下。原本为了保护 AI 预算而设的「每用户图片数配额」，仍然只需要限制存储容量即可。

**代价要认：** 接口抽象只能用最小公分母。各家的 Batch 折扣、`json_schema` 严格结构化输出、显式 prompt caching 用法都不一致，抽象层里都用不上。结构化输出退化为 `json_object` + 提示词里写明 schema + 健壮的解析兜底。

**为什么这笔交易划算：** 牺牲掉的特性主要用来省钱，而单张图的打标成本本就在 $0.001 以下的量级，省钱不是优先级。换供应商的自由度价值更高——尤其在 3.6 的内容问题上，这层抽象直接变成了解决方案。

**安全要求：** API Key（不论用户的还是部署方的）必须加密存储（AES-GCM，主密钥放环境变量），前端只回显后四位，任何接口都不得返回完整 key。

### 3.4 默认推荐配置（不是硬性绑定）

系统不绑定任何模型，但设置页会给出推荐值，也作为部署方的默认配置。

**视觉打标推荐：DeepSeek V4.1 Flash**（2026-09-10 发布，原生多模态，OpenAI 兼容）

**推荐理由不是价格，是中文语感。** 「阴阳怪气」「摆烂」「表面同意实际很无语」这类判断是整个产品的命门，国产模型在这上面大概率优于英文模型。

成本参考（官方定价，供用户估算自己的开销）：

| 项 | 价格 |
|---|---|
| 输入（缓存未命中） | $0.30 / MTok |
| 输入（缓存命中） | $0.006 / MTok |
| 输出 | $1.20 / MTok |
| 单张图片 | ≤ 384 tokens |
| 闲时 | 上述价格的一半 |

单张约 **$0.0007**，1000 张不到 1 美元，闲时再减半。

该模型的 prompt caching 是服务端按前缀自动命中的，不需要手动标记——把固定提示词和标签词表放在消息最前面，这部分几乎免费。这是少数没有被兼容层牺牲掉的省钱特性。

**Embedding 推荐：Qwen3-Embedding-4B（硅基流动托管）**，理由见 3.7。

用户完全可以把**视觉模型**换成别的——设置页的「测试连接」会告诉他们换的那个能不能用（见 3.9）。**Embedding 不开放给用户更换**，理由见 3.7。

### 3.5 动图处理：抽帧，而不是指望模型看懂动图

**问题不是格式支持，是模型只看得到一帧，而那一帧往往是错的。** 表情包动图的第一帧通常是铺垫——人物还没做表情，**文字往往要到后面几帧才出现**。用首帧打标等于丢掉全部关键信息。

**决定：** 动图永远不直接送给 AI，服务端统一归一化。

```
上传文件
  → magic bytes 探测真实格式（不信扩展名）
  ├─ 动图 → ffmpeg 抽全帧 → pHash 去重（去掉长静止段的重复帧）
  │         → 选最多 4 帧（偏向后段，包袱和文字通常在结尾）
  │         → 各自缩放为独立 PNG，一次请求发 4 张
  └─ 静图 → 长边缩到 512 的 PNG
  → AI 只会收到 PNG
```

**为什么是发多张而不是拼成 2×2 网格：** 多数模型对单图有 token 上限（如 DeepSeek 的 384 tokens），拼四格等于每帧只剩四分之一的分辨率预算，表情包里的小字会糊掉。发独立帧能让每帧都吃满分辨率，总成本仍可忽略。拼图方案作为兼容性兜底保留——供应商如果不支持多图输入，自动回退到拼图。

**这个设计在「模型用户可配」之后变得更重要。** 用户会填各种各样的模型，格式支持千差万别（DeepSeek 支持 JPEG/PNG/GIF/WebP，Grok 只支持 jpg/png）。但既然所有模型都只会收到 PNG，**格式兼容性问题被彻底消除**——用户不需要关心自己选的模型支不支持 GIF。

原图原样存 R2，展示和发送始终用原图，只有喂 AI 这一路做归一化。

### 3.6 敏感内容：双通道降级，不是二选一

个人表情包库里必然存在擦边内容。境内受监管的模型对这类内容大概率在 API 层就拦截——**这是合规问题，不是能力问题，调提示词绕不过去**。

**决定：** 利用 3.3 的双通道配置做失败降级，而不是前置分类器。主通道和副通道**都由用户自己填**，用户可以自行决定副通道用哪家。

```
主通道（用户配置）跑全部
  ↓ 被拒（HTTP 内容策略错误 / 返回非合法 JSON / 文本含拒绝措辞）
副通道（用户配置，可留空）自动重试
  ↓ 仍失败或未配置副通道
标记 tag_status = needs_manual，进待人工处理列表
```

**为什么用「拒绝后降级」而不是「前置 NSFW 分类器」：** 少一个模型、少一次推理，而且能顺带覆盖没预料到的拒绝类型（血腥、某些政治梗图一样会被拒）。

**即使两边都失败也不是全丢：** 缩略图和已有的 OCR 文字仍在，那张图依然能被文字搜到，只是没有语义描述。降级是分级的，不是二值的。

**配套约束：** 两个通道输出的标签词汇必须对齐（一个说「无语」一个说「speechless」的话标签检索就废了）。因此**固定标签词表从「好习惯」变成硬性要求**——提示词里给死一份中文标签清单，模型只能从里面挑。用户可配置模型之后这一条更关键，因为系统完全无法预知用户会填什么模型。

**边界：** 涉及未成年人的内容在所有供应商和法律层面都是硬禁的，不存在「换一家就能过」，这类应在入库前拦截。

**共享库让这个边界的分量变重了。** 原本擦边内容只有上传者自己看得到，现在**默认对所有被邀请的人可见**（见 3.0）。托管责任仍在部署方，但多了一层：你邀请的人会看到彼此传的所有东西。开放邀请前必须先想清楚这件事，它不是技术问题。

### 3.7 Embedding 必须全站统一：共享库的最大技术约束

**这是 3.0「库共享」带来的最大技术后果，必须单独讲。**

如果库是隔离的，不同用户用不同 embedding 模型完全没问题 —— 每个人只在自己的库里检索，跨用户的向量从不放在一起比较，「向量空间不兼容」根本不构成问题。

**但库是共享的，这个前提不成立了。** 用户 A 输入查询 → 用 A 的模型编码 → 和**全库**的向量做余弦比较，其中包括 B 用另一个模型编码的那些。不同模型的向量空间之间没有任何对应关系，1024 个维度各自代表什么完全不同。结果不是「差一点」，是**噪声** —— B 上传的图要么永远搜不到，要么随机冒出来。

**所以 Embedding 模型全站一份，由管理员配置，普通用户的设置页里没有这一组。** 真正的硬要求是「同一个模型、同一个版本」，维度一致只是顺带满足。

> 「每张图存 N 份向量、每个模型一份」这个方案不用考虑：新用户填个新模型就要全库重嵌一遍，成本和复杂度都不成立。

**维度仍然固定 1024**，任何模型的输出都归一化到 1024：

| 模型原生维度 | 处理 |
|---|---|
| > 1024 | 取前 1024 维 + **重新做 L2 归一化** |
| = 1024 | 直接使用 |
| < 1024 | **拒绝保存配置**，管理页标红提示 |

归一化这步很容易漏，漏了余弦相似度就不对了。

**为什么截断可行：** 支持 MRL（套娃表征）的模型——Qwen3-Embedding 全系、OpenAI text-embedding-3 全系等——截断基本无损，这是训练时就设计好的能力。不支持 MRL 的模型截断会明显掉质量，所以管理页必须明确提示优先选 MRL 模型。

优先走 OpenAI 的 `dimensions` 参数让服务端直接返回 1024 维；**若供应商不透传该参数，则客户端截断 + 重新归一化**。两条路由「测试连接」自动探测决定（见 3.9）。

**换 Embedding 模型 = 全站重算。** 但这件事的性质变了 —— 从「每个用户随时可能触发」变成「管理员偶尔做一次的运维操作」，频率低得多，UI 复杂度也随之下降：

- 管理页一个「重建索引」按钮 + 进度，不需要面向普通用户的确认弹窗
- 每条记录存 `embed_model`，用于判断哪些记录已过期
- 重算期间搜索自动降级为只用 OCR + 标签，不中断服务

代价不大：几千条重算只要几分钟、几毛钱。

**一个附带的技术红利。** 原方案的向量检索是 `HNSW + WHERE user_id = ?`，这是 pgvector 的经典痛点 —— 带过滤条件的近似搜索会掉召回率，要靠调 `ef_search` 或 iterative scan 补回来。库共享之后这个过滤条件消失了，HNSW 跑在它最舒服的状态。（软删的 `deleted_at is null` 是个轻量过滤，选择率接近 1，不构成同类问题。）

### 3.8 为什么推荐 4B 而不是 8B 或 0.6B

Embedding 归部署方统一配置（见 3.7），所以这是一个**全站做一次、影响所有人**的选择，比原来更需要有依据。Qwen3-Embedding 三档的原生维度是 0.6B=1024、4B=2560、8B=4096。

**为什么不是 8B：** 不是质量，是**搜索延迟**。每次搜索都要实时跑一次查询 embedding，8B 明显更慢，叠加 HyDE 的那次 LLM 调用会让搜索体感变差。导入时慢无所谓（异步），搜索时慢直接伤体验。4B 到 8B 的质量差距很小，这笔交易划算。

**为什么不是 0.6B：** 本项目语料只有几千条短描述，召回根本不难，难的是「可爱一点的滚」这种细微语义的区分度——这吃模型容量，不吃向量维度。0.6B 到 4B 是明显的一档差距。

**一个必须避免的误解：模型容量和输出维度是两个独立的旋钮。** 不要为了凑 1024 维去选 0.6B——4B 和 8B 通过 MRL 一样能输出 1024 维。

**instruct 是非对称的。** Qwen3-Embedding 是 instruction-aware 模型，正确用法是查询侧加前缀、文档侧不加：

```
查询侧：Instruct: {任务描述}\nQuery: 今天真的不想上班
文档侧：一只趴在桌上的猫，看起来非常疲惫……（原文，无前缀）
```

两边都加或都不加会损失几个点。注意这条只对 instruction-aware 模型成立，换成别的模型就不适用——因此这个行为应当跟随 Embedding 配置，而不是写死在代码里。

### 3.9 设置页必须提示什么

**这是本次设计的重点。** 设置页不能只是几个空输入框——用户填了不能用的模型却不知道为什么，是最糟糕的体验。约束必须写在输入框旁边，而不是藏在文档里。

共享库之后这一节分成两个页面：**视觉模型在用户设置页**（每人一份），**Embedding 在管理页**（全站一份，仅 admin 可见）。

#### 用户设置页 · 视觉模型区域的提示文案

```
接口要求
  · 需兼容 OpenAI /v1/chat/completions
  · 必须支持图片输入（多模态）。纯文本模型会报 unsupported content type
  · 必须能稳定输出 JSON。优先选支持 response_format: {"type":"json_object"}
    或 tool calling 的模型
  · 不需要关心 GIF / WebP 支持 —— 系统会统一转成 PNG 再发送

⚠️ 你的打标结果会进入公共库，所有人都会搜到
  · 不填就用部署方的默认配置，那是经过验证的，多数情况下不需要改
  · 换成质量更差的模型，影响的是所有人的搜索结果

推荐
  · DeepSeek V4.1 Flash —— 中文语感好，单张约 $0.0007
  · 副通道建议配一个内容策略更宽松的供应商，用于主通道拒绝时降级
```

#### 管理页 · Embedding 区域的提示文案

```
⚠️ 这是全站唯一一份 Embedding 配置，对所有用户生效

接口要求
  · 需兼容 OpenAI /v1/embeddings
  · 输出维度必须 ≥ 1024，系统会统一截断并重新归一化到 1024 维
  · 强烈建议选择支持 MRL（套娃表征）的模型，否则截断会明显降低检索质量
  · ⚠️ 更换模型会触发全站重新索引，期间搜索降级为 OCR + 标签

推荐
  · Qwen/Qwen3-Embedding-4B（硅基流动）—— 支持 MRL，中文强，延迟适中
```

#### 「测试连接」按钮——设置页最重要的控件

用户会填各种中转服务，实际行为经常与文档不符。**不要让用户手填维度、也不要假设任何能力，全部实测。**

点击后执行：

**视觉模型检测**（用户设置页）
1. 发送一张内置测试图 + 正式的打标提示词
2. 检查：能否接收图片 / 返回是否为合法 JSON / 标签是否落在固定词表内
3. 探测是否支持 `response_format: {"type":"json_object"}`，不支持则自动回退到纯提示词模式
4. 探测是否支持多图输入，不支持则动图自动回退到拼图模式（见 3.5）
5. **失败时把模型的原始返回原样展示出来**，让用户能判断是模型能力问题还是配置填错

**Embedding 检测**（管理页）
1. 发送一段测试文本
2. **自动探测实际输出维度**——以实测为准，不信文档、不让人手填
3. 探测 `dimensions` 参数是否生效，决定服务端降维还是客户端截断
4. 维度 < 1024 直接标红并**拒绝保存**
5. 若库里已有数据且模型与当前不同，保存前额外确认一次 —— 这会触发全站重建索引（见 3.7）

**测试不通过不允许保存配置。** 这一条能挡掉绝大部分「配好了但跑不起来」的情况，是整个可配置设计能不能落地的关键。

### 3.10 检索：三路混合 + RRF 融合

单一检索方式都有明确的失效场景，所以必须混合：

| 通路 | 擅长 | 失效场景 |
|---|---|---|
| OCR 全文 | 「你没事吧」这种精确记得图上文字的 | 无文字表情包 |
| 标签过滤 | 「猫 + 无语」这种结构化筛选 | 说不出标签的模糊意图 |
| 语义向量 | 「今天真的不想上班」这种描述意图的 | 精确文字匹配反而不如全文 |

**融合用 RRF（倒数排名融合），不用加权求和。** 向量相似度和全文检索分数量纲完全不同，加权的权重根本调不出来；RRF 只用排名不用分数，天然免疫这个问题。**Embedding 统一之后这条论证弱化了但没消失**——同一时刻全站用同一个模型，分数分布至少是一致的；但管理员换一次模型，相似度的绝对值分布就整体漂移一次，写死的加权阈值又得重调一轮。RRF 只看排名，换模型不受影响。

**查询侧改写（HyDE）：** 用户输入「今天真的不想上班」是一句短口语，而库里存的是「一只趴在桌上的猫，看起来非常疲惫……」这样的长描述。短句对长文的向量匹配效果一般。先用小模型把查询改写成一句同样风格的描述再检索，成本极低、收益明显。改写复用**搜索者本人**配置的视觉模型通道（纯文本调用）—— 改写产出是文本，再交给全站统一的 Embedding 编码，所以不存在跨模型不兼容的问题。

**中文全文检索的坑。** PostgreSQL 默认的 `to_tsvector` 不会分中文词，直接用等于没用。两个选择：装 `zhparser`/`pg_jieba` 扩展做真正的分词，或者用 `pg_trgm` 做子串匹配。**MVP 选后者**——OCR 精确搜索的本质就是子串匹配，`pg_trgm` 够用，而且不用在部署环境里折腾扩展。

## 四、功能清单

### 4.1 导入

不区分来源，统一走文件上传：

- 多选文件上传
- 拖拽文件夹（递归扫描）
- 剪贴板 Ctrl+V 粘贴
- ZIP 包解压导入
- 手机端从相册选择

**去重在调 AI 之前，且作用域是全局的。** 表情包库重复率极高，先去重能直接省掉相应比例的 AI 调用——用户自带 key 之后，这是在省用户自己的钱。共享库里还多一层意义：两个人传了同一张图，公共库里不该出现两条记录。具体分层和判断规则见 4.7。

导入是异步的，通过 SSE 向前端推送进度。上千张图的处理过程中，应用应当保持可用。

**未配置模型时的行为：** 部署方的默认视觉配置在正常情况下总是存在，所以这属于边缘场景。但若默认值也没设，导入仍然允许——图片正常入库、生成缩略图和哈希，但 `tag_status = pending`。等配置好之后一键批量补打标。不能因为没配模型就拒绝上传。

### 4.2 自动理解

**单次视觉调用产出全部结构化信息**，不做独立的 OCR 链路。

理由：本地 Tesseract 对表情包的艺术字体中文基本不可用，白搭一套基础设施；而多模态模型本来就能在同一次调用里顺带完成 OCR。

单次调用的产出：

| 字段 | 说明 |
|---|---|
| `ocr_text` | 图中文字 |
| `description` | 一句话语义描述，供 embedding 使用 |
| `emotions[]` | 情绪，从固定词表中选 |
| `scenes[]` | 适用聊天场景，从固定词表中选 |
| `tags[]` | 主体/角色/风格等，从固定词表中选 |

**固定词表是硬性要求**，理由见 3.6。开放生成会导致「无语 / 无奈 / 服了」三个同义标签互相割裂，标签检索直接失效。模型可配置之后，词表是唯一能保证不同模型输出可比的手段。

### 4.3 搜索

- 自然语言语义搜索（主要入口）
- OCR 文字精确搜索
- 标签筛选
- 三路结果 RRF 融合排序
- 按情绪 / 场景 / 标签 / 是否动图 / 收藏状态 / 上传者 浏览

### 4.5 管理

| 功能 | 谁可以 |
|---|---|
| 编辑 / 增删标签与描述 | **所有人** |
| 收藏 | 所有人（写自己的） |
| 删除（软删） | 上传者本人或 admin |
| `needs_manual` 待处理列表 | 自己的；admin 看全部 |
| 批量补打标 / 重新打标 | 自己上传的；admin 可对任意图执行 |

**编辑对全员开放，理由见 3.0** —— 标签在共享库里是公共品，谁发现标错了都顺手改掉对所有人都是净收益。防滥用靠记录 `edited_by` / `edited_at`，MVP 不做完整修改历史表，出问题再加。

**删除是软删（`deleted_at`），不是物理删除。** 理由：别人可能已经收藏了这张图，硬删会在别人的收藏夹里留下空洞。软删之后 `user_favorites` 不需要级联，误删也容易恢复。**所有读路径必须带 `deleted_at is null`** —— 这是软删唯一的代价，必须在统一的数据访问层里强制，不能靠每个 handler 自觉。R2 上的原图延迟清理（比如软删 30 天后由定时任务物理删除）。

**admin 的重新打标入口是 3.3 的兜底。** 用户配了烂视觉模型污染公共库时，admin 需要能选中那批图、用部署方的默认配置重跑一遍。

### 4.7 去重

去重分两个不同的层，各自解决不同的问题，不要混为一谈。**库共享之后，两层的作用域都从「每用户」提到了「全局」** —— 两个人传了同一张图，公共库里不该出现两条记录：搜索结果里重复出现，还白花一次打标钱。

**第一层：内容级精确去重（SHA-256）**

对上传的原始文件字节计算 SHA-256，和库里已有记录比对。两个文件完全一样才会命中——哪怕 1 个像素不同、EXIF 头不同，都不命中。用来挡「同一个文件上传两次」。实现简单，**误判率为零**。

**第二层：感知级近似去重（pHash + Hamming 距离）**

pHash（感知哈希）把图片压成一个 64 位整数，代表其视觉指纹。重新截图、换水印、轻度重压缩后的同一张图，pHash 相差只有几个 bit。用 Hamming 距离（汉明距离，即两个整数 XOR 后计 1 的位数）度量相似度，阈值通常设在 8–10 bit 以内认为是近似重复。

**这一层会误判，而且没法靠调阈值消除。** 同一个模板换了字的两张表情包，Hamming 距离可能很近，但它们是两张不同的图，而且往往是用法完全不同的两张。所以近似命中**不能自动跳过，必须让人来判断**。

查询方案：全库直接扫 phash 做 XOR popcount 即可，不需要 BK-tree 或专用索引。PostgreSQL 的 `bit_count(a # b)`（`#` 是 XOR）扫几万行仍在毫秒级，到十万量级再考虑专用结构。

**两层的强制性必须不同**

| 层 | DB 约束 | 用户能否推翻 |
|---|---|---|
| SHA-256 | `unique (content_hash)` 硬约束 | 不能 —— 字节完全相同，没有可判断的东西 |
| pHash | **普通 btree 索引，不是唯一约束** | 能 —— 由业务层询问用户 |

> ⚠️ **这里改掉了原设计，且必须改。** 原方案保留 `unique (user_id, phash)` 当「第二道防线，几乎零成本」。但它会**硬性挡掉 Hamming 距离为 0 的情况** —— 而那恰恰可能是一张重新编码过、用户看了之后决定要保留的不同图。既然判断权交给了人，DB 就不能先斩后奏，这个唯一约束必须降级为普通索引。它现在的成本不是零，是「让用户判断」这个功能根本做不了。

**去重在导入流程里的位置**

```
上传文件
  → SHA-256 查库 → 精确命中 → 静默跳过，只计入摘要
  → pHash 计算 → Hamming 全库扫 → 近似命中 → 进「待确认」队列，不阻塞导入
  → 两关都过 → 写入 memes 表
  → pHash 去重帧（动图）→ 抽帧 → 送 AI 打标
```

注意近似命中的图**先不打标** —— 等用户确认「仍然导入」之后再进打标队列，否则被判为重复的那些白花钱。

**UI 行为：统一走「待确认」队列，不弹中途确认框**

上千张图导入时每张都弹窗，体验会崩掉。所以近似命中**不阻塞导入流程**，而是攒进一个「待确认」队列，导入结束后一起处理：

- 左右并排显示「你传的这张」和「库里已有的那张」，标出 Hamming 距离、分辨率、文件大小、原上传者
- 三个动作：**跳过**（用库里那张）/ **仍然导入**（我认为是不同的图）/ **稍后再说**（留在队列里）
- **队列里只有 1 条时，它看起来就是个即时弹窗** —— 同一套代码，只是单条时换个呈现形式。单张上传的场景因此天然得到即时反馈

精确重复不进这个队列，直接静默跳过。导入摘要报三个数：「已入库 N 张，跳过 X 张完全相同的文件，Y 张待你确认」。

**主动查重（管理功能）**

对于导入前就存在的历史库，提供「扫描重复」入口，找出 Hamming 距离在阈值内的图片对，按相似度分组展示，让用户逐组决定保留哪张。分组展示时优先展示分辨率更高或尺寸更大的那张。这个功能异步跑，结果存一张临时表，不直接删除任何东西，用户确认后才删。**受 4.5 的权限约束：普通用户在这里只能删自己上传的，admin 不限。**

**注意：动图抽帧里也用到 pHash，但那是另一回事。**

在 3.5 的抽帧流程里，pHash 用于去掉动图内部的重复帧（长静止段）——那是帧间去重，发生在文件进入队列之后、选取代表帧送 AI 之前，作用域是同一个文件的帧集合。这里讲的去重是跨文件的入库去重，二者 pHash 的计算对象不同，不要混用。

### 4.8 账号与权限

- 邀请码注册
- 两种角色：`admin` / `member`
- httpOnly cookie 会话（前后端同域，避开跨域 cookie 的麻烦）
- **每用户存储配额**（AI 成本已转嫁给用户，这里只需限制磁盘占用）

**权限矩阵**

| 操作 | 谁可以 |
|---|---|
| 搜索 / 浏览 / 使用 | 所有登录用户，**不做任何归属过滤** |
| 收藏 | 所有人（写自己的 `user_favorites`） |
| 编辑描述与标签 | **所有人**（见 4.5） |
| 删除（软删） | 上传者本人或 admin |
| 重新打标 | 上传者本人；admin 不限 |
| 配置视觉模型 | 所有人（改自己的） |
| 配置 Embedding / 重建索引 / 管理用户 | 仅 admin |

> ⚠️ **风险的位置和隔离库时完全不同，不要照搬旧直觉。**
>
> 隔离库的头号风险在**读路径** —— 搜索接口漏一个 `where user_id = ?` 就是全库泄露。**共享库里这个风险不存在了**：全库可读就是设计本身，没有可泄露的边界。
>
> 风险整个挪到了**写路径**：删除接口漏一个归属检查，等于任何人都能删掉别人的贡献。性质比泄露轻（破坏 vs 泄露），但要求不变 —— 所有写操作必须走统一的 `assertCanMutate(meme, actor)`，不允许散落在各个 handler 里手写判断。
>
> 另外软删引入了一条**新的**读路径约束：所有查询必须带 `deleted_at is null`。它和旧的 `user_id` 过滤一样容易漏，同样必须在数据访问层里强制，不能靠自觉。
>
> API Key 绝不能出现在任何返回给前端的响应里 —— 这一条不受共享影响，照旧。

| 不做 | 原因 |

| Batch API 五折 | 兼容层用不了，且成本基数本就可忽略 |
| Reranker 精排 | 架构留位，MVP 后再加（见第十节） |
| 合集 / 统计页 / 社交 / 公开市场 / 好友分享 | 与核心闭环无关 |
| 独立向量数据库 | pgvector 在这个量级绰绰有余 |

```
前端    Vite + React + TypeScript + React Router   (SPA)
后端    Hono (Node)，同域托管前端 dist + /api
数据库  PostgreSQL + pgvector + pg_trgm

存储    Cloudflare R2（S3 兼容），前端预签名 URL 直传，不过后端
图像    ffmpeg（动图抽帧）+ sharp（缩放/格式转换）+ pHash（去重）
AI      任意 OpenAI 兼容供应商
        视觉：用户自行配置（默认推荐 DeepSeek V4.1 Flash）
        向量：全站一份，仅 admin 可配（默认推荐 Qwen3-Embedding-4B）
部署    Docker Compose，单机可与其他项目共存（见第八节）
```

后端选 Hono：轻量、类型友好、部署不挑环境，与前端同一套 TypeScript。

**导入队列直接用 Postgres，不引入 Redis。** 任务量是「上千张图排队打标」这个级别，`FOR UPDATE SKIP LOCKED` 完全够用。少一个服务就少一份内存占用、少一套前缀要管、少一个会和同机其他项目撞车的东西——这一点在第八节会反复出现。

**AI 调用必须封装成两个接口**，实现里只允许出现 OpenAI 兼容的请求形状，不允许任何供应商特有的分支：

```
VisionTagger.tag(images: PNG[], prompt) → TagResult
Embedder.embed(texts: string[])         → Float32Array[1024][]
```

供应商差异（是否支持 json_object、是否支持多图、是否透传 dimensions）全部由「测试连接」探测后存进配置 —— 视觉的存进 `user_ai_configs`，向量的存进 `embed_config` —— 运行时读配置决定走哪条路径。

**还有一个必须统一的访问层。** 所有涉及 `memes` 表的读写都要走它，负责两件事：读路径强制 `deleted_at is null`，写路径强制 `assertCanMutate(meme, actor)`。理由见 4.8，这是共享化之后风险最集中的地方。

## 七、数据结构

```sql
-- 用户与邀请
users(id, created_at, role, storage_quota_bytes)   -- role: 'admin' | 'member'
invite_codes(code, created_by, used_by, used_at, expires_at)

-- 每用户的视觉模型配置（Embedding 不在这里，见 3.7）
user_ai_configs(
  user_id                 uuid primary key,

  -- 视觉主通道
  vision_base_url         text,
  vision_api_key_enc      bytea,        -- AES-GCM 加密，主密钥在环境变量
  vision_model            text,

  -- 视觉副通道（降级用，可空）
  vision_fb_base_url      text,
  vision_fb_api_key_enc   bytea,
  vision_fb_model         text,

  -- 「测试连接」探测结果，不由用户填写
  vision_json_mode_works  boolean,      -- 是否支持 response_format
  vision_multi_image      boolean,      -- 是否支持多图输入
  verified_at             timestamptz
);

-- 全站唯一一份 Embedding 配置，仅 admin 可改（见 3.7）
embed_config(
  id                      int primary key default 1 check (id = 1),   -- 单行表
  base_url                text,
  api_key_enc             bytea,
  model                   text,
  native_dim              int,          -- 实测输出维度
  dim_param_works         boolean,      -- dimensions 参数是否生效
  verified_at             timestamptz
);

-- 表情包主表（共享库，检索时不按归属过滤）
memes(
  id            uuid primary key,
  uploader_id   uuid not null,        -- 上传者，不是「拥有者」；只用于写权限判断

  -- 存储与去重
  storage_key   text not null,        -- R2 对象键
  content_hash  text not null,        -- SHA-256 hex，精确去重（硬约束）
  phash         bigint not null,      -- 感知哈希，近似去重（刻意非唯一，见 4.7）
  mime          text,
  width, height, size_bytes,
  is_animated   boolean,              -- 前端复制/下载分流依据

  -- AI 产出
  ocr_text      text,
  description   text,
  emotions      text[],
  scenes        text[],
  tags          text[],
  search_text   text,                 -- 上述字段拼接，供 embedding 与全文检索
  embedding     vector(1024),         -- 全站固定 1024 维，见 3.7

  -- 溯源
  vision_model  text,
  embed_model   text,                 -- 换模型后据此找出待重算的记录
  tag_status    text,                 -- pending / ok / refused / needs_manual
  edited_by     uuid,                 -- 最后编辑人（编辑对全员开放，见 4.5）
  edited_at     timestamptz,

  deleted_at    timestamptz,          -- 软删，见 4.5；所有读路径必须带 is null
  created_at    timestamptz
);

-- 收藏是「人和图的关系」，不是图的属性
user_favorites(
  user_id       uuid not null,
  meme_id       uuid not null,
  created_at    timestamptz,
  primary key (user_id, meme_id)
);

-- 索引
unique (content_hash)                            -- 全局精确去重，硬约束
btree  (phash)                                   -- 近似去重全扫用，刻意不做唯一约束
hnsw   (embedding vector_cosine_ops)             -- 语义检索，无归属过滤，见 3.7
gin    (tags)                                    -- 标签筛选
gin    (search_text gin_trgm_ops)                -- OCR 子串匹配
btree  (uploader_id)                             -- 「只看我上传的」
btree  (tag_status)                              -- 待处理 / 过期记录扫描
```

三个容易踩的点：

- **`memes` 表里没有 `favorite` 字段。** 收藏是每人独立的，留在主表上会导致 A 收藏了 B 也看到收藏态。这是共享化时最容易漏的一处 schema 改动。
- **`memes` 表里也没有 `embed_dim`。** 维度是全局常量 1024，不是每条记录的属性。而 `embed_model` 保留，用于管理员换模型后找出待重算的记录。
- **`phash` 刻意不是唯一约束。** 原因见 4.7 —— 它会挡掉用户想保留的近似图，把判断权从人手里抢走。

**表名不加前缀。** 本项目独占一个 database（见 8.3），表名前缀是多余的噪音。需要加前缀的是 database 名、role 名、以及容器/卷/网络/端口/对象键——那些才是真正会和同机其他项目撞车的东西。

## 八、部署

目标环境是**一台机器上同时跑多个项目**。这个前提决定了本节的绝大部分设计——不是为了跑起来，是为了**跑起来之后不影响别人、也不被别人影响**。

### 8.1 命名冲突清单

单机多项目的冲突点远不止数据库名。按严重程度排列：

| 层 | Docker 默认值 | 撞车后果 |
|---|---|---|
| **数据卷** | `<目录名>_pgdata` | 🔴 **两个项目的 Postgres 挂同一个卷，数据直接损坏** |
| **网络** | `<目录名>_default` | 🔴 跨项目容器能互相连通，是安全问题 |
| 宿主机端口 | 5432 / 3000 | 🟠 后启动的那个起不来 |
| 容器名 | `<目录名>-<服务>-1` | 🟠 冲突时创建失败 |
| PG database / role | `postgres` / `postgres` | 🟠 共用实例时互相覆盖 |
| R2 对象键 | 无前缀 | 🟠 共用 bucket 时对象互相覆盖 |
| 镜像 tag | `<目录名>-app:latest` | 🟡 误推误拉 |

**最危险的是卷。** 端口冲突会立刻报错，很好发现；卷冲突是静默的——两个 Postgres 实例挂上同一个数据目录，数据库会被写坏，而且往往过一阵才发现。

### 8.2 单一变量派生全部命名

不要在十几个地方各写各的前缀，**只维护一个变量，其余全部派生**。

`.env`：

```bash
APP_SLUG=mememio          # ← 全项目唯一需要改的命名变量
DB_PASSWORD=<随机生成>
```

`compose.yaml`：

```yaml
name: ${APP_SLUG}          # ← 主防线：容器/卷/网络自动带此前缀

services:
  app:
    build: .
    container_name: ${APP_SLUG}-app
    restart: unless-stopped
    env_file: .env
    depends_on:
      db: { condition: service_healthy }
    networks: [internal, proxy]
    # 注意：不映射任何宿主机端口，见 8.4

  db:
    image: pgvector/pgvector:pg17
    container_name: ${APP_SLUG}-db
    restart: unless-stopped
    environment:
      POSTGRES_DB:       ${APP_SLUG}
      POSTGRES_USER:     ${APP_SLUG}
      POSTGRES_PASSWORD: ${DB_PASSWORD}
    volumes:
      - pgdata:/var/lib/postgresql/data
    healthcheck:
      test: ["CMD-SHELL", "pg_isready -U ${APP_SLUG}"]
      interval: 5s
      retries: 10
    networks: [internal]
    # 同样不映射端口，数据库只在内部网络可见

volumes:
  pgdata:
    name: ${APP_SLUG}_pgdata      # 显式命名，不依赖默认推导

networks:
  internal:
    name: ${APP_SLUG}-internal
  proxy:
    external: true
    name: shared-proxy            # 全机共享的反代网络，见 8.4
```

**顶层 `name:` 是主防线**——设了它之后，Compose 会自动给卷、网络、容器加上这个前缀，不再依赖「目录名」这个极易撞车的默认值。下面的 `container_name` 和卷的 `name:` 是第二层保险，同时让 `docker ps` 的输出一眼能看出归属。

> ⚠️ Compose 的顶层 `volumes:` / `networks:` 的 **key 不支持变量插值**，只有块内的 `name:` 字段支持。所以是 `pgdata: { name: ${APP_SLUG}_pgdata }`，不是 `${APP_SLUG}_pgdata:`。

### 8.3 数据库：独占实例，不共用

两种做法：

| 方案 | 说明 | 取舍 |
|---|---|---|
| **A. 每个项目自带 db 容器**（推荐） | 本项目一个 Postgres 容器 | 隔离彻底；代价是每实例约 100MB 内存 |
| B. 全机共用一个 Postgres | 各项目独立 database + 独立 role | 省内存；但**扩展版本互相牵制** |

**推荐 A**，理由不是内存而是扩展：本项目依赖 `pgvector` 和 `pg_trgm`，共用实例时升级 pgvector 会同时影响同机所有项目，牵一发动全身。独占一个容器，版本完全自己说了算。

若确实要走 B，则必须做到：独立 database（`mememio`）、独立 role（`mememio`）、`REVOKE` 掉该 role 对其他 database 的访问。**不要用共用 database + 表前缀的方式做隔离**——权限边界为零，一次写错 SQL 就能读到别的项目的数据。

### 8.4 端口：一个都不映射

单机多项目下，手工分配宿主机端口是个治标不治本的办法，项目一多必然出错。

**做法：所有项目都不映射宿主端口，统一走一个反向代理容器。**

```
              ┌─────────────────────────────┐
  :80 :443 ── │  Caddy / nginx（唯一暴露端口）│
              └──────────────┬──────────────┘
                             │  shared-proxy 网络
            ┌────────────────┼────────────────┐
            ▼                ▼                ▼
     mememio-app      其他项目-app       又一个项目-app
            │
            │  mememio-internal 网络（外部不可达）
            ▼
       mememio-db
```

反代通过容器名访问（`http://mememio-app:3000`），**端口冲突这个问题从根上消失了**。数据库只挂在 `internal` 网络上，连反代都碰不到它。

`shared-proxy` 是一个外部网络，全机所有项目共用，需先手工创建一次：

```bash
docker network create shared-proxy
```

### 8.5 镜像构建

三阶段：前端产物 → 后端产物 → 运行镜像。

```dockerfile
FROM node:22-bookworm-slim AS web
WORKDIR /w
COPY web/package*.json ./
RUN npm ci
COPY web/ ./
RUN npm run build

FROM node:22-bookworm-slim AS api
WORKDIR /a
COPY api/package*.json ./
RUN npm ci --omit=dev
COPY api/ ./
RUN npm run build

FROM node:22-bookworm-slim
RUN apt-get update \
 && apt-get install -y --no-install-recommends ffmpeg \
 && rm -rf /var/lib/apt/lists/*
WORKDIR /app
COPY --from=api /a/node_modules ./node_modules
COPY --from=api /a/dist       ./dist
COPY --from=web /w/dist       ./public     # SPA 产物，由 Hono 同域托管
CMD ["node", "dist/server.js"]
```

**两个坑：**

- **用 `bookworm-slim`，不要用 Alpine。** `sharp` 的预编译二进制在 musl 上经常出问题，装 ffmpeg 也更麻烦。glibc 基础镜像大一些，但省掉的调试时间远超那点体积。
- **ffmpeg 会让镜像涨约 100MB+**，这是 3.5 抽帧方案的必要成本，可接受。不要为了瘦身换成裁剪版 ffmpeg，动图格式的覆盖面会出问题。

### 8.6 环境变量

```bash
# 命名（唯一需要改的）
APP_SLUG=mememio

# 数据库（主机名就是容器名，走内部网络）
DB_PASSWORD=<随机>
DATABASE_URL=postgres://${APP_SLUG}:${DB_PASSWORD}@${APP_SLUG}-db:5432/${APP_SLUG}

# 密钥
SESSION_SECRET=<随机>
CONFIG_ENC_KEY=<随机 32 字节>     # 加密用户 API Key 的主密钥，见 3.3

# 对象存储
R2_ACCOUNT_ID / R2_ACCESS_KEY_ID / R2_SECRET_ACCESS_KEY
R2_BUCKET=<bucket>
R2_KEY_PREFIX=${APP_SLUG}/        # ← 共用 bucket 时必须，否则对象互相覆盖

# 部署方提供的默认模型配置（用户未配置时使用，见 3.3）
DEFAULT_VISION_BASE_URL / DEFAULT_VISION_API_KEY / DEFAULT_VISION_MODEL
DEFAULT_EMBED_BASE_URL  / DEFAULT_EMBED_API_KEY  / DEFAULT_EMBED_MODEL
```

> 🔴 **`CONFIG_ENC_KEY` 丢失 = 所有用户配置的 API Key 全部永久解不开。** 它不在数据库备份里，必须单独离线备份。这是本项目唯一一个「丢了就没法恢复」的东西。

### 8.7 备份与迁移

- **数据库**：`pg_dump` 定时导出，落到 R2 或宿主机另一块盘。注意 `pg_dump` 会带上 `vector` 类型列，恢复端必须先装好 pgvector 扩展。
- **`CONFIG_ENC_KEY`**：单独离线保存，见上。
- **图片**：已在 R2，建议开 bucket 版本控制。
- **Schema 迁移**：用 `drizzle-kit` 一类工具，走**独立的 migrate 命令**，不要放在容器启动流程里自动执行——将来要是跑多副本，会出现并发迁移。

### 8.8 落地检查清单

新机器部署或者新加一个同机项目时，逐条核对：

- [ ] `.env` 里 `APP_SLUG` 已改成本项目专属值，且与同机其他项目不重复
- [ ] `docker volume ls` 中本项目的卷带 `APP_SLUG` 前缀，且不与他人同名
- [ ] `docker network ls` 中内部网络带前缀；`shared-proxy` 已创建
- [ ] compose 里**没有任何 `ports:` 映射**（db 尤其不能暴露）
- [ ] `R2_KEY_PREFIX` 已设置（若与其他项目共用 bucket）
- [ ] `CONFIG_ENC_KEY` 已离线备份到 Docker 和数据库之外的地方
- [ ] 反代已配置指向 `${APP_SLUG}-app`

## 十一、核心判断

这个项目的技术难度不在存储，甚至不在检索——**在打标质量**。

向量检索、混合排序、pgvector 这些都是成熟方案，照着做就能跑通。真正决定「搜得准不准」的唯一变量是：**AI 有没有真的理解这张图想表达什么**。

模型改为用户可配置之后，这个判断没有变，但多了一层：**系统不再能假设模型的任何能力**。所有差异必须探测、所有输出必须校验、所有约束必须在界面上讲清楚。这也是为什么 3.9 的「测试连接」不是一个可选的锦上添花功能，而是整个可配置设计的地基。

**库改为共享之后，又多了一层：打标质量不再是私事。** 一个人配了烂视觉模型，污染的是所有人的搜索结果 —— 而上面这张图里排第一的那项，权重因此又高了一档。这也是为什么视觉模型默认就用部署方配置、用户要改得先翻开「高级选项」，以及为什么 admin 必须有「对任意图片重新打标」这个兜底。

注意力分配：

```
打标提示词与标签词表设计   ████████████  最重要
模型配置的探测与提示       ████████      可配置设计的地基
发送环节的体验            ██████        差异化所在
检索与排序                ███           成熟方案
存储与基础设施            █             不值得花时间
```

一句话：**这不是一个图片管理系统，是一个语义索引系统，图片只是它的载荷。**
