# 检索与筛选合流：`q` 进 `GET /memes`，检索可翻页

**状态**：`done`（2026-09-26 联合验收通过，验收依据见 §11）。SPEC §8.1 四步全部走完：SPEC 已改（§1.3、§6.3、§2.2 与 §9.29 四处同批）、本任务已开、两端同日确认后一起转 `accepted`、两端实现完成后经联合验收。
**性质**：跨端。

**需求来源**：2026-09-26 产品负责人提出——「搜索和标签筛选结合，并且搜索可以无限滚动翻页」，并明确**允许改契约、允许产品形态变化**。同一天完成四处裁定（§3）。

## 1. 为什么要做

两句话：

1. **搜索结果不能再筛，浏览结果不能按语义搜。** 搜出「今天真的不想上班」那一屏之后想再收窄到「猫」，现在只能换一种筛法——去浏览页按标签筛**全库**，等于重新找一遍；反过来在浏览页筛着筛着想说一句人话，没有入口。
2. **一次搜索是一个快照，翻不动。** 只有前 50 条、没有下一页。而「搜索不分页」是一条**既有立场**，写在 [SPEC §1.3](../../spec/01-http.md) 与 [`api/agents/rules/retrieval.md` §6](../../api/agents/rules/retrieval.md)，理由是「用户只看前几个结果，翻页没有意义」。产品负责人 2026-09-26 明确推翻——推翻记录见 [SPEC §9.29](../../spec/09-decisions.md)。

**这两半是一件事，不是两件。** 能筛的列表能翻页、能搜的列表不能翻，是站不住的；而两者要落在同一个 URL 上，「先筛再搜」和「先搜再筛」才是同一串参数。

## 2. 已查明的事实

每条都是 2026-09-26 读代码与契约得到的。**没有一条是浏览器实测**，验收项的实测责任在 §9。

- **融合池本来就比给出去的多。** `services/search.ts:141` 的 `fuseRankings(paths, effectiveLimit)` 融合的是三路候选的**全集**，只在最后按 `effectiveLimit` 截断；三路各取 `PATH_LIMIT = 50`（`data/search.ts:24`），所以池子 ≤150 条，而 `MAX_SEARCH_LIMIT = 100`（`services/search.ts:30`）。**「搜索翻不动」在 100 → 150 这一段上的代价是一个常量**——这条是裁定 2 的关键背景。
- **`HNSW_EF_SEARCH = PATH_LIMIT * 2` 那个 2:1 余量是按「一个排除词」校准的**：`data/search.ts` 的注释记着实测数字（默认 40 → 39 条，`= 50` → 49 条，`= 100` → 50 条）。挂上七个维度的标签过滤之后会归零，不是掉一点——数字与结论见 §5 第 3 条。
- **三路的 `ORDER BY` 缺最后一级 tiebreaker**：`data/search.ts:198` 的 trgm 路只有 `trgmScore desc, created_at desc`，向量路只有 `<=>`（只有标签路带了 `desc(id)`）。同分同秒时顺序不稳定，**翻页接缝会重复或漏**，做快照之前要补上 `id`。
- **两条路径现在完全独立。** `api/src/routes/search.ts:10-12` 的注释逐字写着：「与浏览（§6.3.2）是两条独立路径：搜索不分页、不带筛选条件、结果按 RRF 融合分排序。**别把 `cursor` 加进来——融合分不是稳定可续的游标，分页会把 RRF 的排序切坏。**」
- **`/search` 的消费者只有一个。** 全仓打这个端点的是 `web/src/lib/api.ts:361` 的 `fetchSearch`（首页那条路），加 `api/tests/read-path-auth.test.ts` 的两条。同域同时部署、不做版本并存（[SPEC §8.3](../../spec/08-collaboration.md)），所以它没有第二方在用。
- **游标不进 URL。** 浏览页的 `cursor` 存在 `cursorRef` 里（`web/src/features/browse/use-browse-list.ts:55`），页面地址不反映翻到第几屏。所以游标变胖、换形态，界面上看不见。
- **游标坏掉是静默从头。** `api/src/data/memes.ts:806-810`，`decodeCursor` 解析失败即忽略游标、返回第一页；约定写在同文件 `:734`、`:742` 的注释里（「解不出来就当没传」，引用 SPEC §1.3），并有测试锁住：`api/tests/read-path-auth.test.ts:192` 断言坏游标得 **200 + 第一页**。错误码表（[SPEC §2.2](../../spec/02-errors.md)）里没有游标类错误。
- **前端也是两套。** `use-search.ts` 管检索态与键盘路径；`use-browse-filters.ts` 加 `use-browse-list.ts` 管筛选与游标分页。两套失败重试、两套防竞态、两套游标作废逻辑。
- **两边写 URL 的历史策略相反**：浏览页的四类写操作全部 `replace`（筛选是「把这一屏看得更细」，不占历史）；搜索词的 `commit` 是 `push`（可分享、可后退）。
- **卡片是同一个组件，动作槽不是。** `web/src/components/MemeCard.tsx` 由页面通过 `actions` prop 给「⋯」入口：浏览页给 `MemeActions`，搜索页**不给**，改为在图片下方渲染一枚全宽按钮（`SearchResults.tsx:224-233`，文案随静图「复制」/ 动图「下载」变）。`MemeActions` 自带 `detectSendPath` 与 `usePrefetchShare`，分流逻辑不依赖搜索页那一份。
- **全屏阅览器没有可见的发送入口**：只有 `Ctrl+C`（`LightboxViewer.tsx`），工具栏是 YARL 自带的缩放/关闭；界面上一个字都没提这个快捷键。
- **既有端规则明确禁止合并**：[`web/agents/rules/state-navigation.md` §6](../../web/agents/rules/state-navigation.md)「不要把它们合成一个『万能搜索框』」，[`web/agents/rules/http.md:76`](../../web/agents/rules/http.md) 也写着搜索不分页。两条都是端规则，低于 SPEC，裁定通过后一并重写。

## 3. 裁定结果（2026-09-26，产品负责人）

四处，全部已定。**未采用的选项保留在原位**，因为「为什么不选它」比结论更容易被忘掉。

### 裁定 1 · 端点形态 → **A：`GET /memes` 吸收 `q`**

`/memes` 成为唯一列表端点，按有没有 `q` 分派召回与排序；`/search` 保留为**冻结的兼容入口**（只认 `q` 与 `limit`，其余参数 `VALIDATION_FAILED`，不分页），**同一个实现，不再演进**——[SPEC §6.3.3](../../spec/06-endpoints.md)。

**为什么不选 B**（`/search` 吸收筛选与游标，两端点并存）：同一个 URL 上两套游标语义、两个列表 hook 常驻一页，「先筛再搜」与「先搜再筛」是同一串参数却必须二选一——正是 `state-navigation.md` §6 警告的形态。B 的代价全在客户端，A 的代价是一段契约文字。

**为什么不删 `/search`**：首页那条路走的就是它，而首页的去向未定（裁定 3）。删了就得同时改首页，与裁定 3 冲突。留着的形式是「薄转发 + 参数白名单」而不是「纯别名」——纯别名会让 `/search?tags=猫` 悄悄变成浏览，属于本项目最忌讳的「客户端看不出错的错误结果」；参数白名单同时对齐 [SPEC §0.4](../../spec/00-overview.md)「请求未知字段返回 `VALIDATION_FAILED`」。

### 裁定 2 · 分页 → **真无限：服务端快照 + 翻倍预取**

**不用把融合池一次性给完**（那是下面「未采用」里的 D），要做成真能一直往下滚：

- 首屏算好这一批（三路候选、RRF 融合），把**三路各自的有序候选名单**连同**冻结的 HyDE 改写文本与查询向量**存进快照。
- 翻页 = 从融合结果里取下一段，**不重跑三路、不调任何外部 AI**。
- 滚到当前候选见底时，**预取深度翻倍**，重扫三路补齐。首屏成本与今天一致，只有真的往下滚的人才付钱。
- 排序在整个会话内稳定，**中途上传的新图不出现在这次检索的后续页里**——那就是快照的定义。

**为什么冻结 HyDE 是必须的，不是优化**：今天每次搜索是一次 LLM 改写 + 一次查询 embedding。若每页重算，改写逐次不同 → 召回池变化 → 翻页重复或漏；而且滚一屏就是一次 LLM 调用。快照把改写和查询向量钉住，这两个问题一起消失。

**为什么不是 keyset 重算**（未采用项 B）：融合分不是稳定可续的键，数据一变排名就移动，页间会重复或漏。

**深度与代价**：契约不设深度上限，但每次翻倍都要按新深度重扫三路，`ef_search` 跟着涨——**这是这条路的结构，不是方案选错**。另外深到几百条之后的融合结果每条基本只被一路的尾部召回，质量会很低。

**过期是一条明确契约**：复用 `VALIDATION_FAILED`（[SPEC §2.2](../../spec/02-errors.md)），**不新增错误码**——客户端对「游标坏了」和「快照过期了」的动作是同一个（丢弃游标、回第一页并说明原因），多一个码只是多一个分支。

### 裁定 3 · 首页 → **本轮不动**

首页代码一行不动，它继续按今天的形态工作、继续走 `/search`。产品负责人给的方向是「重新设计成**像浏览器首页一样**」（搜索框当入口、不再自己渲染结果），**那是另一条任务**，本任务不为它预留实现、也不改它的行为。

### 裁定 4 · 发送入口与卡片动作槽 → **三面齐全，一个动作只出现一处**

这一条同时是[页面地图](../../joint-tasks/2026-09-25-web-page-map.md)的原裁定 1（发送入口准入）与裁定 2（管理动作准入），**在这里裁掉了**，那份任务相应减两条。

| 面 | 发送 | 管理（编辑 / 删除 / 收藏） |
|---|---|---|
| 合并后的列表卡片（搜索与浏览共用） | `⋯` 菜单里那一项 | `⋯` 菜单 |
| 全屏阅览器 | **新增一枚可见按钮**，并在界面上提一句 `Ctrl+C` | 无 |

- **搜索卡片图片下方那枚全宽按钮撤掉**（`SearchResults.tsx:224-233`，连 `sendLabel` 与 `usePrefetchShare`）。它撤掉之后，「发送」在卡片上只剩菜单里一个入口，不会出现两个。
- 代价记一笔：搜索流里「发出去」从 1 击变 2 击。补回来的是阅览器上那枚可见按钮——**这是这次一并改阅览器的理由**，不是顺手加的。

## 4. 契约形态

**契约正文在 [SPEC §6.3](../../spec/06-endpoints.md)，本节只写执行者要先看懂的那几条。**

```
GET /memes?q=今天真的不想上班&emotions=无语&tags=猫&isAnimated=true&cursor=…&limit=40
```

- **先过滤后召回**：七个词表维度、`isAnimated`、`favorited`、`uploader`、`tagStatus` 在三路取 top-N **之前**生效。放到融合之后滤 = 「我明明筛了，结果少了一大截」。
- **响应形状恒定**：无 `q` 时也给 `nextCursor` / `degraded: false` / `rewritten: null` / `matchedBy: []`。不按模式变字段——Hono RPC 的类型是两端唯一的同步手段，两种形状会让每个消费点都要分支。
- **`q` 为空字符串走「无 `q` 分支」**，不报错（前端清空搜索框是常规操作）；`/search` 那边相反，缺 `q` 仍报错（它的语义是「一次检索」）。**两条相反是故意的。**
- **`q` 与 `random=true` 互斥**，返回 `VALIDATION_FAILED`——理由同现有的 `random` + `cursor`：忽略哪一个都是客户端看不出错的错误结果。
- **`limit` 默认 40**（原搜索默认是 50，合流后 `/memes` 统一到 [SPEC §1.3](../../spec/01-http.md) 的列表默认值）。
- **但 `/search` 的默认值冻结在 50，两处不同是有意的**（[SPEC §6.3.3](../../spec/06-endpoints.md)）：首页不传 `limit`，把它对齐到 40 就等于**静默改掉首页看到的条数**，与裁定 3「首页一行不动」冲突。§6.3.3 的「同一个实现」说的是**代码路径**，不是参数默认值。
- **游标两态**：无 `q` 时指向 `(created_at, id)` 全序上的位置，有 `q` 时指向一次检索快照里的位置。混用或解析失败一律 `VALIDATION_FAILED`，**静默返回第一页的老约定取消**（在无限滚动里那等于把第一页追加一遍，屏幕上出现重复）。

## 5. 技术约束（含 2026-09-26 的先行探测结论）

1. **深度是有代价的，只能靠放大重扫换。** 每条通路取多少候选（`PATH_LIMIT`）与 HNSW 的搜索宽度（`ef_search ≥ PATH_LIMIT`）是绑定的，`data/search.ts:24-50` 有完整推导。翻倍预取每次都要按新深度重扫三路，trgm 路的排序代价同步上涨。
2. **翻倍预取只能「向后追加」，不能按新深度整体重排。** 实测同一查询在 `ef=40` 与 `ef=100` 下返回的**集合不同**（40 条 vs 50 条），所以整体重排会让**已经发出去的页边界移动**，重复与漏正落在 §9 第 4 条那个接缝上。规则：每条通路的名单一旦定下前缀就不再改，深扫只把没见过的新 id 按新扫里的相对顺序接在后面——已发出项的路径排名不变 → RRF 分不变 → 新旧页天然对齐。这条要落进 `api/agents/rules/retrieval.md`。
3. **带筛的向量召回：不是掉一点，是归零。已实测，结论是「筛后子集精确扫」。**
   - **后置过滤的产出约等于 `ef_search × 选择率`**：要凑够 `LIMIT` 条就得 `ef_search ≈ LIMIT / p`，`p = 0.03` 时要 1667，而生产值是 100。**`PATH_LIMIT * 2` 那个余量只在 `p ≥ 0.5` 时成立。**
   - 真表 1811 行上：`tags=猫`（筛后 54 条）在 `ef_search=100` 下**返回 1 条**；放大到 4.9 万行，`tags=猫`（筛后 1458 条）**返回 0 条**。
   - **今天线上没暴露是运气不是设计**：选择率低时规划器自己改走 Bitmap/SeqScan 精确路径（结果正确、29ms）兜住了。这个兜底随表长大而消失，而那时后置过滤恰好最毁结果。
   - **结构性事实**：「精确扫子集的代价」与「后置过滤的损失」是**同一个变量**——筛后行数。子集小 → 精确扫又准又快；子集大 → 选择率高、后置过滤够用。所以**一个绝对阈值就能覆盖两段**，不需要按选择率去算 `ef_search`。
   - 两条出路的实测对比：`hnsw.iterative_scan = relaxed_order` 全条件 50 条，但它是 pgvector 0.8 才注册的参数，与 `data/search.ts:39-50` 的部署底线直接冲突——**不用**；**筛后子集精确扫**全条件 50 条、21–29ms，不引新参数、结果精确——**采用**。
   - **它排在分页前面**：翻倍预取会把深度推大、把更多筛选组合推进 HNSW 那一段，先定下带筛召回，分页才站得住。所以 api 的落地顺序是「`GET /memes?q=` 的字段形状先合入 → 带筛召回修法 → 快照与翻倍」。
   - 探测脚本 `api/scripts/probe-filtered-recall.ts`、`probe-scale.ts`、`probe-plans.ts`（文件名里没带——它是同一批，表头的注释逐字写着「跑完即删」）验收还要用一次，**交付前删**。完整数字见「api 端验收」。
4. **HyDE 必须被快照冻结。** 见裁定 2：改写与查询向量一次性钉住，否则逐次改写不同 → 召回池变化 → 翻页错乱，而且滚一屏一次 LLM 调用。
5. **定时任务目前是零实现。** 快照过期清理会成为[回收站与定时清理](../../joint-tasks/2026-09-24-trash-and-cleanup.md)那张清单上的第一条。

## 6. 两端各要改什么

**api**

- `routes/memes.ts`：接 `q`，按有无 `q` 分派召回与排序；两态游标；`q` + `random` 互斥；`limit` 默认 40。
- `routes/search.ts`：改成**冻结转发**——只认 `q` 与 `limit`（其余参数 `VALIDATION_FAILED`）、`q` 必填、`nextCursor` 恒为 `null`，内部复用同一条服务端路径。**缺省 `limit` 冻结在 50**（[SPEC §6.3.3](../../spec/06-endpoints.md)）——不要顺手对齐到 §1.3 的 40：首页不传 `limit`，那会静默改掉首页看到的条数，与裁定 3 冲突。`GET /memes` 缺省才是 40。
- `services/search.ts`：接受筛选条件与深度参数；冻结 HyDE 改写与查询向量并交给快照。`DEFAULT_SEARCH_LIMIT = 50` 留给 `/search`，`/memes` 的缺省由路由按 §1.3 给 40。

**改了什么**

- **`GET /memes?q=` 落地**（§6.3 分派）：按 `q` 去空白后是否为空分派两个分支，**响应形状恒定**——两个分支都给 `items` / `nextCursor` / `degraded` / `rewritten`，每条 item 都带 `matchedBy`（无 `q` 时恒为 `[]`）。`q` 与 `random` 互斥（400）。类型显式写成 `ListItem`（`routes/memes.ts`），不是让两个 `map` 各推一个：`[]` 那种写法会被推成 `never[]`，而它正好是 Hono RPC 给前端的类型。
- **筛选条件只有一份构造**：`data/memes.ts` 的 `MemeFilter` / `memeFilterConditions` / `memeQueryConditions`，浏览与检索三路共用（含 `favorited` 的 EXISTS 半连接、`exclude`、`uploader` / `tagStatus`）。三路各自的 `.where()` 仍各写一遍——那是**故意留着**的重复（`data/search.ts` 文件头、`database.md §1.1`）。三路的 `ORDER BY` 补上了 `id` 末级 tiebreaker。
- **带筛向量召回的兜底**（§5 第 3 条）：HNSW 实返条数 < 本次深度时，`set local enable_indexscan = off` 走「筛后子集精确扫」重跑一次。判据是结构性的——「精确扫子集的代价」与「后置过滤的损失」是同一个变量（筛后行数），所以不需要阈值也不需要算选择率。`ef_search` 取 `深度 × 2`，并夹在 1000（超了 pgvector 是**拒掉**不是截断）。
- **快照**：新表 `search_snapshots`（`migrations/0009_create_search_snapshots.sql`；FK → `users` on delete cascade、`expires_at` 索引）。三层职责：`data/search-snapshots.ts`（一行 jsonb、运行期校验、无 `as`）/ `services/search-snapshot.ts`（翻页编排）/ `lib/ranked-append.ts`（纯函数，追加合并）。首屏冻住三路候选名单 + HyDE 改写 + 查询向量 + 时点 `asOf`；**没有下一页时不落库**（否则首页每搜一次涨一行）；已发出的页连 `more` 一起存下来，重放逐字节相同。
- **深扫只能追加**（§5 第 2 条）：`appendRankedPaths` 保留已发出名单的前缀，只把没见过的新 id 按新扫里的相对顺序接在每路后面，已发出项的路径排名不变 → RRF 分不变 → 页边界不动。
- **深度上限 `MAX_PREFETCH_DEPTH = 400`**：400 的两倍是 800 的 `ef_search`，再翻一倍是 1600，会被 pgvector 拒掉。到顶的表现是 `nextCursor: null`，不是错误。三路都挖不出新 id 时（`saturated`）也停，**允许提前停**。

**验收里抓出来的两个真问题（都已改，代码里留了注释）**

1. **「清除」清掉的是 `q`，不是筛选。** `clear()` 被我建在了 `filtersOnly(sp)` 上面，而那个函数的职责正是**摘掉 `q`**（它本来是给 `hasFilters` 用的）——点下去 URL 从 `?q=cat&isAnimated=true` 变成 `?isAnimated=true`，与按钮名字的语义正好相反，而**只看代码是看不出来的**。现在 `clear()` 自己删筛选键（`VOCAB_FIELDS` + 新增的 `SINGLE_KEYS`，与 `countActive` **共用同一份清单**，免得两处漂），`filtersOnly` 只剩 `hasFilters` 一个消费者，注释里写明「不要拿它当 `clear()` 的底」。
2. **游标被稳定拒绝时是个请求长龙。** 恢复那一支会清掉「这一页失败了、别自动补拉」那道闸，而回第一页拿到的又是「还有下一页」——替身让 `cursor` **稳定地**回 400（真实里对应游标形态对不上、快照 TTL 配错）时，转一圈就再发一次，每圈还弹一次 toast。**这与 2026-09-24 量出来的那条是同一个形状**（页底 2 秒 120 次）。现在**只自动恢复一次**：连续第二次坏就按普通失败停下（`error` + 页底的「重试」——那本来就是那条路唯一的出路），用户点「重试」重开一次机会，翻页真成功过一次也清零。断言量的是「`cursor=q-page-2` 一共只发了 2 次」；不加这道闸，3 秒内会涨到十几次。
