## 1. 为什么要做

- **向量路静默少召回。** `data/search.ts:213-225` 取 `LIMIT 50`，而 pgvector 的 `hnsw.ef_search` 默认是 40，HNSW 一次最多返回约 40 条；再叠加 `embed_model` 和排除标签的后置过滤，换模型期间会更少。SPEC §9（`09-decisions.md:213` 附近）说「库共享后没有过滤条件，HNSW 跑在最舒服的状态」，这只说对了一半：**`LIMIT` 超过 `ef_search` 这件事与过滤无关。**
- **OCR 路每次搜索都扫全表。** `data/search.ts:116-126` 的 `similarity(...) >= 0.1` 走不了 trgm 索引（只有 `%` 运算符能走），又和 `LIKE` 用 `OR` 连在一起，所以 `memes_text_trgm_idx` 实际没被这条查询用到。
- **动图抽帧的解码量随帧数平方增长** ✔。`image/frames.ts:46-49` 对**每一帧**单独起一个 ffmpeg 进程，用 `select=eq(n,i)` 从头解码到第 i 帧（`image/probe.ts:248`）；动态 WebP 每帧还要把整个文件重读一遍。真实库里去重后状态数最多 81 帧，原始帧数更多。几百帧的 GIF 大概率超过 90 秒的整体超时，5 次重试后落成 `needs_manual`。导入阶段（`services/import.ts:276`）还白抽一遍，结果不用，而且这条路径没有整体超时。

### 5.1 第 1 条：向量路的 `ef_search`

改法：`data/search.ts` 的 `vectorPathCandidates` 包进事务，先
`select set_config('hnsw.ef_search', '100', true)`（≡ `SET LOCAL`），再取数。
常量为 `HNSW_EF_SEARCH = PATH_LIMIT * 2 = 100`。

**A. 机制本身**（`enable_seqscan = off` 强制走 HNSW，15/15 条查询）：

| 会话设置 | 14 条常规查询 | `动漫角色 -带字幕` |
|---|---|---|
| 不设（pgvector 默认 **40**） | 40 条 | **39** 条 |
| `hnsw.ef_search = 100`（本任务取值） | **50** 条 | **50** 条 |
| `+ hnsw.iterative_scan = 'relaxed_order'` | 50 条 | 50 条 |

带排除词那条在默认档少两条（40 → 39），这就是任务里说的「叠加后置过滤会更少」。
`ef_search` 的档位实测：`39 → 40 → 49 → 50 → 50`（默认 / 40 / 50 / 60 / 100），
所以 `PATH_LIMIT × 2` 是留了一倍余量给后置过滤，不是刚好卡在 50。

**没选 `iterative_scan`**。本机 0.8.6 上两种写法都返满 50 条，所以这不是效果之争，
是**部署底线之争**：`hnsw.iterative_scan` 是 0.8 才注册的参数，更老的版本上这条
`set_config` 是个永远等不到提升的占位符，**静默忽略**，`LIMIT` 照旧被截成 40；
`hnsw.ef_search` 自 HNSW 存在（0.5）起就是运行时参数。另外实测**没能**复现
「`relaxed_order` 打乱 `<=>` 升序」（返回的 50 条仍是升序），所以代码注释里不写这条，
改写成版本理由——结论不变，理由换成站得住的。

**顺带实测到的一条**：`hnsw` 在 pgvector 加载后是**保留前缀**，`set_config` 一个它没注册的
`hnsw.*` 名字会**直接报错** 42602 `"hnsw" is a reserved prefix`（不是静默忽略）；
而在**尚未加载 pgvector 的连接**上先设 `hnsw.ef_search` 建的是占位符，扩展首次被用到时
把它提升上去，值照样生效（全新连接 + 强制索引：不设 40 条 → 设 100 后 50 条，
走真代码也是 50 条）。后者固化成了用例。

### 5.2 第 2 条：OCR 路走 trgm 索引

改法：`data/search.ts` 的 `ocrPathCandidates` 把 `similarity(…) >= $3` 换成 `%`
（阈值由会话变量 `pg_trgm.similarity_threshold = 0.1` 喂，同样只在事务里设），
并给 `original_filename` 补上 `%` 那一支。

| | 改前 | 改后 |
|---|---|---|
| where 里的相似度条件 | `greatest(similarity(…), similarity(…)) >= $3` | `… % $1 or … % $2 or … like $3 or … like $4` |
| `EXPLAIN`（关掉 seqscan） | **Seq Scan**（仍是全表） | **Bitmap Heap Scan → BitmapOr → 4 × Bitmap Index Scan** |
| 用到的索引 | 无 | `memes_text_trgm_idx`、`memes_original_filename_trgm_idx`（各两次） |
| 默认计划下的耗时（15 条查询平均） | 16.6 ms | 17.2 ms |
| 召回条数 | 1 / 1 / 3 / 1 / 1 / 3 / 0 / 0 / 50 | 完全相同 |

**那条「拆开，别用 `OR` 连」我按效果交付，没按字面交付**：真正让索引用不上的是
`similarity() >= 阈值` 这个**非索引条件**，不是 `OR` 本身——它一旦和 `LIKE` 用 `OR` 连起来，
`BitmapOr` 就拼不出来，连本来能走索引的 `LIKE` 两条也一起废了（改前关掉 seqscan 仍是
Seq Scan 就是这件事的证据）。改后四个分支**全是可索引的**，`BitmapOr` 成立（上表）。
按字面拆成两次查询再合并，只会多一次往返和一次去重，收益为负。
这一条与任务正文的差异记在这里，总管若不同意可以回退到字面写法。

### 5.3 第 3 条：一次 ffmpeg 调用输出全部帧

改法：`image/probe.ts` 新增 `extractAllFrames`（ffmpeg 一次调用
`-vsync 0 -start_number 0 -f image2 <dir>/f%06d.png`，动态 WebP 仍走 sharp 的 `page`），
`image/frames.ts` 改成在 `withTempDir` 里一次抽完再逐帧去重；帧号从**文件名**读回来
（`f%06d`），不靠顺序。

**逐帧一致**（改前实现取自 `git show HEAD:api/src/image/frames.ts`，import 路径不变，
是真对照而不是照抄一遍再和自己比）：

| 样本 | 原始/去重/送帧 | 送出的帧号 | 改前 | 改后 | 一致 |
|---|---|---|---|---|---|
| `animated.gif` | 4 / 4 / 4 | `0,1,2,3` | 249 ms | 88 ms（2.8×） | 是 |
| `animated-long.gif` | 12 / 12 / 10 | `1,2,3,5,6,7,8,9,10,11` | 640 ms | 121 ms（5.3×） | 是 |
| `animated-many-frames.gif` | 240 / 30 / 10 | `40,88,136,184,192,200,208,216,224,232` | 12,503 ms | 1,267 ms（9.9×） | 是 |
| `animated.webp` | 4 / 4 / 4 | `0,1,2,3` | 31 ms | 37 ms（**0.8×**） | 是 |
| `apng.png` | 4 / 4 / 4 | `0,1,2,3` | 193 ms | 63 ms（3.1×） | 是 |

「一致」= 原始帧数与去重帧数相同、送出的帧号逐个相同、每帧 PNG **字节相同**。

240 帧那个样本的时间构成：一次 ffmpeg 调用 **220 ms**（写出 240 个 PNG 共 3.24 MB）
+ 240 次 pHash 解码 **951 ms** = **1,171 ms**。也就是说剩下的时间几乎全在
`computeFramePhash`，跟抽帧无关；旧实现的 12.5 秒里绝大部分是 240 个进程各自
从头解码（总解码量是帧数的平方）。

**`animated.webp` 那一栏是回归，如实写在这里**：31 → 37 ms（约 +6 ms）。
原因是这条支路本来就在内存里切页，改后多了一步把每帧写成 PNG 落到临时目录。
4 帧样本上绝对值很小，但它与帧数无关地多了一次磁盘写；换来的是一份**统一**的
「帧 = 磁盘上的一个 PNG 文件」的契约（`extractAllFrames` 的返回类型），
去重与采样那段因此不用分两条路径。

**`MAX_RAW_FRAMES = 1000`**（`image/constants.ts`）。依据：产出上限 `MAX_FRAMES = 10`
的 **100 倍**；成本是 `O(帧数)` 次 sharp 解码（实测 240 帧 951 ms，约 4 ms/帧），
1000 帧约 4 秒 + ffmpeg 一趟，仍在整体超时之内，而 1000 之上再多的帧只会被去重和
采样丢掉，付的是纯成本。**卡在 `probeMetadata` 上而不是抽帧那一层**：认帧数的调用方
不止抽帧（导入靠它判 `is_animated`），只拦一处等于漏一处。实测 1001 帧的文件：

```
code=FILE_TOO_LARGE
message=动图有 1001 帧，超过 1000 帧上限
details={"frameCount":1001,"maxFrames":1000}
```

选 `FILE_TOO_LARGE` 而不是 `UNSUPPORTED_FORMAT`：SPEC §2.3 把后者定义成
「magic bytes 探测结果不是支持的图片格式」，而这个文件谁都认得，是**太大**。

⚠️ **APNG 必须留在 ffmpeg 那条路上**（实测：libvips 读 APNG 时 `metadata().pages`
是 `undefined`，`page: 1/2/3` 全部返回第 0 帧的内容）。哪天有人看「动态 WebP 走 sharp」
顺手把 APNG 也挪过去，模型拿到的会是同一张首帧的若干副本，而偏后段的采样恰恰是为了
避开首帧——两者合起来是「标签全错且不报错」。这条写进了 `frame-extraction.test.ts` 的注释。

### 5.4 第 4 条：导入阶段不再整套抽帧

改法：`services/import.ts` 里导入期的 `extractFrames(...)`（结果直接丢掉）换成
`extractFramePng(localPath, 0)` —— **只解第 0 帧**。探活的理由没变（在导入期失败，
用户拿到的是带原因的 `failed`；等到打标阶段才失败，是一批 `pending` 到天荒地老的图），
但一帧就够：解不开的文件在第一帧就报错。

| 样本 | 帧数 | 改前（整套抽帧） | 改后（解一帧） |
|---|---|---|---|
| `animated-many-frames.gif` | 240 | 12,503 ms | **51 ms** |
| `animated-long.gif` | 12 | 640 ms | 46 ms |
| `apng.png` | 4 | 193 ms | 50 ms |
| `animated.webp` | 4 | 31 ms | 7 ms（sharp 支路） |

**「复用」没有采用，理由写在代码里**：帧不落库，打标时还要重新下载再抽一遍，
导入期抽出来的东西没有任何地方用得上；真要复用就得把帧存进对象存储并加一列，
那是契约变更（SPEC §5.2），不在本任务范围内。改前那条路径**没有整体超时**，
这也是「导入卡住」的来源之一。

### 5.5 测试与检查

新增 `api/tests/frame-extraction.test.ts`（8 条）：每个动画样本都逐帧比对
「一次抽帧」与「逐帧抽取」的像素；GIF / 动态 WebP 还比对 libvips 的 `page` 切法
（APNG 除外，理由见上）；240 帧样本的 240 / 30 / 10 与具体帧号；
`MAX_RAW_FRAMES` 的上限（测试里现造一个 1001 帧的 1×1 GIF，断言
`FILE_TOO_LARGE` + `details.frameCount`）。

`api/tests/search-paths.test.ts` 加了 5 条：相似但不连着的原文也召回（这一路是 trgm，
不只是子串）、阈值只在本路事务里生效不留给连接池的下一个查询（用 `max: 1` 的客户端，
两次调用之间必然同一条连接；断言方式是在新连接上问 `%` 运算符本身——`current_setting`
在没加载过 pg_trgm 的连接上会报 `unrecognized configuration parameter`，
占位符读不到）、阈值确实是我们设的那个、走 HNSW 时也要取满 `PATH_LIMIT`、
**全新连接上 GUC 也生效**（断的是机制：事务里 `current_setting('hnsw.ef_search')`
读回来必须是 `'100'`，再加一条「条数 > 40」——40 是同一套种子下**不设** GUC 的实测值）。

**故障注入**（确认用例真的守得住，不是恒绿）：

- 拿掉向量路那行 `set_config` → 「走 HNSW 时也要取满」立刻红：
  `expected [ …(40) ] to have a length of 50 but got 40`。放回去即绿。
- 全新连接那条用例的对照组来自实测：同一条全新连接、同样关掉 seqscan，不设 `ef_search`
  时 `n=40`，设 100 后 `n=50`——所以「> 40」这条断言不是恒真；拿掉 `set_config`
