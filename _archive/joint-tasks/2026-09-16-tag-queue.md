# 打标队列消费者（合并收藏端点）

**状态：`done`** · 创建 2026-09-16 · 验收关闭 2026-09-16 · **api 单端任务**，web 不动

## 为什么

导入已经上线，库里能进图了——但**每一张都停在 `tag_status = pending`、`embedding` 为 null**。后果是三件事同时被卡住：

1. **搜索永久降级。** 三路融合实际只跑 OCR/trgm 两路，向量路一直 `degraded: true`。检索是这个产品的全部价值，现在它缺一条腿。
2. **评测集拿不到真数据。** `recall@5` 需要真实 embedding，[评测集任务](../../joint-tasks/2026-09-13-eval-set.md) 卡在这里；搜索任务转出的「未跑评测集」遗留项同因。
3. **词表 v1 无法迭代。** 词表要靠真实打标结果暴露缺词和误命中，[词表 v1](../../joint-tasks/2026-09-13-vocab-v1.md) 现在只能靠人想。

`tag_jobs` 表、入队（写 memes 同事务）、取任务语句、抽帧、词表校验、向量截断归一化都已就位。**缺的只有消费者本身和视觉调用**。

**顺带合并进来的缺口：** `web/src/lib/api.ts:133` 的 `toggleFavorite()` 已经在对 `/memes/{id}/favorite` 发 PUT/DELETE，但 `api/src/routes/memes.ts` 里只有两个 GET——**收藏功能现在是坏的**。SPEC §6.4 早已定契约、`user_favorites` 表和 `favorited` 的读路径都在，只差两个 handler。放进本任务是因为它和「让库里的图真正可用」是同一件事，不值得单开任务。

## 范围裁定：视觉通道用部署方默认通道

本任务**只用 `env.defaultVision`**，不等用户自带 key。

理由：用户视觉配置的读写与 AES-GCM 解密属于 [SPEC §6.5](../../spec/06-endpoints.md) 的配置任务（含 web 设置页和测试连接），那是一整个跨端任务。消费者和配置读写是两件事，等它会让一条已经能跑的链路再压半个月。这与 HyDE 的现状一致——HyDE 也走 `env.defaultVision`，是同一处已知偏差，将来同一批解决。

三条约束，不满足就是做错了：

- **主通道来源必须收在一个可替换的 resolve 函数里**（类比 `ai/embedder.ts` 的 `resolveEmbedConfig()`）。接入点唯一，配置任务上线后只改这一处。**不要在 worker 里直接读 `env.defaultVision`。**
- **没有探测记录时按最保守路径走**——不用 json mode、不发多图、客户端截断（`api/agents/rules/ai-providers.md §2`）。部署方默认通道同样没有测试连接记录，**不许因为「这是我们自己配的」就假设它支持什么**。
- **`env.defaultVision` 为 null 时按 `AI_NOT_CONFIGURED` 处理**：不消费、不失败重试，图留在 `pending`，等配好后批量补打标（`queue.md §3`）。这是产品要求的降级态，不是配置错误。

## 注意

**打标质量是公共品。** 一个人配了差模型污染的是所有人的搜索结果，所以改打标链路要对照评测集，不能只看单张图效果。

**禁止任何供应商特有的分支**，尤其禁止按 `baseUrl` 猜（`if (baseUrl.includes('deepseek'))` 一旦出现抽象就没了）。能力从配置读，配置从实测来。

**入队时的 `memeId` 必须来自 `data/memes.ts` 的查询结果**，不要为了省一次查询在 `tag_jobs` 上 join `memes`——那会绕过 `deleted_at is null`，表现是给已删除的图打标且不报错（`queue.md §8`）。

**不改 SPEC。** 本任务不新增字段、不改字段含义：`tag_status` 的四个取值在 §5.2.3 已定，收藏契约在 §6.4/§5.4 已定，响应结构不变。提示词和重试参数是本端实现约束，随便调。

## api 端验收

**实测口径：** `npx tsc --noEmit` 干净；`vitest --project unit` 94 passed / 11 files；`vitest --project integration` 102 passed / 10 files（真 Postgres `<db>_test`）。集成测试里**只换掉两样**——R2 换成内存实现、`fetch` 换成桩；数据库、抽帧、拼图、PNG 转码、词表校验、写回事务全是真的。

测试分两层，不重叠：判定逻辑（`lib/vision-output.ts`、`lib/retry-policy.ts`、`lib/frame-plan.ts`）是纯函数，在 `src/lib/*.test.ts` 里用 `docs/fixtures/responses/` 的**真实供应商响应**做单测（`vision-output.test.ts` 28 条）；集成层测的是「判定完之后库里变成什么样」，那里的响应是构造的。

### 三种拒绝形态

| 形态 | 单测（真实样本） | 集成（落库结果） |
|---|---|---|
| HTTP 层 | `classifyHttpFailure` 对 451、400 `content_policy`、400 `protocol_not_supported`、429/5xx 的分类 | HTTP 451 → 视觉只调 1 次、`tag_jobs.status = failed`、`attempts = 1`、`tag_status = needs_manual` |
| 200 但正文是拒绝 | `interpretVisionContent` 对 `REFUSAL_HINT` 的识别 | 正文 `抱歉，我无法描述这张图片。` → 同上，且**不重试** |
| JSON 结构完整但内容全空 | `isEmptyTagFields`：五个字段齐全但全为空/空数组 | 结构合法全空 → `needs_manual`，`description` 与 `search_text` 留 null（没有写进半条记录） |

判空另外测了**词表过滤之后才变空**的那一支：`emotions` / `scenes` / `tags` 全是越界词，`applyVocab` 过滤完剩空 → 仍然判拒绝。顺带确认了另一个方向——**部分越界只丢那几个词，不否定整条记录**（`tags.style` 里混一个越界词，其余字段照常入库，`tag_status = ok`）。alias 归一化在词表校验之前跑，用 `emotions: ['服了']` 钉住，落库是 `无语`。

⚠️ **`tag_status = 'refused'` 这个取值目前跑不到。** 本任务只有主通道（「范围裁定」），降级链实际是「主通道 → `needs_manual`」，所有终局失败都落 `needs_manual`。等 SPEC §9.5 定稿、副通道接上，`refused` 才会成为可达状态。

### 四个重试分支

全部用**改库里的 `attempts` 再让 worker 跑一轮**来验，不靠等真实退避（退避基数 30s，测试等不起）：

- `AI_UNREACHABLE`（503）→ `status` 写回 `pending`、`attempts = 1`、`run_after > now + 10s`（指数退避确实生效）、`memes.tag_status` 仍是 `pending`；把 `attempts` 预置成 4 再跑 → `failed` + `needs_manual`（上限 5 次）
- `AI_REFUSED` → 见上表，一次就终局，不回队列
- `AI_INVALID_OUTPUT` → `pending` 且 `run_after < now + 10s`（走的是 `INVALID_OUTPUT_RETRY_MS`，不是指数退避）；`attempts` 预置成 1 再跑 → `failed` + `needs_manual`（主通道只重试 1 次）
- `AI_UNSUPPORTED`（400 `protocol_not_supported`）→ 调 1 次、`failed`，不重试

另外两条与重试相关的：

- **embedding 失败不回滚打标**：`tag_status` 留 `ok`、`search_text` 非 null、`embedding` 为 null、任务回 `pending`。重试那一轮断言 `visionCalls` 仍然是 1、`embedCallCount` 是 2——**重试 embedding 不会再付一次视觉调用的钱**，这是「失败不回滚」真正要保住的东西。
- **排队期间图被软删** → 0 次视觉调用，任务直接 `done`。

### 动图路径

- `animated.gif`（4 帧，已有样本）：走拼图，**发出去是 1 张 PNG**，提示词里带「网格图」字样。静图对照组发 1 张 PNG、无帧提示。
- `animated-long.gif`（12 帧，**本次新增**）：`tests/tag-queue-degrade.test.ts` 里跑满降帧梯子，实测 `images` 序列 `[10, 4, 1]`，拼图那一级确认是 1 张而不是 4 张，且三级 `model` 全是同一个——**先降帧不降通道**。降一级就成功时不再往下降（`[10, 4]`，`tag_status = ok`，任务 `done`，降级不算错误）。
  - 新增这个样本是因为 `animated.gif` 只有 4 帧，`planVisionAttempts` 排不出 10 帧那一级，梯子最关键的第一级根本跑不到。生成逻辑加在 `api/scripts/gen-fixtures.ts`（可复现，不是手捏字节），产物 `docs/fixtures/images/animated/animated-long.gif` 237 KB。
  - ⚠️ 这条梯子**今天在生产里走不到**：`resolveVisionConfig()` 固定返回 `multiImage: null`（没有探测记录就按最保守路径走，「范围裁定」第二条），动图的 plan 永远是单级拼图。所以该文件用 `vi.mock` + `importOriginal` **只替换 `resolveVisionConfig` 一个函数**把能力位打开，`callVision`、提示词、图像管线都是真的。SPEC §6.5 的配置任务把探测结果存下来之后，这条路径会自然变成真实流量路径。

### `AI_NOT_CONFIGURED`

单独一个文件（`env.ts` 在首次 import 时冻住值，同进程没法既有配置又没配置）。清空六个 `DEFAULT_VISION_*` / `DEFAULT_EMBED_*`，worker 起 1 秒：任务仍是 `pending`、`attempts = 0`、`last_error` 为 null、`tag_status = pending`、`fetch` 0 次。直接调 `tagMeme()` 返回 `not_configured` 而不是 `failed`。

要点是「**没被取走**」而不是「取走了但没做」——当成失败重试的话，退避五轮之后整库都会变成 `needs_manual`，而部署方只是还没填环境变量，填完之后本该自动补上的那批图全都得人工改回 `pending`。

### 收藏

`tests/favorites.test.ts` 10 条，走真 HTTP（`testApp.request`）：

- **幂等的判据是库里只有一条**，不是「第二次没报错」：连发两次 PUT 之后查 `user_favorites` 计数为 1；连发两次 DELETE 都是 204。
- **软删过滤**：`softDeleteMeme` 之后 PUT / DELETE 都是 404 `NOT_FOUND`，且没有写进收藏表。外键只保证图存在，不保证它没被删——这条挡的就是「靠外键兜底」。
- **人和图的关系不是图的属性**（SPEC §5.4）：Bob 收藏 Alice 的图之后，`memes` 行的 `edited_by` / `edited_at` 仍为 null、`tag_status` 不变；两个人各自收藏同一张图互不影响，Alice 取消不影响 Bob。
- 未登录两个方法都是 `UNAUTHENTICATED`。

### 并发按用户分

6 个重任务（同一用户）+ 1 个轻任务（另一用户）同时入队，断言轻任务完成时重任务**没有全部做完**——判据是「没有排在六个后面」，不是「第一个完成」（后者依赖调度时序，会偶发失败）。

### 评测集：**没跑**

按 `api/AGENTS.md §5` 直说。本任务动了打标提示词（`src/ai/vision.ts` 的 `SYSTEM_PROMPT` 把整份词表内联进系统提示，为前缀缓存），按规矩应当对照评测集，但现在跑不出有意义的数字：
