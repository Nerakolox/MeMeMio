# 认证功能

**状态：`done`** · 创建 2026-09-14 · 验收 2026-09-14

## 为什么

认证是整个项目所有接口的前提。没有会话就没有 `currentUser`，没有 `currentUser` 就没有权限判断，导入、搜索、打标队列、配置——每一条接口都依赖它。骨架已经跑通了类型链路，但没有实现任何业务逻辑，现在从最小的独立单元开始：先让人能登进来。

SPEC 对会话的设计有几处非显然的决定，实现前必须清楚：

- **会话存 PostgreSQL，不引入 Redis。** 见 [§9.11](../spec/09-decisions.md)。不要因为「会话通常用 Redis」就绕过这个决定。
- **邀请码是一次性的，过了 `expires_at` 也不能用。** `invite_codes.used_by` 非空即消耗。
- **第一个注册的用户自动成为 `admin`。** 判断依据是 `users` 表是否为空，不是靠配置项。
- **cookie 在生产环境带 `Secure`，本地开发不带。** 同域部署，不需要 CSRF token 以外的跨域处理。
- **SPA 启动时的第一个请求是 `GET /auth/me`，返回 401 则前端跳转登录页。** 这是前后端之间的一条契约，不是实现细节。

## 做完的标准

- [ ] `POST /auth/register` 验证邀请码有效（未使用、未过期），创建用户，消耗邀请码，建会话，返回 User 对象
- [ ] `POST /auth/login` 验证 name + password，建会话，返回 User 对象
- [ ] `POST /auth/logout` 销毁会话，返回 204
- [ ] `GET /auth/me` 已登录返回当前用户，未登录返回 `UNAUTHENTICATED`（HTTP 401）
- [ ] 第一个注册用户 role 自动设为 `admin`，之后的用户 role 为 `member`
- [ ] 会话存 PostgreSQL，不引入新的外部依赖
- [ ] httpOnly + SameSite=Lax cookie；生产环境加 `Secure`，本地开发不加
- [ ] 密码哈希，明文不进数据库、不进日志
- [ ] SPA 启动时调 `/auth/me`，401 跳登录页，200 继续正常流程
- [ ] 登录页可独立访问（未登录用户直接打开应用看到的是登录页，不是空白或报错）
- [ ] 手动联调：注册 → 刷新 → 仍是登录态；登出 → 刷新 → 回到登录页

**暂不做：** admin 的邀请码管理接口（`GET/POST /admin/invites`）和用户管理接口（`GET /admin/users`、`PATCH /admin/users/{id}`）。这些依赖认证，但不阻塞后续导入和搜索开发，单独列任务。

## 两端各自做什么

### api 端

**涉及的 SPEC：** §3.1、§3.2、§5.1、§6.1；错误结构见 §2；响应信封见 §1。

1. **会话表迁移**：新建 `sessions(id, user_id, expires_at, created_at)` 或等效的持久化方案。会话不存 Redis，见 §9.11。
2. **密码字段**：`users` 表加 `name text not null unique` 和 `password_hash text not null`——这两个字段不在 §5.1 的对外表示里，但必须存在。入库前用 bcrypt 或 argon2 哈希，明文不落盘。
3. **`POST /auth/register`**：验证 inviteCode 有效（`used_by is null` 且 `expires_at is null or expires_at > now()`），事务内创建 user、消耗 invite_code、建 session、写 cookie。`users` 表为空时将新用户 role 设为 `admin`。
4. **`POST /auth/login`**：查 name → 比对 hash → 建 session → 写 cookie。
5. **`POST /auth/logout`**：删 session 记录，清 cookie，返回 204。
6. **`GET /auth/me`**：从 cookie 读 session_id → 查 session → 查 user，返回 `{ id, role, storageQuotaBytes, storageUsedBytes, createdAt }`。`storageUsedBytes` 聚合自 `memes` 表（含软删未满 30 天的记录，见 §3.6）。未登录或 session 已过期返回 `UNAUTHENTICATED`。
7. **认证中间件**：统一提取 `currentUser`，后续所有需要登录的路由通过中间件注入，handler 内不重复读 cookie。
8. **回填本文档**：完成后在「api 端验收」小节回填实测情况。

### web 端

**涉及的 SPEC：** §6.1（/auth/me 是 SPA 启动第一个请求）；错误消费见 §2。

1. **SPA 启动逻辑**：应用加载时调 `GET /auth/me`。200 → 进入正常流程；401（`UNAUTHENTICATED`）→ 跳转登录页。这个检查必须是阻塞式的——在结果回来之前不渲染任何需要登录的内容，也不先闪一下主界面。
2. **登录页**：name + password 表单，调 `POST /auth/login`。成功后跳转到应用主页（或原来要去的页面）。错误展示服务端返回的 `message`，不自行造文案。
3. **注册页**：name + password + inviteCode，调 `POST /auth/register`。成功后直接进入应用，不再走登录页。邀请码无效时展示服务端错误。
4. **登出**：调 `POST /auth/logout`，清本地状态，跳回登录页。
5. **类型消费**：通过 Hono RPC 消费 api 导出的 User 类型，不手写类型定义。
6. **回填本文档**：完成后在「web 端验收」小节回填实测情况。

## api 端验收

完成日期：2026-09-14

**8 项任务全部完成：**

1. **会话表迁移** — `migrations/0001_add_auth_fields.sql`：`users` 加 `name`（unique）/ `password_hash`，新增 `sessions(id, user_id, expires_at, created_at)`，外键级联删除。

2. **密码字段** — `src/data/auth.ts`：`hashPassword` / `verifyPassword` 使用 Node 内置 `scrypt`（salt 16 字节 + key 64 字节），明文不落盘，`timingSafeEqual` 防 timing attack。

3. **`POST /auth/register`** — 验证邀请码（`used_by is null` 且未过期）；事务内创建用户、消耗邀请码、建会话；第一个用户自动设为 `admin`；写 httpOnly + SameSite=Lax cookie，生产加 Secure。

4. **`POST /auth/login`** — 查 name → `verifyPassword` → 建 session → 写 cookie。用户不存在与密码错误返回同一消息，避免用户名枚举。

5. **`POST /auth/logout`** — 删 session 记录，清 cookie，204。

6. **`GET /auth/me`** — 从 cookie 读 session_id → 查有效 session → 查 user → 聚合 `storageUsedBytes`（软删 30 天内计入，SPEC §3.6）。未登录或过期返回 `UNAUTHENTICATED` 401。

7. **认证中间件** — `src/middleware/auth.ts`：`requireAuth`（抛 UNAUTHENTICATED）和 `optionalAuth`（注入 null），统一从 cookie 解析 session，handler 不重复读 cookie。

8. **Bug 修复（连带）** — `src/data/memes.ts` 的 `assertCanMutate` 原来比对 `actor.role === 'User'`，SPEC §3.2 定义管理员角色为 `'admin'`，已修正；对应测试和工厂函数一并更新。

- `npm test` — 23/23 通过（3 个单元 + 1 个集成）。
- 手动联调待 web 端完成后进行。
