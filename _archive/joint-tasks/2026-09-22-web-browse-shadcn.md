### 顺带修掉的那个真缺陷

顶栏（`App.tsx`）是 `z-10`，而卡片上的角标 /「⋯」/ 收藏（`components/MemeCard.tsx`）
**也是 `z-10`**，且 DOM 更靠后；`SidebarInset` 只是 `relative`（**不构成层叠上下文**），
于是两者在同一个层叠上下文里按 DOM 顺序比——**滚动时卡片浮层画到顶栏上面**。

产品负责人裁定：顶栏抬到 `z-9999`。

## 行为变化（有意的，逐条记）

1. **断网不再显示 `undefined`**：`toStateError(err)` 给出「连不上服务端，确认 api 是否已启动」。
2. **失败 note 变成红色**：今天错误与成功的 note 长得完全一样（`.browse__note--error` 这条
   规则在 CSS 里根本不存在，只有 `role` 不同）。
3. **chip 从约 24px 变成 44px**：筛选栏明显变长（本来就能滚）。
4. **同一组筛选条件的 query string 从此是规范化的**：`VocabPicker` 按词表顺序重排选中值，
   今天按点击次序排。
5. **641–767px 这一档换了形态**（断点 640 → 768）：由「163 个 chip 铺满整屏」变成
   「工具条 + 满宽瀑布流」。
6. **抽屉打开时，顶栏只是「画在上面」，不是「还活着」**——这条原先写的是「顶栏仍可点，
   点 ☰ 能开合导航」，**实测推翻了它**（见下面「绘制与交互」）：Radix 的模态给 `body` 挂
   `pointer-events: none`，抽屉以外**全都点不动**，在顶栏那一条上按下命中的是遮罩、
   效果是**把抽屉关掉**。视觉上顶栏确实没被遮罩蒙住（这条成立），交互上不成立。
7. **发出的请求只认最后一次**：`use-browse-list` 用一个自增序号丢弃过期响应。
   今天没有这层保护，连点两个筛选时先发的响应可能后到、把上一组筛选的结果盖回来
   （`DiscoverWall` 记过同一课）。这是本次顺手补的，不是迁移必须。
8. **编辑面板与导航抽屉里的同级 chip 也拿到了 `cursor-pointer`**（同一个 `VocabPicker`）。
   今天它们的指针是箭头（那条 `cursor: pointer` 只写在 `.browse__tag-btn` 上）。
9. **换筛选时不再拿旧游标发一页**（实测抓到的真缺陷，迁移前那份也带着）：滚到第二页之后
   换筛选，重置 effect 里的 `setNextCursor(null)` 要到下一次渲染才生效，而观察器的闭包
   还揣着上一次的游标，重注册时若 sentinel 仍在视口里就会**用旧筛选的游标配新筛选的参数**
   发一页出去。修法是加一个**同步作废**的 `cursorRef`，观察器只认它。详见
   `use-browse-list.ts` 里那段注释。

### 顶栏「压在下面」：绘制与交互要分开量

顶栏抬到 9999 之后，`SheetOverlay`（`z-50`）在它下面——但这里有个**计划时没想到**的层次，
两个方向都量了才说清楚（探针：`elementFromPoint` + 把两边 `pointer-events` 都恢复后重测）：

- **绘制上顶栏赢**：抽屉开着时直接取点命中 `div[sheet-overlay]`，把遮罩的 `pointer-events`
  关掉、顶栏的打开再取同一点，命中的是 **header 自己**。即遮罩的 `bg-black/30` **不蒙顶栏**。
- **交互上顶栏不可点**：Radix 的模态给 **`body` 挂 `pointer-events: none`**
  （实测 `getComputedStyle(header).pointerEvents === 'none'`），抽屉以外一切不可点。
  在顶栏那一条（38, 28）上按下，命中的是遮罩 → 效果是**关掉抽屉**，不是「点 ☰ 开合导航」。

所以计划表里「抽屉打开时顶栏仍可点」这条**不成立**，是本页三处 Sheet 的**模态语义**决定的，
不是 z-index 能改的；抽屉本身从 y=56 起，视觉上也不与顶栏打架，因此保持原样。

### 同一条缺陷在浏览页也真的存在（计划的猜测被推翻）

计划里写「浏览页因 masonic 单元格带 `transform`（自成层叠上下文、按 z=0 画）本来就压不上去」
——**不成立**。实测 masonic 的单元格是 `position: absolute; top: Npx; left: 0`，`transform: none`
（`.mjs` 里量到的 computed style），`z-index: auto` 的绝对定位元素**不构成层叠上下文**，
所以卡片浮层的 `z-10` 就在根上下文里跟顶栏比。两页各量一次、各带一次对照：

| 页面 | 顶栏 9999（现状） | 把顶栏临时改回 10（对照） |
|---|---|---|
| 首页 `/` | 命中 **header** | 命中卡片收藏按钮的 `svg` |
| 浏览页 `/browse` | 命中 **header** | 命中卡片收藏按钮的 `svg` |

对照那一列是关键：它证明这条断言**判别得出差异**（不是「本来就没坏」），也证明浏览页
同属这条缺陷。构造重叠要把视口压到 400 高：浏览页的文档只有 ~969（绝对定位的单元格从
y≈140 起），720 高时可用滚动量被钳在 ~249，卡片**进不了** 0..56 的顶栏带——第一次跑就是
这样停在 y=340，那条断言量的不是重叠处。

### 列数对账：1280 下逐字相同，2560 下**故意不同**

masonic 的列数只由容器宽度决定（`columnWidth`/`columnGutter`/`overscanBy` 一个字没动，
`git show HEAD:web/src/routes/browse.tsx` 对过）。公式取自它自己的
`dist/main/use-positioner.js:210`：`列数 = ⌊(宽 + 12) / (160 + 12)⌋`，
`列宽 = ⌊(宽 − 12×(列数−1)) / 列数⌋`。先用两个实测点校验公式，再外推迁移前：

| 视口 | 迁移前（无封顶） | 迁移后（`max-w-6xl`） |
|---|---|---|
| 1280 | 瀑布流区 717 → **4 列 × 170** | 同左（封顶没生效）——**逐字相同** |
| 2560 | 瀑布流区 1997 → 11 列 × 170（**算出**） | 瀑布流区 908 → **5 列 × 172**（**量出**） |

2560 那格是**有意的行为变化**（不封顶时超宽屏会铺成十几列小图）；单元格仍 ≥160px，
styling.md 那条底线没破。校验点：717 → 4 列 × 170、908 → 5 列 × 172，两次都与量到的
数字逐位相同，所以 1997 那一格照同一公式推算。

### 打桩带了一处「游标显式判死」

真实实现里游标是不透明的，跨筛选复用它由服务端解释——那样测得出来的只是「发了个怪请求」。
打桩改成**游标里带筛选签名**（`p2:<按名排序的参数>`），签名与本次参数不符就记 `badCursor`
并回 400。于是「换筛选时拿旧游标发了一页」变成一个可断言的事件；实测清除时**第一发是重置**
（无筛选参数、无 cursor），也没有任何 `badCursor`。

### 一、左栏：`sticky` 为什么做不到，以及改成了什么

先排查，量到的是**可粘余量 = 容器高 − 左列高**，而：

```text
左列高 = max-height = 100vh − 56   （163 个 chip 永远撑满，不缩）
容器高 = max(左列高, 结果列高)      （md:items-start，两列各按自己长）
```

**结果列比视口矮时余量就是 0**，左列整段跟着页面走。七档窗口逐档量（滚到页面底部那一段）：

| 视口 | 结果列高 | 左列 max-height | 余量 | 实测左列 top（scrollY 0.25/0.5/0.75/1.0） |
|---|---|---|---|---|
| 1024×768 | 2185 | 712 | 1473 | 56 / 56 / 56 / 56（钉住） |
| 1280×800 | 865 | 744 | 121 | 56 / 56 / 56 / 56（钉住） |
| 768×800 / 900×1200 | 3869 / 1633 | 744 / 1144 | 大 | 全程 56（钉住） |
| **1440×900** | 841 | 844 | **0** | **68 / 56 / 44 / 32**（= 80 − scrollY，整段跟着走） |
| **1920×1080** | 871 | 1024 | **0** | 同上（滚程只有 48px） |
| **2560×1440** | 871 | 1384 | **0** | 同上 |

也就是说：**左栏「固定」与否取决于结果列有多高**，图片少的时候立刻失效；余量那一档的滚程
48px 来自外壳 `p-6` 的上下内边距。这不是「差一点」，是设计依赖了一个与图片数量有关的量。

改成**外壳式布局**：md 以上容器高度钉死 `100svh − 顶栏`，两列各 `overflow-y-auto`，文档不滚。

```text
md:-my-6   抵消外壳 p-6（同一个 6，改一个要改另一个）——不抵消页面就多 48px 可滚
md:h-…     减顶栏；svh 与外壳的 min-h-svh 同一把尺
md:py-6    加回来：容器正好铺满顶栏以下，两列位置与改前一模一样
去掉 md:items-start（stretch 才是要的：容器高度已定，左栏不会再被短结果压扁）
```

顺带发现并修掉一个**新冒出来的抖动**：结果列成了滚动容器之后，竖条出现/消失会让容器窄
15px（Windows 的滚动条占宽），而 masonic 按容器宽度算列数——列宽 168 → 165 → 墙变矮 →
竖条又消失，**1440×900 上稳定在「两条滚动条同时在」的相位**：墙 888 > 列 877，结果列多出
一条横向滚动条，右端 11px 被切。`md:[scrollbar-gutter:stable]` 让客户区宽度与竖条无关，
回路从根上不存在（该档列宽随之由 168 变 165，列数不变，仍是 5）。

### 二、顶栏 z-index：9999 → 60

60 只和两个邻居有关：卡片浮层与侧边栏是 `z-10` / 轨道 `z-20`、Radix 那层是 `z-50`，
中间没有别的东西——所以 60 与 9999 在当前全站没有可观察的差别（首轮那四条断言全部重测通过）。
**唯一的上限来自全屏阅览**：`.yarl__portal` 自带 `z-index: 9999`。两者从「同值比 DOM 顺序」
变成「`9999 > 60` 比数值」，顶栏那个数因此**不能再加到 9999 以上**（`App.tsx`、
`ImageViewer.tsx`、`styling.md` 三处都写明了这条）。

## 续（2026-09-22，同日第三批）：分栏可拖 + 两处滚动换成 shadcn 的 ScrollArea

用户三次验收的第三句：「把这这两个部分都用 shadcnUI 的那个滚动条组件来切换。同时换成
可拖拽宽度的那个组件」——两处滚动（筛选列、结果列）换 `ScrollArea`，两列之间换
`ResizablePanelGroup`（新增依赖 `react-resizable-panels@^4.13.1`）。

### 一、四个必须量过才知道的坑

1. **`Group` 的行内样式压过大类**：库给自己写 `height:100%; width:100%; display:flex`，
   文档说「除 `overflow` 外不可覆盖」。要在断点上换高度/显示方式只能上 `!important`
   （`max-md:block! max-md:h-auto! md:h-[calc(100svh_-_var(--app-header-h))]!`）。
   少了这三个 `!` 的表现是**容器高 = 内容高**，页面又能滚了，左栏跟着跑——直接退回第二批之前。
2. **分隔条的方向选择子看着像反的**：`aria-orientation` 描述**分隔条自己**，横向分栏实测拿到
   `aria-orientation="vertical"`，正好落进基础样式那支（`w-px` 竖线）。按「库把组的方向写进去」
   去改（我改了），当场变成 1281×1 的横线、两个面板被挤成 0 宽。**注册表文件一个字没改**，
   理由写在 `ui/resizable.tsx` 头部。
3. **面板宽度首帧是 0**：react-resizable-panels 等自己的 ResizeObserver 报数（先 0、随后 1039），
   而 masonic 的容器 element 会被 `key={didEverMount}` **重挂一次**——一次性首读 + 挂在旧节点上的
   observer 两个坑叠起来，表现是「24 张图在 1039px 宽里排成一竖条」。改成无依赖 layout effect +
   `measured` ref（元素没换直接 return）。
4. **手机上 `pr-3` 会吃掉一列**：那个 viewport 在窄屏不滚、没有滚动条要躲，
   白扣 12px 正好让列数从 2 掉到 1（(330+12)/172 = 1.98）。所以留白写成 `md:pr-3`。

### 二、真缺陷：虚拟化跟着 `window.scrollY`，而页面已经不滚了

`<Masonry>` 的滚动位置来自 `useScroller()` → `@react-hook/window-scroll`，读的是
**`window.scrollY`**。md 以上页面不滚（第二批改的外壳式布局）、滚的是结果列，于是它量到的
`scrollTop` **恒为 0**，可见范围永远钉在 `[0, window.innerHeight × overscanBy]` = 前 2700px。

后果不是「性能差一点」，是**滚到下面一片空白**（容器高按全部条目算 4065，里面只摆了
前 2700 的格子），而且无限滚动每追加一页空白只会更长。实测：90 条 6 列，滚到列底时
最低的那张图在视口上方 400px 处。

改用 masonic 的**原语**（`useMasonry` + 自己喂 `scrollTop` / `height`，文档里写明了这种用法），
滚动源**由「谁真的在滚」现场判定**而不是按断点分叉（`scrollEl.scrollHeight >
scrollEl.clientHeight + 1` 才算元素在滚，否则退回窗口）——手机上那个 viewport 高度是 auto，
整页在滚，按断点分叉就会让手机整份渲染。理由全写在 `features/browse/BrowseResults.tsx` 头部。

|---|---|
| 布局 | 容器 [280,56,1296,844] `display:flex`；筛选面板 [280,80,220,796]、结果面板 [525,80,1051,796]；分隔条 [512,80,**1**,796]、`aria-orientation=vertical` |

## 续（2026-09-22，同日第四批）：标签与按钮的尺寸按**指针**分档

用户四次验收：「现在所有的标签 TAG、按钮都太大了，**【预览页 筛选板块是最佳实例】**，
改小一点」。这一条**改的是一条规则**（`styling.md` 那条「44px、没有例外」），不只是样式。

### 一、改了什么

`lib/touch.ts` 的 `TOUCH` 由字面量 `min-h-11` 变成 **`min-h-11 pointer-fine:min-h-8`**——
一处改动，40 个调用点（浏览 / 首页 / 搜索 / 卡片 / 编辑面板 / 设置页）全部跟着降。
另有三处手写 `min-h-11` 的落点一并改成同一条闸门：侧边栏 `NAV_ITEM_SIZE`、
筛选栏那四行（`BrowseFilters.tsx` 新提的 `ROW`）、顶栏 ☰（`size-11 pointer-fine:size-8`）。
卡片上的浮层按钮（「⋯」与收藏）由 `size-8 max-sm:size-11` 改成 `size-8 pointer-coarse:size-11`。

### 二、为什么是 `pointer` 而不是 `md:` / `any-pointer:`

那条 44 的来历是**手机单手操作**，而断点按**宽度**猜指针，两种都猜错：700px 的桌面窗口被
当成手机（白扛 44），宽屏平板被当成桌面（手指按 32）。`pointer` 描述的是**主指针本身**。
不用 `any-pointer: coarse` 是因为它问的是「这台机器有没有粗指针」，触屏笔记本（有触控屏也有
触摸板）答「有」，于是每台带触摸屏的桌面都退回 44 高的行。`pointer-fine:` 这个变体仓库里
早就在用（`MemeCard` 的浮层显形）。

`min-height` 只抬不压，所以细指针那一档是**把额外加的那 12px 收回去**，落到各控件**自己的**
`size` 变体上（这也是库作者的默认密度），不是把控件压到 32。

筛选列因此短了 **792px（−23%）**，1600×900 首屏从 11 行 chip 变成 16 行。
`?emotions=开心` 的筛选、`清除` 的出现与点击两档都照常（chip 点击 → URL → 请求那条链路没动）。

  本次只把**窄桌面窗口**那一档从 44 收回 32。
- 没动 SPEC（纯本端样式与一条本端规则）。

**「点文字能翻转」这一条是实测出来的、不是想当然的**：裸 `<label>` 包住一整个 Radix
`Switch`（`<button role="switch">`）确实会转发点击，且给出无障碍名——但这条转发在
`Checkbox` 上成立不保证在 `Switch` 上成立，所以逐条量了（组件里那两段注释记的就是这个）。

### 三、没动的

- **没动「多选器」**（情绪 / 场景 / 标签那 163 个 chip）：它们本来就是多选、不是布尔开关，
  换成开关会在语义上把「可多选」说成「开/关」。用户那句「多选器换成开关」按上半句的语境
  判为指顶上那两个复选框。
- 没动第四批的尺寸闸门、没动筛选→URL→请求那条链路、没动 SPEC。

## 续（2026-09-22，同日第六批）：顶栏 z 收回 20，三处抽屉回到全高

用户第六次验收：「顶部的 Z-INDEX 调了吗，**现在还是和侧边栏展开有冲突，会一起显示**」。

这一条推翻的是本任务第二批自己的一个决定（顶栏抬到 `z-60`、三处抽屉改「从顶栏下沿开始」）。

### 一、现象与成因

手机档开导航抽屉时，屏幕上是**两条**：上面一条 56px 的顶栏（还带那个 ☰），下面是抽屉本身，
抽屉的品牌行被挤到顶栏下面。看起来像「顶栏和侧边栏同时在」。

成因是第二批把顶栏抬到了 `z-60`，比 Radix 那一层（`z-50`）高——抽屉再怎么全高也盖不住它，
于是当时给三处抽屉各写了 `data-[side=*]:top-(--app-header-h) bottom-0 h-auto` 去**避开**顶栏。
那是个绕路：**真正错的是顶栏的高度不该超过 50。**

而且那条顶栏在抽屉开着时**是假的**：Radix 的模态给 `body` 挂了 `pointer-events: none`，
在顶栏那一条上按下命中的是 `SheetOverlay`，效果是**把抽屉关掉**（第二批的注释里已经实测记着
这件事），所以「留着顶栏可点」这个理由本来就不成立。

### 二、改法：顶栏 `z-60` → `z-20`，三处抽屉删掉偏移

`z-20` 仍然 > 卡片浮层的 `z-10`（第二批真正的目标：修「卡片浮层画到顶栏上面」），
同时 < Radix 那一层 `z-50`——于是抽屉与遮罩都盖得住顶栏，`top-(--app-header-h)` 那三个类
连同它们的推导一起删掉，注册表的 `inset-y-0` 原样保留。

| 文件 | 改动 |
|---|---|
| `src/App.tsx` | 顶栏 `z-60` → `z-20`；`## z-index` 那一整段重写（含「上限是 50 不是 9999」） |
| `components/ui/sidebar.tsx` | 移动端 `SheetContent` 删掉三个 `data-[side=*]:top/bottom/h-auto` |
| `features/manage/MemeEditPanel.tsx` | 同上（右侧面板） |
| `features/browse/BrowseFilterSheet.tsx` | 同上（左侧抽屉），只留 `data-[side=left]:w-[85vw]` |
| `components/ImageViewer.tsx`、`agents/rules/styling.md` | 跟着把 `9999 > 60` 改成 `9999 > 20`；`--app-header-h` 引用表里删掉「三处抽屉的顶边」那一行 |

### 三、实测（`web/dist` + 打桩，1600×900 与 390×844）

| 断言 | 结果 |
|---|---|
| 首页图墙（**无 `transform`**，就是当初会画错的那种格子）滚到卡片收藏按钮与顶栏相交处 | `elementFromPoint` 命中**顶栏**——`z-20 > z-10` 这条修好着 |
| 导航抽屉（390） | 盒 `[0,0,293,844]`、`z-50`；`elementFromPoint(60,28)` 命中抽屉里的导航项，**不再是顶栏**；品牌行中心命中品牌行自己 |
| 筛选抽屉（390） | 盒 `[0,0,332,844]`；自己的 × `[16,44]` 中心命中 × 本身 |
| 编辑侧边栏 | 桌面 `[1180,0,420,900]`、手机 `[0,0,390,844]`；× `[16,36]` / `[16,44]` 中心命中 × 本身 |
| 遮罩 | `z-50`，盖住顶栏（不再有一条亮着的顶栏） |
