# 供应商探测

**状态：`in_progress`** · 创建 2026-09-13 · **2026-09-22 更正**：此前写 `planning` 是过期的，探测早就开工了——[`docs/fixtures/responses/`](../docs/fixtures/responses/) 里已有两份真实响应转储（2026-09-14，`api.codexzh.com` / `api.deepseek.com`）。按任务板的口径是「持续优化」类，转 `in_progress`。**「做完的标准」那 8 条一条都还没勾**，其中「至少测 3 个供应商」才走完 2 个；最重要的是第三项拒绝形态——它决定 `AI_REFUSED` 的判定怎么写，没测出来之前那段判定仍然是推测。

## 为什么

整个"模型可配置"的设计建立在一个假设上：**供应商的实际行为和文档不一致，所以必须实测**。

这个假设本身没被验证过，而且下面几件事的实现方式完全取决于实测结果：

| 探测什么 | 影响 | SPEC |
|---|---|---|
| 中转服务对 `dimensions` 参数的实际支持 | 服务端降维还是客户端截断 | [§9.13](../spec/09-decisions.md) |
| 对 `response_format: json_object` 的实际支持 | json 模式还是纯提示词兜底 | [§9.14](../spec/09-decisions.md) |
| **境内模型对擦边内容的拒绝形态** | 降级判定逻辑怎么写 | [§9.15](../spec/09-decisions.md) |
| 各视觉模型对动图的实际行为 | 抽帧方案的必要性 | [§9.16](../spec/09-decisions.md) |
| **单请求图片数上限** | 动图抽帧上限定在哪、怎么降级 | [§9.4](../spec/09-decisions.md) |

**第三项最重要。** [SPEC §2.4](../spec/02-errors.md) 说 `AI_REFUSED` 有三种形态，那三种是**推测出来的**——真实形态可能更多、也可能不是这三种。判定写错了的表现是：一张被拒的图被当成打标成功写进库，带着一组空标签，搜不到也没人知道为什么。

## 做完的标准

- [ ] 至少测 3 个供应商 / 中转服务（含一个境内受监管的）
- [ ] 每个供应商的**真实响应**脱敏后存进 `docs/fixtures/responses/`
- [ ] 拒绝形态归纳成一张表，写进本文件
- [ ] `api/src/lib/` 的拒绝判定函数用这批样本做单测
- [ ] 确认 `dimensions` 和 `json_object` 的支持情况确实参差不齐（若全都支持，测试连接的探测项可以简化）
- [ ] 确认视觉模型对动图确实只读首帧（若不是，抽帧方案要重新评估）
- [ ] **测出各供应商的单请求图片数上限**，确认 10 张是否普遍可用；记下超限时返回的错误形态（判定降级要用）
- [ ] 结论搬进 [SPEC §9](../spec/09-decisions.md)，把 §9.5 从 `proposed` 转 `accepted`

## 两端各自做什么

| 端 | 做什么 |
|---|---|
| api | 写探测脚本、归纳形态、实现判定逻辑 |
| web | **只在结论影响测试连接的展示项时参与**（比如发现某一项探测不出来，界面就不该显示它） |

## 注意

> ⚠️ **必须存真实响应，不能编。**
>
> 自己造的假响应只会覆盖自己想得到的情况。真实供应商的花样永远超出想象——「返回 markdown 代码块包裹的 JSON」这种就没人会主动去编。见 [`docs/fixtures.md`](../docs/fixtures.md)。

脱敏时注意：**个别中转服务会在错误体里回显收到的 Authorization**。存进仓库前逐个检查。

测擦边拒绝时用的图片不要进仓库。
