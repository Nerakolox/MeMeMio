# 梗名别名层

**状态：`planning`** · 创建 2026-09-13

## 为什么

用户搜的是「奶龙」「哈基米」「耄耋」，而视觉模型**说不出这些名字**——梗是社群知识，长尾、高速更新、大量晚于训练截止。

原则已定在 [SPEC §9.18](../spec/09-decisions.md)：**不让模型命名，梗名走别名层**。这个任务负责把原则变成能落地的数据形态和检索路径。

它没做之前，搜「哈基米」返回的是空，或者更糟——搜「耄耋」返回一堆老年人的图。

## 要决的三件事

**一、别名数据放哪。** 两个候选：

| 方案 | 好处 | 坏处 |
|---|---|---|
| 进 `tags[]` 的开放命名空间 | 不加表，现有三路检索直接吃到 | 和闭集词表混在一个字段里，校验逻辑要分流 |
| 独立表 `meme_aliases` | 边界干净，可加来源、热度、创建人 | 查询期要多一次 join 或预加载 |

倾向独立表——**别名是「查询词 → 描述词」的映射，和「这张图有什么标签」不是一回事**，塞进 `tags[]` 会让两种语义共用一个字段。但需要先确认查询期扩展的开销。

**二、扩展后怎么进三路。** 扩展出来的词是加进 `pg_trgm` 的 OR 条件，还是也参与向量查询？向量那路把查询从「哈基米」换成「橘猫」可能改善也可能漂移，**得测**。

**三、谁能写别名。** 按[开放编辑](../spec/09-decisions.md)的一致性，应该是所有人可写；但别名是全站生效的，一条错映射的影响面比一个错标签大得多。需要定：是否要 admin 复核、是否保留创建人。

## 第一批真实别名数据（2026-09-13）

[评测集](2026-09-13-eval-set.md)的 `humanName` 由库主人逐条填完了，**30 张里 14 张有名字，去重后 29 条别名**。这是本任务第一份不靠想象的输入，三件事里有两件可以直接往下定了。

### 它长这样

```
161 / 723 / 768  →  白圣女与黑牧师、塞西莉亚
 75 / 410        →  VRCHAT、kipfel
350              →  魔法少女的魔女审判、魔裁、夏目安安
395              →  魔法少女的魔女审判、魔裁、樱羽艾玛
118              →  GIRLS BAND CRY、闺泣、小孩姐、井芹仁菜
200              →  蔚蓝档案、BA、笑面教授、教授
458              →  本、牢本、本子魔法使
```

### 四条能直接用的结论

**一、别名不是「角色 → 描述词」，是两层。** `GIRLS BAND CRY` = `闺泣`、`蔚蓝档案` = `BA`、`魔法少女的魔女审判` = `魔裁` —— **作品名本身就有别名**。除了「角色 → 作品」，还得有「作品别名 → 作品」。上面「要决的三件事」第一条倾向的独立表要能表达这一层，`tags[]` 那个方案基本可以排除了：一个扁平字符串数组装不下两级映射。

**二、社群叫法和官方名是两类词，热度天差地别。** `小孩姐` / `牢本` / `教授` / `初音猫` 是真正会被打进搜索框的，`井芹仁菜` / `森亚露露卡` 是查得到但没人打的。别名表需要 `weight` 或 `source` 区分，否则冷启动时两类词会被同等对待。

**三、`original_filename` 这条路在这个库上是死的。** 本任务原计划让 api「`original_filename` 入 trgm」——但 QQ 导出的 `pack_info.json` 里 989 张**全部**叫 `表情_N`，人工命名过的 **0 条**。这条通路对 QQ 来源的图零收益，别指望它兜底。

**四、收益天花板是 47%。** 30 张里 **16 张库主人自己也叫不出名字**。别名层再完善也补不了这部分，它们只能靠 `description` 向量。立项收益按「47% 的图 × 名字类查询占比」算，不要按全库算。

> ⚠️ **通用词劫持是这批数据暴露的最大风险，比「耄耋」那个例子严重得多。**
>
> 填出来的别名里有 `本`、`教授`、`BA`、`猫娘`、`猫`。`本` 是单个常用汉字，`教授` 是普通名词——一旦把 `教授` 映射到《蔚蓝档案》那张图，**全站每一次正经搜「教授」都会被劫持**，而且用户不会知道发生了什么。
>
> 「耄耋 → 老年人」是别名**缺失**导致的误召回，方向是漏；这个是别名**存在**导致的误召回，方向是污染，影响面大得多，且会随着别名表变大而单调恶化。
>
> 所以「三、谁能写别名」那一条不只是权限问题，还得定**词形准入规则**。至少要有：单字别名不收；与常用词冲突的别名要么不收、要么只在同时命中其他信号时才生效。这条定不下来，别名表不能开放编辑。

### 对三件事的影响

| | 原状态 | 现在 |
|---|---|---|
| 一、数据放哪 | 两个候选，倾向独立表 | **基本定了独立表**——两级映射 + `weight`/`source` 字段，`tags[]` 装不下 |

| 三、谁能写 | 权限问题 | **加一项：词形准入规则**，见上面的通用词劫持 |

## 两端各自做什么

| 端 | 做什么 |
|---|---|
| 总管 | 定数据形态与写权限，维护初始别名 |
| api | 查询期扩展（**放 HyDE 之前**）、零结果记录、提示词约束、~~`original_filename` 入 trgm~~（见上：QQ 来源 989 张全是 `表情_N`，这条零收益，留着只对其他来源有意义） |
| web | 别名的查看与编辑入口、补标交互、搜索无结果时引导用户补一条别名 |

`web` 那条「无结果时引导补别名」是**闭环的关键**：零结果是发现缺失梗名的唯一时机，错过了就只能靠人事后想起来。

## 注意

> ⚠️ **别名扩展必须是查表，不能交给 HyDE。** HyDE 用的是用户配的模型，那个模型同样不认识哈基米。确定性扩展可解释、可修正，模型改写不是。

> ⚠️ **梗名不进 [`shared/vocab/`](../shared/vocab/README.md)。** 闭集词表存在的理由是让不同模型的输出可比；梗名是开集，每月都在长。混进去会毁掉闭集的意义，而且每加一个梗都要走一次[不兼容变更流程](../spec/04-vocabulary.md)。

这个任务**不阻塞骨架**，但它会改 `memes` 的读路径，所以要在检索实现定稿前做完。
