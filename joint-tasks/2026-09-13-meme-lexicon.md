# 梗名别名层

**状态：`planning`** · 创建 2026-09-13

## 为什么

用户搜的是「奶龙」「哈基米」「耄耋」，而视觉模型**说不出这些名字**——梗是社群知识，长尾、高速更新、大量晚于训练截止。

原则已定在 [SPEC §9.18](../spec/09-decisions.md)：**不让模型命名，梗名走别名层**。这个任务负责把原则变成能落地的数据形态和检索路径。

它没做之前，搜「哈基米」返回的是空，或者更糟——搜「耄耋」返回一堆老年人的图。

## 要决的三件事

**一、别名数据放哪。** 两个候选：

| 方案 | 好处 | 坏处 |
|---|---|---|
| 进 `tags[]` 的开放命名空间 | 不加表，现有三路检索直接吃到 | 和闭集词表混在一个字段里，校验逻辑要分流 |
| 独立表 `meme_aliases` | 边界干净，可加来源、热度、创建人 | 查询期要多一次 join 或预加载 |

倾向独立表——**别名是「查询词 → 描述词」的映射，和「这张图有什么标签」不是一回事**，塞进 `tags[]` 会让两种语义共用一个字段。但需要先确认查询期扩展的开销。

**二、扩展后怎么进三路。** 扩展出来的词是加进 `pg_trgm` 的 OR 条件，还是也参与向量查询？向量那路把查询从「哈基米」换成「橘猫」可能改善也可能漂移，**得测**。

**三、谁能写别名。** 按[开放编辑](../spec/09-decisions.md)的一致性，应该是所有人可写；但别名是全站生效的，一条错映射的影响面比一个错标签大得多。需要定：是否要 admin 复核、是否保留创建人。

## 做完的标准

- [ ] 三件事各有结论，写进 SPEC §9.18 并转 `accepted`
- [ ] 别名的数据形态定稿（表结构或字段约定）
- [ ] 零结果搜索的记录落地，**这是别名表的冷启动来源**
- [ ] 用真实梗名验证：`耄耋` 不再命中老年人的图
- [ ] 打标提示词补上「不确定不要猜 IP 名」的约束，并跑[评测集](2026-09-13-eval-set.md)确认标签污染率没变差
- [ ] `web` 的补标入口可用

## 两端各自做什么

| 端 | 做什么 |
|---|---|
| 总管 | 定数据形态与写权限，维护初始别名 |
| api | 查询期扩展（**放 HyDE 之前**）、零结果记录、提示词约束、`original_filename` 入 trgm |
| web | 别名的查看与编辑入口、补标交互、搜索无结果时引导用户补一条别名 |

`web` 那条「无结果时引导补别名」是**闭环的关键**：零结果是发现缺失梗名的唯一时机，错过了就只能靠人事后想起来。

## 注意

> ⚠️ **别名扩展必须是查表，不能交给 HyDE。** HyDE 用的是用户配的模型，那个模型同样不认识哈基米。确定性扩展可解释、可修正，模型改写不是。

> ⚠️ **梗名不进 [`shared/vocab/`](../shared/vocab/README.md)。** 闭集词表存在的理由是让不同模型的输出可比；梗名是开集，每月都在长。混进去会毁掉闭集的意义，而且每加一个梗都要走一次[不兼容变更流程](../spec/04-vocabulary.md)。

这个任务**不阻塞骨架**，但它会改 `memes` 的读路径，所以要在检索实现定稿前做完。
