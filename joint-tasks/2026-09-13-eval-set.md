## 为什么

这是本项目投入产出比最高的一件事。没有它，下面这些问题只能靠拍脑袋：

- 打标提示词改了，是变好还是变坏？
- 用户想换一个模型，那个模型够不够格？
- 词表这么设计，不同模型真的能对齐吗？
- 0.6B / 4B / 8B 三档 embedding，差距值不值那点延迟？

在模型可配置 + 库共享之后，第 2 条尤其重要：**用户配的模型会影响所有人**，而「这个模型够不够格」需要一个客观答案。

完整论证见 [`docs/eval.md`](../docs/eval.md) 与 [SPEC §9.12](../spec/09-decisions.md)。

## 选图结果

30 张选自 989 张 QQ 收藏库，清单与理由在 `manifest.json` 的 `cover` / `notes` 字段里。几张值得单独知道的：

| 图 | 为什么它不可替代 |
|---|---|
| `139` GIF | 头顶电池图标 满→空→半→满，人物几乎不动。**首帧和末帧都是满电**，只取首帧会得到相反语义；变化的是图标不是文字，OCR 也救不了。**这是抽帧方案唯一无法被其他通路替代的证据**，见 [SPEC §9.4](../spec/09-decisions.md) |
| `944` / `949` / `951` | 同一张底图配三条不同字幕，一条干净、两条擦边。画面完全相同 → **是否被拒只可能由文字触发**。这是 [§9.15](../spec/09-decisions.md) 拒绝形态探测唯一干净的样本，别浪费 |
| `161` / `723` | 同一张漫画，一张干净、一张被平铺水印盖满，dHash 距离 **1**。它们**该**判为重复——问题是保留哪张，因为水印那张的 `ocrText` 会被污染。去重保留策略需要依据，这对就是 |
| `958` GIF | 120 原始帧 → 去重 50，全集最长，采样必然触发；同时是擦边动图，**抽帧后 10 张里任一张被拒整条就失败**，降级要在多图场景下也成立 |
| `118` | 扩展名 gif 但只有一帧，必须判为静图 |
| `395` | 打乱字序的性暗示大字。`ocrText` 存乱序、用户搜正序 → **pg_trgm 那一路必然落空**，三路混合在这张上只剩两路。同时是拒绝形态的第二根轴：测模型解不解得开乱序 |

选图没有靠肉眼找相似——**全库 pHash 两两比对后按 Hamming 升序看**，989 张里 ≤8 的有 40 对，上面几组都是这么翻出来的，人工翻不到。

## 两端各自做什么

| 端 | 做什么 |
|---|---|
| 总管 | 选图、标注、维护 `manifest.json` |
| api | 写 `scripts/eval.ts`，输出指标（详见下方） |
| web | **不参与**，这个任务不碰前端 |

### api 端：`scripts/eval.ts` 规格

**运行方式：** `tsx --env-file=../.env scripts/eval.ts`

**供应商配置：** 优先读 `EVAL_VISION_BASE_URL` / `EVAL_VISION_API_KEY` / `EVAL_VISION_MODEL`，回退到 `DEFAULT_VISION_*`。这样可以不动主配置单独测一个供应商。不要 import `src/env.ts`（它会触发全量 env 校验；脚本只需要 vision 三件套）。

**协议选择：** `EVAL_VISION_PROTOCOL` 控制请求格式，三选一，默认 `openai`：

- `openai`（默认）：`POST {BASE_URL}/v1/chat/completions`，鉴权 `Authorization: Bearer <key>`，body 用 `messages` 数组，图片以 `image_url` 类型传入，响应取 `choices[0].message.content`。兼容 DeepSeek / Kimi / 智谱 / 硅基流动 / vLLM / Ollama 等绝大多数兼容网关。
- `openai-responses`：`POST {BASE_URL}/v1/responses`，鉴权同上，body 用 `input` 数组（OpenAI Responses API 格式），响应取 `output[0].content[0].text`。
- `anthropic`：`POST {BASE_URL}/v1/messages`，鉴权 `x-api-key: <key>` + `anthropic-version: 2023-06-01`，`system` 单独字段，图片以 `{ type: "image", source: { type: "base64", media_type, data } }` 传入，响应取 `content[0].text`。Claude 原生及兼容此格式的网关。

脱敏写 responses 文件时，`x-api-key` header 同样替换为 `[REDACTED]`。汇总输出里在供应商那行旁边加一行"协议: openai / openai-responses / anthropic"。

**输入：**
- `docs/fixtures/eval/manifest.json`（路径相对仓库根目录，用 `process.cwd()` + `../` 解析，和 `src/paths.ts` 的惯例一致）
- `shared/vocab/vocab.json`
- `docs/fixtures/eval/images/` 下的实际图片文件（图片不进仓库，本地跑时才有；文件缺失则该条 `status: skipped`，不报错退出）

**第一阶段只输出四项指标，不需要数据库：**

1. **JSON 有效性** —— 模型返回的内容能否被 `JSON.parse` 解析，且包含 `description` / `emotions` / `scenes` / `tags` 四个字段
2. **词表合规率** —— `emotions` / `scenes` / `tags.subject` / `tags.style` 里的每个词是否全部在 `vocab.json` 对应集合内；违规词逐条记录
3. **拒绝形态** —— 被拒时归类为以下三种之一并记录原始响应（脱敏后）：
   - `http_error`：HTTP 状态码 ≥ 400
   - `refusal_text`：200 但正文是拒绝措辞（不可解析为 JSON，或解析后字段为空且含拒绝词）
   - `empty_fields`：200 且 JSON 合法，但 `emotions` / `scenes` 同时为空数组
4. **humanName 污染** —— `description` 字段里是否出现了 `manifest.json` 中 `humanName` 数组的任意词条（表示模型在没有被要求的情况下自行编了角色名）

**`acceptAlso` 语义必须实现：** 合规率计算时，`acceptAlso` 里的词既不算命中也不算污染，从分母里剔除。漏了这条会把 `698` 算成假污染。

**多目标 humanName：** `塞西莉亚` 对应 `161` / `723` / `768` 三张，污染检测要对全集做，不是一对一。

**输出：**
- 跑完后打印汇总到 stdout（每项指标的通过率 + 失败清单）
- 同时把每条的原始结果写到 `docs/fixtures/responses/<供应商名>-<日期>.json`（脱敏：把 Authorization header 里的 key 替换为 `[REDACTED]`）；供应商名从 `EVAL_VISION_BASE_URL` 的域名部分提取

**recall@5 不在这里。** 那一半等检索实现完成后再补，不要等它一起写。

**不引入新依赖。** `node:fs`、`node:path`、原生 `fetch` 足够；图片转 base64 用 `readFileSync` + `Buffer.toString('base64')`。

严格说这不是跨端任务，放这里是因为**它阻塞的东西横跨两端**（词表转 `accepted` 之前，`web` 的筛选 UI 不该对具体词条做假设）。

## 标注由谁来定

草稿可以由 AI 起草，但**基准值必须由人逐条改过**。

「期望搜到这张图的 query 是什么」「这张图算不算阴阳怪气」没有客观答案，只有**这个库的实际使用者**的答案。如果标注是 AI 写、人扫一眼点头，那评测集衡量的就是 AI 的先验和 AI 自己是否一致——分数会很好看，且毫无意义。

**扫一眼就通过 = 没有基准。** 至少要真改掉一部分，才说明看过。

## 这个任务会顺带暴露的四件事

发现于 2026-09-13 翻库、起草标注与第一批校对时，**不在本任务的验收标准里，但必须记下来别丢**：

1. **`tags.subject` 已经实测失效，不是推测。** 选出的 30 张里 `subject` 全部是「动漫角色」——**30/30**，`style` 是「动漫」的 25/30。标签过滤那一路在这个库上没有区分度，三路混合实际退化成两路，这动摇的是 [SPEC §9.10](../spec/09-decisions.md) 的前提。交给[词表任务](2026-09-13-vocab-v1.md)决定 `subject` 是否重新设计。
   > 但 `无文字` / `带字幕` 这一对有信号（15 / 9），它直接指明该走哪条检索通路。精简词表时不要连它一起砍。
2. **[§9.18](../spec/09-decisions.md) 的别名层是主路径，但收益有个明确天花板。** 库主人填完 `humanName`：**14/30 有名字（29 条去重别名），16/30 本人也叫不出**。有名字的那些（`塞西莉亚` `kipfel` `井芹仁菜` `樱羽艾玛`）视觉模型一个都说不出来，别名层确实是唯一通路；但认不出的那 16 张，别名层再完善也补不了，只能靠 `description` 向量。**收益按 47% 的图算，不是全库。** 数据和三条实现结论已交给[梗名别名层任务](2026-09-13-meme-lexicon.md)，其中「通用词劫持」（`本` `教授` `BA` 都被填成了别名）是比原计划的「耄耋」问题严重得多的风险。
3. **`emotions` 和 `scenes` 的边界不自明。** 起草这 30 条标注时，对着词表仍然把 `讨好` `看戏` `撒娇` `心虚` 填进了 `scenes` **共 10 处**，靠脚本校验才抓出来。起草者对着词表都会错，模型只会错得更多——这不是手滑，是词表设计问题。交给[词表任务](2026-09-13-vocab-v1.md)。
4. **文本通路会在真实输入上整条失效，`395` 是第一个实证。** 图上写的是打乱字序的句子，`ocrText` 只能照抄乱序（替用户「修正」成正序就是在编造图上没有的字），而用户搜的是正序——pg_trgm 匹配不上，[§9.10](../spec/09-decisions.md) 的三路在这张上只剩两路。同一张图还证明了：模型把乱序**强行解释成一个通顺但错误的意思**是最难发现的污染形态，因为结果读起来完全正常（起草者就是这么错的）。交给 api 端写打标提示词时明确：宁可照抄不解释。
