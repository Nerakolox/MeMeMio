# 词表 v1

**状态：`planning`** · 创建 2026-09-13

## 为什么

`shared/vocab/vocab.json` 现在是 **v0.1.0 / `proposed`**——一份能用的起草版本，但**没经过任何验证**。

它必须转 `accepted`，因为三处代码同时消费它：打标提示词、输出校验、前端筛选 UI。词条不定下来，这三处都只能写成"先这样"。

词表是打标质量的地基，而[打标质量是这个项目的命门](../docs/README.md)。

## 现在这版有什么问题

起草时能想到的、需要验证的：

1. **`scenes` 可能太细也可能太粗。** 粒度标准是「我现在想干什么」，但「加班」「下班」「上班摸鱼」这三个是不是应该合并，只有看真实数据才知道
2. **`aliases` 是猜的。** 哪些同义词真的会被模型吐出来，得看实际输出
3. **`tags.subject` 里的类别词**（动漫角色、明星、游戏角色）粒度对不对——它们是**类别**不是具体 IP，这点已由 [SPEC §9.18](../spec/09-decisions.md) 定死：**具体梗名永远不进闭集词表**，走[别名层](2026-09-13-meme-lexicon.md)。这里要验的只是类别本身模型分不分得清
4. **每个维度 1–4 个**这个数量约束没验证过，可能太松
5. **同一个词会不会同时落在两个维度**（比如「摆烂」既像情绪又像场景），这会让模型犹豫

## 做完的标准

- [ ] 用[评测集](2026-09-13-eval-set.md)的 30 张图跑至少 2 个模型，统计词表合规率
- [ ] 统计模型实际输出里**不在词表内**的高频词，决定收编还是登记为 alias
- [ ] 检查没有词条同时出现在两个维度
- [ ] 检查 `aliases` 的键没有出现在三个维度的词条列表里（会造成归一化死循环）
- [ ] 删掉验证下来没人用的词条——**词表越短，模型选得越准**
- [ ] bump 到 `1.0.0`，`status` 改 `accepted`
- [ ] 更新 [`shared/vocab/README.md`](../shared/vocab/README.md) 的状态段落

## 两端各自做什么

| 端 | 做什么 |
|---|---|
| 总管 | 改 `vocab.json`，主持词条取舍 |
| api | 校验逻辑（含 alias 归一化）、提示词里的清单拼接 |
| web | 筛选 UI 分区展示、标签编辑控件的选项源 |

**这是真正的跨端任务**：词条变了两端同时坏，而且坏法不同——`api` 是校验失败，`web` 是筛选项对不上。

## 注意

> ⚠️ **词表变更默认按不兼容处理。** 删除或重命名一个词条会让已有记录的该标签**失去意义，但不报错**。见 [SPEC §4.4](../spec/04-vocabulary.md)。

现在库里还没有数据，**所以现在是改词表成本最低的时刻**。一旦开始导入真实数据，每次删词都要带数据迁移。

`tags` 在 JSON 里按 `subject` / `style` 分组，**存库时是扁平的**。改结构时不要把分组带进数据库。

**改完必须跑评测集。**
