# 骨架搭建

**状态：`planning`** · 创建 2026-09-13

## 为什么

现在项目只有文档，一行代码都没有。

骨架的价值不在"先跑起来"，在于**把几个只能在工程层面定下来的东西定下来**：两个工作区怎么共享类型、`shared/vocab/` 两端怎么读、本地开发怎么起、构建产物怎么进一个镜像。这几件事定错了，后面每个功能都要绕着它写。

**它不依赖前三项任务。** 骨架不碰具体词条、不碰供应商行为、不碰打标质量。

## 做完的标准

- [ ] `api/` 起得来，`GET /api/v1/health` 返回 200
- [ ] `web/` 起得来，Vite 代理到 `api`，同域无 CORS 配置
- [ ] `web` 通过 Hono RPC 消费 `api` 导出的类型，**改一个字段名 `web` 侧编译报错**
- [ ] 两端都能读到 `shared/vocab/vocab.json`
- [ ] `docker compose up -d db` 起 Postgres，pgvector 与 pg_trgm 扩展可用
- [ ] 首个 migration 建表，可重复执行
- [ ] 启动时校验环境变量，缺 `CONFIG_ENC_KEY` 直接退出并说清楚缺了什么
- [ ] 错误中间件在位，返回 `{ code, message, requestId }`
- [ ] 三阶段 Dockerfile 能构建出单镜像，`api` 托管 `web` 的产物
- [ ] 测试跑得起来，且**连的是真 Postgres**

## 两端各自做什么

| 端 | 做什么 |
|---|---|
| api | 工程配置、migration、错误中间件、env 校验、Dockerfile、compose |
| web | Vite 配置与代理、路由骨架、`api.ts` 单一出口 |

放在跨端任务里，是因为**类型链路和 vocab 读取这两件事只有两端一起做才验证得了**。一端单独"做完了"证明不了任何事。

## 先落地的验证点

这几条不是功能，是**用来证明约束确实生效**的：

1. **改 `api` 的一个字段名，`web` 必须编译失败。**证明类型链路真的通了，而不是两边各写一份长得像的类型
2. **删掉 `CONFIG_ENC_KEY`，进程必须退出**，不能带着空 key 起来
3. **migration 没跑就启动，必须报错**而不是自动跑——生产环境自动跑 migration 是事故来源
4. **一条软删记录，默认查询必须查不到**

第 1 和第 4 条建议直接写成测试留在仓库里。

## 注意

> ⚠️ **不要在 `proposed` 的具体词条上做硬编码分支。** 词表还在 [词表 v1](2026-09-13-vocab-v1.md) 里改，代码只能把它当数据读，不能 `if (emotion === '无语')`。

同理，不要提前写死任何供应商的行为判断——那些结论要等[供应商探测](2026-09-13-provider-spikes.md)。

**`lib/` 里不要出现 `utils.ts`。** 从第一天起就按职责命名，这个文件一旦存在就再也清不掉。

镜像用 `bookworm-slim` 不用 Alpine，理由见 [`docs/deployment.md`](../docs/deployment.md)——sharp 在 musl 上的坑不值得踩。
