## 为什么要做

用户 2026-09-22 给的那个例子就是全部理由：

> 比如一张微笑角色配「你说得都对」的图，视觉事实可能是微笑，交流用途却可能是敷衍、反讽。
> 把它标成「开心、赞同」

v0.1.0 只有 `emotions` / `scenes` 两个语义维度，这张图**没有一种标法是对的**：

- 标「开心」——脸确实在笑，但发这张图的人一点也不开心，搜「敷衍」搜不到它；
- 标「敷衍」——`emotions` 里塞了一个不是情绪的词，于是「图里的人在感受什么」这一维从此不可信；
- 两个都标——`emotions` 同时装着互相矛盾的两个值，排序时它们还会各贡献一次命中。

问题不在词条不够，在**维度不够**：脸上是什么（视觉事实）、心里是什么（情绪）、话怎么说（语气）、
发它要干什么（交流用途）是四件**互相推导不出来**的事。挤在一维里，模型只能挑一件，
而它挑的通常是最表面那件（脸）。

同一批讨论里定下的第二件事：

> 其次这里定了，RAG SEARCH 也有点问题

检索确实有五处缺陷，其中三处**不报错**，见下面的「顺带修掉的五个检索缺陷」。

### 明确不做的

**不做动漫 / 角色识别**——用户原话：「算了这样成本太高，就先各种 维度+场景语义识别吧」。
本任务只拆语义维度，不引入任何需要外部知识库或角色库的能力。

## 已定的裁定（用户逐条选过）

1. **维度落库方式**：新增 4 列（`expressions` / `tones` / `purposes`，加上 `scenes` 语义收窄），
   `scenes` 从「什么都往里塞」收窄为**生活情境**（加班、考试、过年……）。
   不选「一列 JSONB 装五维」——那样每个维度的 GIN 索引和 `@>` 过滤都要重写成 JSON 路径，
   而六个维度是**同构**的，同构的东西用同构的列表达。
2. **混模型向量的修法**：**向量路按 `embed_model` 过滤**（SPEC §9.20），不选「换模型时整路停摆」。
3. **执行范围**：**全做，包括迁移和 web 筛选 UI**。

## 顺带修掉的五个检索缺陷

前三个是这次读代码时发现的，后两个是拆维度直接带出来的。**标 ⚠️ 的三个不报错**，
它们的表现都是「搜索悄悄变差」：

| # | 缺陷 | 表现 |
|---|---|---|
| ① | HyDE 改写**替代**了原查询去做向量检索 | ⚠️ 改写最爱丢否定和语气：「不要真人」被改成「一个真人在摆手」，向量路召回一整屏用户明说不要的图。改成编码「原查询 + 改写」，原查询在前（截断在尾部） |
| ② | 中文查询命中率偏低 | 文本路与 `original_filename` 的匹配口径 |
| ③ | 文本路把 `search_text` 也拿去做 trgm 匹配 | ⚠️ `search_text` 里拼着标签值，同一个信号被文本路和标签路**各计一次分**，靠标签沾边的图压过原文精确命中的图。文本路改为只匹配 `ocr_text + description`，`original_filename` 单独匹配（SPEC §9.21） |
| ④ | 换 embedding 模型期间库里有两代向量 | ⚠️ 两代向量不在同一个空间，余弦距离只是噪声。按 `embed_model` 过滤，并**必须同时置 `degraded: true`**（SPEC §9.20）——否则召回变少而界面上毫无痕迹 |
| ⑤ | 重建索引任务失败后没有出路 | 失败的 job 卡住，旧模型的向量永远留在库里，④ 的状态变成永久 |

### 维度标签用 SPEC 全称，不用简称

分区标题是「面部表情 / 情绪 / 表达语气 / 聊天用途 / 生活情境 / 标签」，不是「表情 / 情绪 / 语气 / 用途 / 情境」。
口语里「语气」「情绪」「表情」几乎是同一个意思，而**分区标题是用户唯一能看到的判据**——
他要靠它决定「敷衍」该勾在哪一栏。简称省下的那两个字不值这个代价。

### 筛选面板从「平铺」改成「折叠分区」

190 个 chip 平铺在 220px 的筛选列里是 2000px 以上，而产品负责人已经为这一列的尺寸抱怨过两次
（「所有的标签、按钮都太大了，浏览页的筛选板块是最佳实例」）。折叠的代价是**可发现性**——
收起时看不见里面有哪些词。三处补偿：
标题用全称（上一节）；收起时标题旁有**计数徽标**（能看出这一维有没有条件在生效）；
**已经有值的维度默认展开**（分享出去的筛选链接打开就是展开的那几维）。

`defaultValue` 只在挂载时算一次是对的：两个调用点在身份变化时都会重挂
（编辑面板按 `key={meme.id}`，筛选面板随路由），所以不存在「换了一张图但分区停在上一张的展开状态」。

### ⚠️「浏览器没开过」当场就咬了一口：编辑面板「描述以下全空白」（2026-09-22，用户报障）

用户报：`/browse` 点「编辑」，**描述以下什么都看不见**。真缺陷，已修。

**根因不是词表，是 `overflow-hidden` 遇上定高 flex 列。** `MemeEditPanel` 的 body 是
`flex min-h-0 flex-1 flex-col overflow-y-auto`——高度确定。flex 子项默认 `flex-shrink: 1`，
所以内容比它高时子项被压缩而不是溢出滚动；其余子项缩不动（`min-height: auto` 等于内容高），
而**带 `overflow-hidden` 的子项自动最小尺寸是 0**，于是全部负空间落在它身上。六个词表维度
那一块换成注册表 `Accordion` 之后正好自带 `overflow-hidden`（`overflow-hidden rounded-2xl border`），
于是被压成 **2px**——只剩边框，内容全剪掉，**不报错、不告警**。

修法在**容器**上，不加在子组件上：body 加 `[&>*]:shrink-0`。理由是这样一来往后往这个面板里
塞任何带 `overflow-hidden` 的注册表组件（`Card` 也是）都不用再想一遍。

**实测**（真 Chrome `--headless=new`，1440×900，链接 `web/dist` 里那份**真编译产物**
`index-HjtQL1ZT.css`，DOM 结构与面板逐类同构；不是量真页面）：

| 面板 body 的类 | accordion 高 | 自身内容 | 可见 | body |
|---|---|---|---|---|
| `…overflow-y-auto overscroll-contain px-6 py-4 outline-none`（修复前） | **2.0px** | 329 | 1% | 774px，可滚 |
| 上面那些 + `[&>*]:shrink-0`（修复后） | **331.0px** | 329 | 100% | 774px，可滚 |

`[&>*]:shrink-0` 确实进了产物：`web/dist` 里有 `.\[\&\>\*\]\:shrink-0>*{flex-shrink:0}`。

**这条仍然不算「在 /browse 上验过」**——执行这次修复的会话没有登录态，量的是同构 DOM，
真页面要用户刷新后确认。上面那张清单（六维勾选、默认展开、徽标、抽屉滚动、PATCH 只发改动维）
一条都没少。

本仓没有常驻 e2e（`joint-tasks/README.md` 的「已知缺口」最后一条），所以「浏览器实测」
意味着再写一次一次性 CDP 脚本。下一次为别的事起浏览器时至少要覆盖：

- 六个分区各勾一个词 → URL 上六个参数都在，请求带齐六个
- 带 `?tones=敷衍&purposes=表面附和` 进页 → 这两维默认展开、其余收起
- 收起状态下计数徽标的数字等于该维已选数量
- 手机抽屉里展开两三个维度后仍然滚得动（标题常驻不跟着滚）
- 编辑面板改一个新维度 → `PATCH` 的 body 里**只有**改动的那一维

一旦对有数据的库跑过 `0006`，这三个词的存量值就找不回来了。

### 2. 筛选面板折叠分区，你接受吗？

190 个 chip 平铺在 220px 那列里是 2000px 以上，而你为这列的尺寸抱怨过两次
（「所有的标签、按钮都太大了，浏览页的筛选板块是最佳实例」）。所以我改成了可折叠分区。

代价是**可发现性**——收起时看不见里面有哪些词。补偿了三处（全称标题 / 计数徽标 / 有值的维度默认展开），
但**我没在浏览器里看过实际密度**，所以这条是纸面推理，不是实测结论。
不接受的话，退路是「平铺但每维只显示前 N 个 + 展开更多」。

### 3. 评测集要不要在合入前补？

`api/AGENTS.md §5` 要求动了词表 / 提示词 / 检索就说明跑没跑。**没跑**，而且现在跑是反效果
（见上面那节）。真要跑，前置是「迁标注 + 把 30 张图捞回来」，是评测集任务的工作量，不是本任务的。

我的判断是**先合入，评测集另开一轮**——五个检索缺陷里有三个是静默劣化，压着不合入的成本更高。
但这是你的取舍。

### 不跟着走的三样

| 东西 | 怎么办 |
|---|---|
| `.env` | 被 `.gitignore` 排除。照 `.env.example` 重建。⚠️ **`CONFIG_ENC_KEY` 换了，数据库里已加密的用户 API Key 就永久解不开**——本机库是空的所以无所谓，但如果新设备要接旧数据，必须把同一个 key 带过去 |
| Postgres 的数据卷 | Docker 卷不跨机器。新设备起一个新库、跑迁移即可——**本机开发库 `memes` 是 0 行，没有数据要搬** |
| `docs/fixtures/eval/images/` | 本来就不进仓库（含擦边内容），而且**本机这个目录也是空的**。要跑评测集得先从 R2 私有前缀捞回来 |

### 新设备从零到能跑

```sh
git pull
cp .env.example .env     # 然后把值填上（见 docs/environments.md §1）

# Node 必须 ≥ 20.12，本轮用的 22.23.0。nvm 用户注意默认版本
node -v

docker compose -f compose.yaml -f compose.dev.yaml up -d db
cd api && npm ci && npm run migrate
cd ../web && npm ci

# 闸门
cd ../api && npm test && npm run typecheck
cd ../web && npm run typecheck && npm run build
```

⚠️ **`npm test` 建不出 `_test` 库时**看 `docs/environments.md` §3.1——本机撞到的是
collation 版本错配，那是**这台机器的卷**的问题，新设备上全新的卷大概率不会复现。
