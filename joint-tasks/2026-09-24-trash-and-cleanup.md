# 回收站、查重与定时清理

**状态**：`planning` ｜ **性质**：**跨端** ｜ 开于 2026-09-24

## 1. 为什么要做

**删除只进不出** ✔。SPEC §6.4 写了 `POST /memes/{id}/restore` 和 `GET /memes/duplicates`，但 `api/src/routes/` 里两个都没有，web 也没有「已删除」入口。删错一张图，用户自己找不回来。§3.4 预留的「admin 已删除视图」（`includeDeleted` 方法）同样没有实现。

**清理任务一个都没做。** `api/agents/rules/queue.md §6` 列了五个定时任务，全仓库没有任何调度。后果：软删的图永远不会物理删除，配额也就不会释放（§3.6）；失败或超限留下的 `temp/` 孤儿对象越积越多；7 天未处理的 `needs_review` 也不清。[导入加固](2026-09-24-import-hardening.md)修掉的竞态和失败分支，此前留下的孤儿同样要靠它来收。

**「重传一张删过的图」没有定义。** `findMemeByContentHash` 有意包含软删记录，于是：①返回已删记录的 `memeId`，违反 §2.2「不暴露曾经有过」；②「仍然导入」那条路径会谎报 `imported`；③内容哈希有唯一约束，删过的图在物理删除之前（而现在物理删除永远不发生），**再也导不进来**。

## 2. 待定的契约问题（`planning` 的原因）

1. **重传删过的图算什么？** 候选：
   - ①上传者本人重传 = 恢复原记录；别人重传 = 新图（先清掉旧记录的哈希占用）；
   - ②一律按新图处理，旧记录的哈希在软删时就改成墓碑值；
   - ③一律 `exact_dup`，但不带 `memeId`。

   **总管倾向①**：它最接近用户直觉。代价是恢复路径和导入路径要共用一套逻辑。
2. **restore 的可见范围**：上传者只能看到自己删掉的，admin 看全部？这决定 web 回收站是放在设置页，还是作为浏览页的一个筛选。
3. **物理删除与外键**：`import_items.similar_to` / `meme_id`、`user_favorites.meme_id`、`tag_jobs` 的外键都是 `ON DELETE no action`，物理删除会被挡住。要改成 cascade / set null，需要迁移。
4. **`GET /memes/duplicates`（主动查重，异步任务）** 是否本轮一起做，还是继续留在已知缺口里。

以上定下来之后写进 SPEC §6.4 / §3.4 / §9，转 `accepted`，再开工。

## 3. 定下来后两端各改什么（草案）

- **api**：restore 端点（过 `assertCanMutate(…, 'delete')`）；`includeDeleted` 读方法；五个定时任务（先记日志再删，能 dry-run，见 `queue.md §6`）；外键迁移；导入命中软删记录时按裁定处理。
- **web**：「已删除」视图 + 恢复按钮；删除成功的提示里给一个「撤销」入口。
