# 近似重复自动判定：距离 0 直接判重，其余问视觉模型

**状态**：`done`（2026-10-01）。2026-09-29 契约写成 `proposed`（[SPEC §9.33](../spec/09-decisions.md)），api、web 两端已各自回填；**§6 的联合真链路验收由产品负责人本人 2026-10-01 亲测通过**，见文末「产品负责人验收」。
**性质**：跨端。api 是主体；web 只有两小处，**不阻塞 api 先合入**（见 §5 顺序）。

## 1. 为什么要做

产品负责人一次导入 500 多张，待确认队列里**绝大多数是 Hamming 距离 0**。[§9.7](../spec/09-decisions.md) 当年的判断是「近似重复交给人」，前提是命中量小、人能逐条看；500 条全是距离 0 的时候，「让人看一眼」退化成了 500 次点「跳过」。

要解决的是**新导入**不再产生这堆条目，以及**已经在队列里的**能省力地清掉。

## 2. 已定的方向（产品负责人 2026-09-29）

| 问题 | 裁定 |
|---|---|
| 距离 0 | 直接判重复，不问任何人 |
| 距离 1…`NEAR_DUP_DISTANCE`（现为 8） | 交给「打标配置的 LLM」判定 |

总管在此之上补的三处（**产品负责人没说、我按 [§9.7](../spec/09-decisions.md) 的不对称原则定的，不同意就在这里改**）：

1. 视觉模型答**三态** `same` / `different` / `unsure`，不是二选一。`unsure`、调用失败、超时、输出不合法、没配视觉通道 → 回落到原来的待确认队列。**模型出问题既不让条目 `failed`，也不默默入库。**
2. 自动判重的条目**留痕**（`meme_id` / `distance` / `reason`），因为这一支删暂存对象、不可撤销。
3. **不加开关**。理由与推翻条件都在 §9.33。

## 3. 做完的标准

1. 新导入一张与库里某张距离 0 的图：条目 `exact_dup`、不调任何 AI、不写 `memes`、暂存对象被删，`distance` 与 `reason` 有值。
2. 距离 1–8：调一次视觉通道（上传者本人的，与打标同一解析），两张图各以 **PNG** 送出；`same` → 同 1；`different` → 正常入库打标；其余五种情形 → `needs_review`，与今天逐字一致。
3. 距离超过阈值：行为不变。
4. 视觉调用**有超时**，且超时不会让整批停下；一批里既有距离 0 又有需要问模型的，互不影响。
5. `exact_dup` 的下游都还成立：批次快照 `skipped` 计数、SSE `item` / `done`、web 进度页。**字段形状不变**。
6. 存量待确认队列里的条目**原样还在**，能照旧「仍然导入」/「跳过」。

## 4. 存量：那 500 多条怎么办

本任务的自动判定只作用于新导入。存量条目有两条路，**这里只落地第一条**：

- **（做）web 队列页「距离为 0 的全部跳过」**：用户主动点，前端逐条调**已有的** `POST /imports/reviews/{batchId}/{fileName}`（`action: "skip"`），**不需要新接口、不动契约**。这是人在做决定，不违反 [§9.7](../spec/09-decisions.md)。
- **（不做，待裁定）对存量条目重跑「距离 1–8 问视觉模型」**：需要一个新的批量接口 + 进度呈现，几百次视觉调用花的是用户的额度，要先问。**做不做由产品负责人定**，要做的话另开任务，别塞进这一张。

## 5. 各端要改什么

**顺序**：api 先合入不会让 web 坏（`result` 取值与字段形状不变，web 只是把一部分本来会进队列的图算成「跳过」）；web 两处随后补。所以**没有硬阻塞**。

### api 端

- `services/import.ts` ⑤ 处：`findNearestByPhash` 之后按 §9.33 三档分流。**仍在「配额之前、入库之前」**，与今天 `needs_review` 同一位置。
- 视觉判重的调用：走 `resolveVisionConfig(uploaderId)`（`ai/vision.ts`），复用打标的超时 / 输出校验 / 降级套路（`ai-providers.md §3`，输出不可信、必须校验）。**新写一份判重提示词与输出解析**，别复用打标的词表校验。要求：只要有任何可见差异（文字、表情、构图、局部）就不是 `same`，拿不准 `unsure`；输出严格 JSON，含 `verdict` 与一句 `reason`。
- 两张图的取法：静图直接转 PNG；动图取代表帧（沿用 `image-pipeline.md` 的抽帧，**一律 PNG，不送 GIF**）。库里那张从 R2 按 `storage_key` 取，**不走 `memes` 之外的读路径绕软删**——命中时它已经被 `findNearestByPhash` 过滤过。
- 留痕：`recordItemOutcome` 对自动判重写 `memeId`（被比中的那张）、`distance`、`reason`。
- `image/constants.ts` 里 `NEAR_DUP_DISTANCE` 的注释「只攒队列，不做任何自动处理」**作废，必须改**——它现在是错的。`import.ts` 顶部注释的管线顺序同理。
- **顺带修一处与 SPEC 不一致的读路径**：`data/imports.ts` 的 `listReviewQueue` 用 `innerJoin(memes) … isNull(memes.deletedAt)`，被比中的那张一旦软删，**整条待确认条目从队列里消失**，而 [SPEC §6.2.3](../spec/06-endpoints.md) 明确要求「不删除条目、`existing` 返回 `null`」。改成 `leftJoin`，让条目留下、`existing` 为 `null`（软删过滤仍要在 join 条件里，不能漏）。这一条**独立于自动判重**，但同一个文件，一起做；它是用户问「待确认的图还在不在」时唯一会丢的路径。
- 测试：`tests/phash-near-dup.test.ts` 等现有近似重复用例的期望要跟着改；新增距离 0、`same`、`different`、`unsure`、调用失败、没配通道各一条。**视觉上游用替身，说明白它是替身**（`testing.md`）。
- 跑 `cd web && npm run typecheck`（闸门）与 `npx vitest run`。

### web 端

- 进度页文案：`ImportProgress.tsx` 里「跳过 N 张**完全相同的文件**」不再准确（现在也包括画面相同的），改成不夸大的说法，如「跳过 N 张库里已有的图」。条目行的 `reason` 若能显示，一并显示，用户要能看见「为什么没进库」。
- 队列页：加「距离为 0 的全部跳过」（§4 第一条）。**要有二次确认，并写明这一步删的是暂存文件、不可撤销**；逐条调已有接口，中途失败不清空已成功的，如实报「跳过了 X / 失败了 Y」。**不改后端契约。**
- 做完在 `web/README.md` 或相应规则里若提到「近似命中一律进队列」的地方同步。

## 6. 验收

- 联合验收要**真链路**：造三张图——原图、重新编码的同图（应距离 0）、同模板换字的图（应距离小但非 0，观察模型怎么答）。**换字那张的结果就是 §9.33「什么情况下推翻」第 1、2 条的第一份实测**，不管模型答什么都要记下来。
- 没配视觉通道的账号导一张距离 1–8 的：必须落回 `needs_review`。
- 没跑的项不要写成跑过了。视觉上游若全程是替身，说明「模型的真实判断质量没量过」。

## 7. 已知风险与欠账（写在这里，别指望有人记得）

- **距离 0 ≠ 字面同一张。** 同一模板换了字，低频上可能距离恰为 0，会被静默丢掉。这是产品负责人明知的取舍，§9.33 已写；推翻条件是「出现一次以上」。
- 判重的**质量没有评测集**。`docs/eval.md` 里没有近似重复这一组；要量就得建，不阻塞本任务（[§9.27](../spec/09-decisions.md)：边用边迭代）。
- 与[回收站、查重与定时清理](2026-09-24-trash-and-cleanup.md)的关系：那张任务里「7 天未处理的 `needs_review` 清理」目前**一个定时任务都没有**，所以待确认条目现在实际上**永不过期**。本任务不动它；但那张任务开工时要知道，自动判重之后队列里剩下的是「模型拿不准」的那部分，清理策略的前提变了。

## 8. api 端验收

**api 端做完（2026-09-29）。没动 SPEC、没加字段 / 接口 / 错误码、没碰 `web/`。** 视觉上游在所有测试里都是替身，**模型的真实判断质量没量过**。

改了什么：

- `services/import.ts` 步骤 ⑤，仍在配额与入库之前，三档分流：
  - 距离 0 → `exact_dup`，不调 AI、不写 `memes`、删暂存对象；`memeId` / `distance` / `reason`（「画面完全相同（距离 0）」）留痕。
  - 距离 1…`NEAR_DUP_DISTANCE`（8）→ 问**上传者本人**的视觉通道（`resolveVisionConfig(userId)`），两张图都以 PNG 送出。`same` → `exact_dup` 留痕（`reason` 含模型的理由）并删暂存对象；`different` → 走原有配额 / 入库 / 打标；`unsure`、没配通道、取图或抽帧出错、调用失败、超时、输出不合规、输出被截断 → `needs_review`，与此前逐字一致（`similarTo` / `distance` / 「库里已有一张相近的图（距离 N）」，temp 保留）。整个判定包在 try/catch 里，模型这一环出任何问题都不会让条目 `failed`，也不会默默入库。
  - 超过阈值：不变。
- 新增 `ai/dup-judge.ts`：判重专用提示词（有任何可见差异就不是 `same`、拿不准 `unsure`）与请求。超时 `min(AI_TIMEOUT_MS, 12s)`；只有配置里 `jsonModeWorks === true` 才带 `response_format`；永不抛；日志只记状态 / 失败类别 / 模型名，不记响应正文。
- 新增 `lib/dup-verdict.ts`：纯函数解析 `{verdict, reason}`。`verdict` 只认 `same` / `different` / `unsure` 三个字面值，`reason` 折叠空白并限 200 字，`finish_reason: length` 一律不信。**没有复用打标的提示词或词表校验。**
- 动图：新图与库里那张各取**中间帧**再转 PNG。
- `data/imports.ts` `listReviewQueue`：`innerJoin` + `where isNull(deletedAt)` 改成 `leftJoin`，软删条件放在 ON 里；被比中的那张已软删时条目留在队列、`existing` 为 `null`（[§6.2.3](../spec/06-endpoints.md)）。`ReviewQueueEntry.existing*` 相应可空，`routes/imports.ts` 的 `/reviews` 对 `null` 直接给 `existing: null`。
- 注释：`image/constants.ts` 的 `NEAR_DUP_DISTANCE`（作废「不做任何自动处理」）与 `services/import.ts` 顶部管线顺序已更正。
- SSE `item` 本来就把 `reason` / `memeId` 原样带出，所以 `exact_dup` 的依据会直接到 web 进度页，字段形状没变。
