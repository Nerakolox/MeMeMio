## 1. 为什么要做

产品负责人要 Apple 相册那样的体验：库里的图按「是谁」自动归组，用户只负责给组起名，之后能按人物筛、能用名字搜。

这**部分推翻** [SPEC §9.22](../spec/09-decisions.md) 里「放弃动漫 / 影视角色识别」一条。当时放弃的理由是要预置角色库、要持续更新、要额外的检索调用；这次的做法不需要角色库——**先聚类、后由人命名**，模型不必认识任何角色。所以只推翻「不做」，不推翻它的理由。两者的关系已写进 [SPEC §9.34](../spec/09-decisions.md)。

2026-09-29 追加：人物之上还要一层**系列**（通常是一部作品），由人挑人物组成。它和七个词表维度、收藏、上传者一样是浏览的筛选维度，但它是开集，不进词表。

## 2. 已定的（产品负责人 2026-09-29）

| 问题 | 裁定 |
|---|---|
| 对象范围 | 二次元角色与真人脸**都要** |
| 入口 | 浏览页筛选区上半部分最下面加「人物」按钮，打开**居中大 modal**：每格一个人物的封面图、名字、图数 |
| 推理 | **不做本地推理**，走远端图片向量模型 |
| 聚类 | 要自动归类（无监督），人只命名 / 合并 / 拆分 |
| 向量 | 同意 §9.2 的倾向：整图、缩放到长边 768、截 1024 维，不画框 |
| 挂人物的阈值 | 0.825（两轮探测都零混簇） |
| 合并建议 | 按组给；全局清单不做「清空」承诺 |
| 视觉模型 | 不进判定，也不进建议 |
| 跨画风的同一个角色 | 接受要人手合并 |
| **系列** | 人物之上的父级，**人手挑人物维护**，机器不生成。新的分类维度 |

**向量模型**：平台上只有 `Qwen/Qwen3-VL-Embedding-8B` 支持图片，所以不做选型，直接用它。它与现有文本 embedding（Qwen3-Embedding-4B）同族，理论上「用名字搜人物」可以多一条召回通路，**v1 不做**（§7）。**人物向量单独存、单独配置，不与现有文本 embedding 合并**——合并等于换全站 embedding 模型，要走 [§9.20](../spec/09-decisions.md) 的迁移并全量重算，不在本任务内。

总管在此之上补的（**产品负责人没说、我按探测数据和已有原则定的，不同意就在这里改**，改了 SPEC 跟着改）：

1. **系列是树**：一个人物至多属于一个系列，系列可以是空的。代价：联动 / 客串的角色只能挂一处。等真的不够用再改成多对多（§9.34 推翻条件 4）。
2. **合并不可撤销**。合错了靠把图移出来修；确认框必须写明这一点和涉及的图数。撤销要存合并前的快照，v1 不值。
3. **全员可改、记操作人**，与编辑标签同理；**删系列限创建者或 admin**，与删图同一个不对称（[SPEC §6.7.1](../spec/06-endpoints.md)）。
4. **每张图都参与成组**，所以猫、纯文字、同一模板也会成「人物」。v1 **不按标签预筛**（「主体与风格」那一维的准确率撑不起一道闸），给一个「隐藏」收拾；真库 500 张的分布看过再说。隐藏的人物照样吸新图，否则被藏的那组会重新长出来。
5. **未命名的显示、标「未命名」**，否则没地方起名；**只有一张图的默认折叠**（modal 默认 `minCount=2`，底部一个「也显示只有一张的」）。
6. **Meme 的对外表示不变**，不加「属于哪个人物」。「不是他」「设为封面」只出现在按人物筛的浏览里，那时客户端已经知道是谁。
7. **v1 的「按名字找」就是 modal 里的名字过滤**（`GET /persons?q=`）。搜索框里打人名自动变成人物筛选、别名，都留给[梗名别名层](2026-09-13-meme-lexicon.md)——名字全员可改，直接接进搜索等于开一条劫持路径，要先有那边的词形准入规则。
8. **入口是一个「人物」按钮**，modal 里「人物 / 系列」两个 tab；有人物或系列筛选生效时，按钮上显示那个名字、能一键清掉。
9. **写操作一律不调 AI**；合并建议从已存的向量算。
10. **图片向量配置全站一份、admin 配、花部署方的额度**，与文本 embedding 同一个理由（[§9.6](../spec/09-decisions.md)）。**第一次配好不自动补跑存量**，由管理员点，点之前界面说清条数与花谁的钱。

## 4. 第 0 步：探测（已完成，2026-09-29）

> 两轮结果见 §9，结论已进 [SPEC §9.34](../spec/09-decisions.md)。下面是开探测前写的要求，原样留作记录。其中「真值补齐之前不跑」「不通过就挂起」已不再适用：产品负责人看过 §9.2 的数据后拍板了方向，真人缺口按 [§9.27](../spec/09-decisions.md) 不阻塞。

**要回答的问题**：拿 Qwen3-VL-Embedding-8B 给主体算向量，同一角色的图是不是互为最近邻？聚类阈值大概在哪？

| 变量 | 取值 |
|---|---|
| 输入 | **整图** vs **裁出主体后的图**（框由视觉模型返回，看它画得准不准） |
| 维度 | 原生维度，与 MRL 截断后（若支持）各一组 |
| 对象 | 二次元角色、真人脸各单独报，不混着算平均 |

**真值来源与它的缺口（必读）**：评测集里 `humanName` 已填 14/30，但**同一角色有两张及以上的只有两组**——塞西莉亚（161 / 723 / 768）、kipfel（75 / 410）。魔裁的 350 与 395 是同作品的不同角色，反而是很好的**负例**。只有两个正组，**得出不了任何阈值**，最多能证明「不是完全不行」。

所以探测前要先补真值：由库主人从库里挑，**每个角色 3–5 张，至少 10 个角色，二次元与真人脸各一批**，再挑若干「长得像但不是同一个」的对子做负例。这一步是人做，不是 api 做。**在真值补齐之前，api 不要开始跑。**

**要报告的**：

1. 同角色对的相似度分布 vs 不同角色对的分布，两条分布是否分得开、重叠多少。
2. 整图 vs 裁剪的差距。**如果裁剪没有明显提升，就不用为「让视觉模型画框」付这笔复杂度**，也不必要求用户配的视觉模型会返回框。
3. 视觉模型返回的框：命中率、明显偏移的占比、纯文字图 / 无主体图怎么处理。
4. 一张图 / 一个主体的调用耗时与单价，据此估存量 500+ 张的补跑成本。
5. 真人脸单独判断：通用向量不行的话，云端人脸比对 API 是另一条路（要花钱，且有隐私与合规问题），**只记结论，不在本任务里接**。

**通过 / 不通过**：本任务不预设数字线，探测后由产品负责人对着分布图裁定。**倾向**：误合并（两个角色并成一组）远比碎片（一个角色分成两组）伤人，因为误合并会让人物筛选混进别的角色；所以阈值取偏保守，靠「这两组可能是同一个」的合并建议收拢。**不通过就停在这里，本任务转 `planning` 挂起，不硬做。**

**产出放哪**：结果写进本文件 §9，脚本放 `api/scripts/`（与 `eval.ts` 同处）；**不进 `src/`、不加迁移、不加接口**。图片真值不进仓库（与 `eval/images/` 同规矩）。

## 5. 做完的标准与各端要改什么

### 5.1 做完的标准

1. **没配图片向量时一切照旧**：导入、打标、搜索与今天逐字一致；人物与系列接口返回空列表，不报错；浏览页「人物」按钮在，modal 是空态。
2. 配置测试通过（`imageInputWorks = true`）才能保存；替身上游回「图被丢掉」的样子（两张不同的图向量几乎一样，或图片 token 为 0），保存被拒。密钥只回显后四位。
3. 配好之后**新入库的图**自动算向量、挂人物。向量调用失败、超时：`tag_status` 不受影响，导入不 `failed`，那张图只是暂时不属于任何人物。
4. 管理员点补跑：存量排进队列，状态计数来自库里；再点一次不重复排。
5. 同一套表情（评测集甲组那种）进来后自成一个人物；跨画风碎成几组时，在其中一组的「可能是同一个」里能看到兄弟组。**任何地方都不出现相似度数字。**
6. 改名、归系列、设封面、隐藏、合并、拆出、移出、点「不是同一个」、系列增删改：结果对，留痕字段有值。**被人移出的图，再跑一次补算或换模型重算，仍然不回来。**
7. 合并后：来源人物消失，它们身上的「不是同一个」转到目标上，目标与来源之间的那条丢掉；确认框写明不可撤销和涉及的图数。
8. **软删四条**：软删一张图，所在人物图数减一；那张是封面时换成最新的一张；人物的图全删了，它从列表消失、`GET` 返回 `NOT_FOUND`；按人物 / 系列筛的浏览里不再有它。
9. 按人物 / 系列筛浏览；带 `q` 时同样「先过滤后召回」（[SPEC §6.3.1](../spec/06-endpoints.md)）；与其他筛选取 AND。
10. 删系列：非创建者、非 admin 拿到 `FORBIDDEN`；删掉后其下人物还在，只是不属于任何系列。

「恢复一张软删的图，人物跟着回来」和「物理删除级联」**现在验不了**：恢复接口与定时清理都还没有（[回收站任务](2026-09-24-trash-and-cleanup.md)），随那张任务验。

### 5.2 顺序与阻塞

**api 先，分两批合入。** 只是新增接口，api 先合不会让 web 坏。

| 批 | api | web 随后能做的 |
|---|---|---|
| 一 | 迁移、图片向量配置与测试连接、向量任务与分配、补跑、读接口（列表 / 详情 / 建议）、浏览的 `person` / `series` 参数 | 设置页的配置卡与补跑面板、「人物」按钮与 modal、按人物 / 系列筛 |
| 二 | 写接口（PATCH、merge、rejections、assignments、系列增删改） | 起名、合并、「不是他」、设封面、隐藏、系列管理 |

**web 的阻塞点**：web 从 api 的 Hono RPC 路由类型取请求 / 响应形状，**不手写接口类型**（[SPEC §7.1](../spec/07-naming.md) 那条教训）。第一批路由类型合入之前，web 最多做不碰接口的静态骨架；第二批同理。

### api 端

先读：`database.md`（迁移、pgvector 索引、归一化）、`queue.md`、`ai-providers.md`、`image-pipeline.md`、`env-validation.md`、`testing.md`。

- **迁移** `0010_…`：[SPEC §5.7](../spec/05-data-models.md) 的五张表。`meme_subjects.embedding` 建余弦 HNSW；系列名唯一按 `lower(btrim(name))`；`meme_subjects.meme_id` 随 `memes` 物理删除级联。
- **常量**（[§9.26](../spec/09-decisions.md)，不进配置）：长边 768、截 1024 维、挂人物阈值 0.825、建议最多 3 条。`embed_model` 存「模型 + 预处理口径」，如 `Qwen/Qwen3-VL-Embedding-8B@768`；**改长边等于换模型**，存量要重算。
- **上游请求形状**（探测实测，硅基流动）：只认 `input: [{ image: "data:image/png;base64,…" }]`；`dimensions: 1024` 生效；**同一条 input 里别同时放 `text`**，图会被静默丢掉。回来的向量截断后重新 L2 归一化（本端入口 §4）。可跑的参考在 `api/scripts/person-probe.ts`。
- **配置**：`/config/image-embed` 的 GET / PUT / test 照 `/config/embed` 那套（`routes/config.ts`、`services/ai-config.ts`、`ai/probe.ts`），多一个 `imageInputWorks`：送两张明显不同的图，向量几乎一样或上游报的图片 token 为 0 就判 `false`。部署方兜底变量 `DEFAULT_IMAGE_EMBED_BASE_URL` / `_API_KEY` / `_MODEL` 进 env 校验、[`docs/environments.md`](../docs/environments.md) 与 `.env.example`。
- **向量任务**：入库后单独排队，**不挂在打标任务上**——打标失败、没配视觉通道都不能连带人物。送出去的一律 PNG；动图取代表帧，与近似重复判定同一取法。失败按 `queue.md` 重试，终局失败只记在这一行，不动 `tag_status`。并发先用代码常量；**要进运行参数就是改 [SPEC §5.6](../spec/05-data-models.md)，回总管**。
- **分配**：
  - 规则与探测脚本的 `cluster()` 一致：和每个人物的**质心**（成员向量之和再归一）比，最高的够阈值就挂，否则新建未命名人物。质心可以现算（pgvector 的 `avg`）；要落缓存列就是改 SPEC §5.7，回总管。
  - 质心只用未软删的成员算。隐藏的人物照样参与；图全被软删的人物没有质心，不参与。
  - **这一步要串行**（例如 advisory lock，只锁分配、不锁上游调用）：同一个新角色的两张图并发进来，不串行就会各建一个人物。
  - `assigned_by` 非空的行一概不碰；已分配的行重算只换向量。
- **补跑**：`POST /admin/persons/reindex` 只排「未软删、没有当前口径向量」的，幂等；状态来自真实计数，不影响 `degraded`。换模型要 `confirmReindex`。
- **读接口**：列表的五个参数、排序、游标照 [SPEC §6.7.3](../spec/06-endpoints.md)。图数、封面、成员**一律过 `memes.deleted_at is null`**；图数为 0 的人物不出现。合并建议：两组之间的相似度取两组里最像的那一对图（探测脚本 `suggest()` 的口径），排除隐藏的与点过「不是同一个」的。**任何响应都不带相似度数值。**
- **浏览筛选**：`GET /memes` 的 `person` / `series` 也要进搜索那条「先过滤后召回」（`services/search.ts`、`data/search.ts`），不能只接浏览。
- **写接口**：逐图的操作按 `edit` 过 `assertCanMutate`，软删的图 `NOT_FOUND`；merge、assignments 各是一个事务；`person_rejections` 写入时把较小的 id 放前面。**每个写接口都挂校验器**，否则 RPC 推不出请求体类型、web 只能手写——`PATCH /memes/{id}` 现在就是这样，别再来一个。
- **测试**（上游用替身，说明白是替身）：没配置时一切照旧；`imageInputWorks = false` 存不进；并发分配不重复建人物；人做过的归属在补跑 / 重算后不变；软删四条；merge 转移 rejections；系列同名 `CONFLICT`、删系列 `FORBIDDEN`。
- 闸门：`cd web && npm run typecheck`、`npx vitest run`。
- **不跑真补跑**：它花部署方的额度，跑之前问产品负责人。

### web 端

先读：`settings-ux.md`、`state-navigation.md`、`feedback.md`、`http.md`、`styling.md`。

- **设置页（admin 段）**：「图片向量」卡照 `EmbedSettings`（先测后存、`imageInputWorks` 的结果要说人话、密钥只显示后四位）；补跑面板照 `ReindexPanel`，**点之前说清要排多少张、花的是部署方的额度**，跑的时候轮询状态。

- **居中大 modal**，「人物 / 系列」两个 tab：
  - 人物格：封面、名字（`null` 显示「未命名」）、图数；按图数降序、滚动加载。默认 `minCount=2`，底部「也显示只有一张的」；顶部名字过滤（`q`）；「已隐藏」单独一个入口（`hidden=true`）。
  - 系列格：封面（空系列没有）、名字、人物数、图数；「新建系列」在这个 tab 里。
  - 点人物格 = 加 `person` 筛选、关 modal；点系列格 = 加 `series` 筛选、关 modal。
- **按人物筛的浏览页头部**：名字（可改）、所属系列（可改）、隐藏；「可能是同一个」最多 3 格，每格「合并」「不是同一个」。合并确认框写明**不可撤销**和涉及的图数；谁当目标就留谁的名字，界面上要看得出来。
- **卡片「⋯」**：只在按人物筛时多两项——「不是 X」（`none: true`）、「设为封面」。批量选图「拆成新人物」（`newPerson`）接口有，v1 界面可以先不做。
- **按系列筛的头部**：系列名（可改）、「编辑成员」（勾选人物，整份提交 `personIds`）、删除（只对创建者与 admin 显示，二次确认里说明人物不会被删）。同名 `CONFLICT` 就地提示。
- **不显示任何相似度数字**，接口也不给。

## 9. 探测结果

### 9.1 冒烟（2026-09-29，产品负责人给了一次性 key，api 执行者代跑）

**这是冒烟，不是 §4 的正式探测。** §4 要的真值还没补，这一轮用评测集现成的 30 张图拼了一份（放在 `tmp/person-probe/smoke/`，不进仓库）：21 个身份，4 个正组共 11 个同角色对，另有 1 组同模板换字的图（3 对）单独统计。**全是二次元，一张真人都没有。** 这点量够排除方案，不够定阈值。脚本 `api/scripts/person-probe.ts`，报告与缓存在 `smoke/_out/`。

**接口（硅基流动，`https://api.siliconflow.cn/v1`，`.com` 那个域名 401）**

- 图片只认 `input: [{ image: "data:image/png;base64,..." }]`；字符串、`messages`、`{type:'image_url'}` 三种写法都回 400（code 20015）。
- 原生 4096 维；`dimensions: 1024` 生效。批量与单张结果逐位相同。
- 同一条 input 里同时给 `text` 和 `image`，**图会被静默丢掉**（`image_tokens: 0`）；`instruction` 字段无效。所以没法给图片向量加指令。
- image token 按长边算：256 → 64，512 → 240，768 → 552，1024 → 960（方图）。

**发现 1：向量对输入分辨率很敏感，必须归一到固定长边。** 同一张图缩到不同尺寸，两份向量的 cosine 只有 0.66–0.94（292 号在长边 768 与 512 之间是 0.725），比很多**不同角色**的对子还低。这和 vLLM 已报的回归一致（vllm#33954、QwenLM/Qwen3-VL-Embedding#59）。下面的数都是在「送之前缩放到长边 768，小图放大、大图缩小」的条件下测的；不归一时整图最近邻 8/11。**落地时这是硬约束**：换尺寸 = 换向量空间，存量要全部重算。

**发现 2：整图就够，裁剪没有提升，维度截到 1024 也不掉。**

| 输入（长边 768） | 维度 | 同角色对 p50 / min | 不同角色对 max | 最近邻命中 | 零误合并时召回 |
|---|---|---|---|---|---|
| 整图 | 4096 | 0.902 / 0.562 | 0.812 | 9/11 | 8/11 |
| 整图 | **1024** | 0.900 / 0.564 | **0.791** | 9/11 | **9/11** |
| 头部裁剪 | 4096 | 0.904 / 0.584 | 0.814 | 7/11 | 7/11 |
| 身体裁剪 | 4096 | 0.838 / 0.624 | 0.839 | 8/11 | 5/11 |

按随机入库顺序做增量聚类（挂到最近的簇，够不上阈值就另起一簇），整图 1024 维，每个阈值打乱 20 次取平均：阈值 0.825 时得 23 簇，21 个身份，**混了人的簇 0**，多出 2 个碎片；降到 0.800，混了人的簇 0.1（4096 维是 0.8）。裁剪在所有阈值下的碎片都更多（头部 4.0）。→ §4 第 2 项：**裁剪没有明显提升，不必为画框付这份复杂度。**

**发现 3：分不开的是「同一角色，不同画风」。** kipfel 3D 与黑白两张只有 0.562；塞西莉亚的 Q 版（768）与另两张只有 0.787 / 0.798，和最像的不同角色对（161-50 0.812、692-84 0.793）混在一起。模型认的更像「同系列 / 同画风」，不是「同一个角色」。这类只能靠人合并。

**发现 4：灰区交给视觉模型反而更糟，§9.33 那套三档不能照搬。** 整图 4096 维 0.70–0.83 之间 79 对，逐对问 `Qwen3-VL-32B-Instruct`「是不是同一个角色」：

| 真值 \ 模型 | same | different | unsure |
|---|---|---|---|
| 同角色（2） | 0 | **2** | 0 |
| 不同角色（77） | **4** | 62 | 11 |

两个同角色对都是塞西莉亚的 Q 版，模型的理由是「画风差异明显」；4 个误判 same 全是「蓝发 + 猫耳 vs 蓝发 + 猫耳」（264 / 292 对 480）、「金发 + 猫耳 vs 金发 + 猫耳」（458 对 944 / 951），原图我已看过，确实是不同角色。它和向量犯的是同一类错，放进环里只会多出误合并。平均 13 s/对，79 对共 96,618 tokens（约 1.2k/对）。**§9.2 正例多了以后重测，「召回为 0」不成立，改看那边。**

**发现 5：框是准的，但用不上。** 30/30 检出主体，坐标逐张对照原图没有明显偏移，只有 283 号检出两个主体；32B 画框约 9.4 s/张，30 张约 1.6 万 tokens。既然裁剪不提升，**§6 的「检测框由谁出」就不用回答了**。代价要说清：整图方案一张图只有一个向量，**多人同框的图最多归一个人物**（本集 1/30，库里的真实比例没量）。

**存量补跑估算**：整图长边 768 每张 ≤ 552 image tokens，500 张约 28 万 image tokens；8 张一批约 0.8 s，串行约 1 分钟。**单价没查**，不写金额。

**没测的**：真人脸（本集一张都没有，§4 第 5 项完全空白）；产品负责人的大真值；用名字（文本）搜人物；同一对图换顺序问视觉模型会不会改判；动图只取了中间帧，没比多帧。

**倾向（已被 §9.2 那一版取代，留作对照）**：

- 整图 → 缩放到长边 768 → 截 1024 维（与现有文本 embedding 同维，存储不翻倍）→ 保守阈值挂簇（本集 0.825 起零误合并），否则自成新簇。
- 不画框，不让视觉模型参与判定。
- 灰区（本集约 0.72–0.825）只生成「这两组可能是同一个」的**合并建议**，由人点。
- 画风差异大的同一个角色，产品上要接受「必须人手合并」。
- 正式探测仍要补真值，**真人那批是硬缺口**：真人脸通用向量不行的话，走的是 §4 第 5 项另一条路，影响整个方案。

### 9.2 补真值后重跑（2026-09-29）

**数据。** 产品负责人补了 3 个二次元角色共 17 张：A 粉发 8 张、B 初音 Q 版 4 张、C kipfel 5 张，平铺在 `tmp/person-probe/set1/`。C1 与评测集 75 号逐字节相同（sha256 前 16 位 `ce61815cc341104a`），产品负责人确认 C 就是 kipfel。于是把评测集的 410 并进来当 C6，评测集那边去掉 kipfel；初音猫（22）可能与 B 是同一个，也去掉。合起来 45 张、22 个身份、6 个正组（补充 3 组 + 评测集的甲、乙、塞西莉亚），另有 1 组同模板换字单独统计，放在 `combo2/`。**仍然全是二次元**；§4 要的「至少 10 个角色」还差。下面都是整图、长边 768，不写维度的都是 1024 维。缓存齐全，离线重算不花额度。

**发现 6：不同角色的上沿是稳的；同一角色的下沿取决于「是不是同一套图」。**

| 整图 1024 维 | 同角色对 | p50 | min | 不同角色对 max | 最近邻命中 |
|---|---|---|---|---|---|
| 评测集剩下的 3 个正组 | 10 | 0.900 | 0.788 | 0.791 | 9/9 |
| 补充的 3 个角色 | 49 | 0.766 | 0.564 | 0.754 | 18/18 |
| 全部 45 张 | 59 | 0.796 | 0.564 | 0.791 | **27/27** |

评测集的甲、乙两组是同一位画师的同一套表情，原图看过；塞西莉亚那组最低的两对，恰好是 Q 版那张。补充的三个角色都跨了画风：A 有像素风、3D 和加滤镜的，C 有彩色、黑白和低清的。

不同角色对的上沿在冒烟和这一轮都是 0.791，所以阈值放在 0.8 附近是站得住的。站不住的是这个阈值能收进多少：同一套图基本全收，跨画风的同一个角色只收一半左右。

| 全部 45 张，阈值 | 簇数（22 个身份） | 混了人的簇 | 碎片 |
|---|---|---|---|
| 0.775 | 21.9 | 1.7 | 3.8 |
| 0.800 | 27.9 | 0 | 5.9 |
| 0.825 | 30.6 | 0 | 8.7 |

- 碎片几乎全出在补充的 3 个角色：单独算时，0.800 下 3 个角色被分成 8.0 簇。
- 0.800 是边缘：评测集单独算、以及冒烟里，混簇都是 0.1（20 次打乱的平均）。
- 0.825 在冒烟和这一轮的每个范围里都是 0。

**发现 7：合并建议要「按组给」，不能「排成一张全局清单」。**

模拟方式：保守阈值挂完簇后，模拟人来收拢碎片。
- 两组之间的相似度取两组里最像的那一对图。
- 每次合并后重排。
- 点掉过的「X 不是 Z」，在 X 并进别的组以后仍然生效。
- 20 次入库顺序取平均。
- 脚本里是 `suggest()`。

| 全部 45 张，阈值 | 碎片 | 单看一组：最像的那组就是它的兄弟 | 全局清单：收一半碎片前点掉的错建议 | 全局清单：收全前点掉的错建议 | 互为最近：第一轮对 / 错 |
|---|---|---|---|---|---|
| 0.800 | 5.9 | 8.8 / 8.9 | 0 | 68 | 3.0 / 1.4 |
| 0.825 | 8.7 | 12.7 / 12.7 | 0 | 68 | 4.0 / 1.0 |

- **按组给**：在人物详情里给一条「可能是同一个」，只给和它最像的那一组，几乎都对。代价是没有兄弟的组也会被给一条，而那一条必然是错的。人点掉就行，不自动合并。
- **全局清单**：前一半碎片一条错的都不用点。拖尾每次都是 C6，就是 kipfel 黑白低清的那张，它和同伴最高只有 0.697，排在上百对不同角色后面。换成「互为最近才给」也救不回来，收全之前要点掉 71 条。所以**不要承诺「把待合并清单清空」**，全局列表只放前几条。

**发现 4 修正：视觉模型判灰区，召回不差，但会误合并。** 整图 4096 维、相似度在 0.70–0.83 之间的共 224 对：

| 真值 \ 模型 | same | different | unsure |
|---|---|---|---|
| 同角色（37） | 35 | 2 | 0 |
| 不同角色（187） | **9** | 164 | 14 |

冒烟里的 2 个同角色对（都是塞西莉亚的 Q 版）这回照样判错。新加的跨画风同角色对（像素对 3D、彩色对黑白）全部判对。所以冒烟里「召回为 0」是样本太小造成的。

判成 same 的 9 对错例仍是同一类：
- 初音 Q 版（B2 / B4）对甲组的蓝色猫耳兜帽：模型把初音的发饰读成了猫耳。
- 264 / 292 对 480。
- 458 对 944 / 951：金发 + 猫耳。

模型说 same 的 44 次里错了 9 次。按 §4 的不对称原则，**它仍不能用来自动合并**。拿它给建议排序也没有必要，发现 7 里单看一组的最近邻已经是 8.8 / 8.9。成本是每对 13–21 s、约 1.2k tokens。

**倾向（取代 §9.1 那一版，仍待产品负责人裁定）**：

- 不变：整图 → 缩放到长边 768 → 截 1024 维，不画框。
- 挂簇阈值取 0.825：两轮数据里都零混簇。0.800 能少一些碎片，但处在边缘。
- 合并建议按组给：人物详情里列出最像的那一组，给几条待定。全局清单只放前几条，不做清空承诺。
- 视觉模型不进判定，也不进建议。
- 产品上要说清楚：同一套表情包会自动成组；**同一个角色换了画师、换了画风，大多要人手合并**。

**没测的**：
- 真人：硬缺口没变。
- 更多角色：22 个身份里只有 6 个正组。
- 500 张规模下全局清单和按组建议的表现：本集只有 45 张，拖尾只会更长。
- 用名字搜人物。
- 同一对图换个顺序问视觉模型，会不会改判。

### 10.5 过程中发现并修掉的一个真 bug

`GET /series/{id}` 返回 500：`TypeError: date.toISOString is not a function`，栈在 `serialize/meme.ts`。

原因是 **`db.execute()` 把 timestamptz 当文本给出来**，列类型只在 `select()` 那条路上生效；行类型却写着 `Date`，于是类型检查一路放行，到序列化才炸。这条只在「列表为空 / 字段恰好为 null」之外的路径上才露头，`GET /persons/{id}` 是等一个非空 `updated_at` 才会撞上。修法是在 `src/data/persons.ts` 里收口成 `toDate` / `toDateOrNull`，并加了一条「留痕字段非空时也是 ISO 串」的回归测试。

### 11.3 过程中发现并修掉的一个真 bug：合并之后白屏

**复现**：按人物筛 → 卡片「⋯」→「不是 X」摘掉一张 → 「合并」→ **整页只剩侧边栏和工具条，图墙全没了**。控制台：`TypeError: Cannot read properties of undefined (reading 'meme')`，栈在 `BrowseResults.tsx` 的 `itemKey` 里，由 masonic 的 `useMasonry` 在 `search()` 时抛。

**成因**：合并走的是 `list.reload()`（整表替换）。重拉回来那一页比屏幕上现有的短，而 masonic 的位置器**按 index 缓存**，缩短之后它会去读 `items[i]` 上那个 `undefined`，抛错 → React 把整棵树卸掉 = 白屏。同一课在删除那条路径上早就记过（`epoch` + 换 `key` 重挂）。

**修法**（`features/browse/use-browse-list.ts`）：整表替换那一支**在 `setItems` 的同一次提交里** bump `epoch`（即换 `<BrowseWall key>`），判据是「屏幕上本来有没有东西」（`itemsLenRef.current > 0`，用 ref 读是为了不把 `items` 塞进 `load` 的依赖数组）。删除那条路径原有的 `applyRemoval` 不动。

⚠️ **第一版修错了，值得记一笔**：把 bump 放进 `reload()` 里没用——它在 fetch 回来**之前**就落地了，那一次重挂拿到的还是旧的 3 条，缩短发生在重挂**之后**，照样抛。**bump 必须与 `setItems` 落在同一次提交里。**

回归断言已进脚本：`合并之后页面没有整片消失（列表缩短时位置器要重挂）`。

另一处（不是产品 bug，但让排查绕了一圈）：瀑布流**滚动时会给卡片挂 `pointer-events: none`**（`BrowseResults` 的 `IDLE_MS = 130ms`，为了不让滚过去的每一格都触发 hover）。`scrollIntoView` 本身就是一次滚动，于是「滚到位 → 立刻点」在脚本里点不中；而桌面那一档卡片本来就在视口中间、滚不动，**两档不一致**。（同一次排查里我先把它错记成「触摸模拟下 `pointerType` 对不上」，那是错的，脚本注释已改回。）

#### 13.2.1 坏在什么地方

| 人物大小 | 61 | 43 | 23 | 9 | 5 | 3 | 单图人物 **136** 个 |
|---|---|---|---|---|---|---|---|

- **组内比组间还疏**：61 那组组内两两最低 0.629 / 平均 0.771，而它的成员到**别的**人物成员的相似度能到 **0.904**。43 组 0.763 / 0.904；23 组 0.772 / 0.870。

**文本向量**：1773/1773 张都已经有（`Qwen/Qwen3-Embedding-4B`，`memes.embedding` 非空），description 平均 49 字。**零边际成本，是现成资产。**

**对话 VLM（二分判定要用的那只）——单价没有，要另给。** 这份价目是 embedding 的，embedding 模型不会回答「是不是同一个人」。按每次调用 ≈ 两张图（2×700）+ 提示词 ≈ **1500 输入 tokens** 估：

| 做法 | 调用次数 | token 量 | 随人物数 P 增长吗 |
|---|---|---|---|
| 朴素：每个人物 × 每张未归类图 | P × U（P=50 → **88,650**；P=200 → **354,600**） | — | **是，乘性** |
| 向量提名：每张图只比 top-5 人物代表 | U × 5 = **8,865** | ≈ 13M | **否** |
| 单张重建（图上操作菜单） | P（P=50 → **50**） | ≈ 7.5 万 | 线性、恒小 |

**人物数 ≤ 5 时直接全比更便宜**（U×P < U×5），超过 5 就改用 top-5，**成本封顶在 U×5**。把对话模型的单价代进 13M tokens：若 ¥1.8/M → 全库约 **¥24**；若 ¥0.7/M → 约 **¥9**。量级是**十到几十块**，但要真数得跑一次小批量量一下它实际吃多少图 tokens。

### 13.6 待议问题点

**① 技术路径定哪一个？**
§9.34 定的是「整图向量自动成组、人只命名」，已被 13.2.1 推翻。选项：(a) 全自动分组、人只命名——上限最高，但需要一只真能认人的裁判；(b) **机器提议、人确认**；(c) 纯人工。
**建议 (b)**：错了也无害（人看到的是两张并排的图），且不需要一次跑对全库。(a) 和 (c) 都能由 (b) 退过去，反过来不行。

**② 二分判定交给 VLM 值不值得？**（**未验证**）
图向量不行 ≠ VLM 不行，但也**没有证据说行**。同一个模型、同一个库、同样「脸红张嘴」的图，VLM 也可能一律说「是」。
**建议**：做 13.7 ① 那个实验，20 次调用出结论。在出结论之前不要再往前设计。

**③ 向量当「提名者」的召回率是多少？**（**未知，是成本结构成立的前提**）
只测出**精度**差（0.90 上都不是同一个人）；**召回**（真同一个人有没有排进 top-5）没测。精度差与召回差不是一回事，但很可能是一回事。
**建议**：不用真值集——跑 200 张试跑，人扫一眼结果看「明明是他怎么没提出来」多不多（13.7 ②）。这正是产品负责人定的「边用边迭代」，也正是上次栽的地方：一次全库跑完、没人看中间结果。

**④ 价格**：见 13.5。**要产品负责人给对话模型的单价**才能把 8,865 次和 13M tokens 换算成钱。

**⑤ 什么触发比对？**
现在是「上传即自动挂」，已停。选项：只有人点重建 / 上传后攒着 / 定时。
**建议**：只有人点。两个粒度——**单张**（图的操作菜单里，「找找跟这张像的人物」，P 次、恒小、日常用）与**全库**（偶尔点一次，先报价、可只跑前 N 张）。

**⑥ 重建出来的是「建议」还是「结果」？**
**建议**：建议。产品负责人确认无误的一键全收，拿不准的逐张看。现在没有任何证据支持自动挂。

**⑦ 机器能不能创建人物？**
**建议：不能。** 它只能说「属于已有的人物 X」或「不知道」。「136 个单图人物」之所以能产生，就是因为机器被允许建人物。

**⑧ 代表图谁挑、几张？**
**建议**：人建人物时挑（1 张起，可多挑）；人确认过的图可以自动扩充进代表集——**人挑的比模型挑的准**。

**⑨ 判断结果缓存与失效**：按 pair 缓存；人物合并 / 拆分 / 改名后那部分失效重算。否则同一对图两次跑出两个答案，分组会漂。

**⑩ 已有的文本向量能不能当免费提名者？**
1773/1773 张都有，零边际成本；13.2.1 的粗对照里它比图向量分得开（0.94 → 0.64–0.80），但仍然不确定够不够。
**建议**：既然免费，让 ② 的实验顺便把两条提名路径都比一下。

**⑪ SPEC §9.34 怎么改？**
推翻条件 ①②已触发，正文还在，状态仍是 `proposed`。本次只在 §9.34 加了一句指针指到本节。
**建议**：等路径定了**一次改到位**，别现在改成半截。

**⑫ 已经落地的接口与界面留不留？**
§5.7 / §6.7 那套（人物的增删改合、系列、浏览筛选、管理页、图片向量配置）**几乎都与「裁判是谁」无关**，服务的是 (b) 和 (c)。
**建议：留。** 真正要下的只有「机器自动挂」那一小块。**这也意味着「两条路都要重做一遍」是不成立的**——重做的成本比看上去小得多。

**⑬ 那 288 条图片向量留还是删？**
`person_id` 已置空、行还在。**建议：留**，它是 ② 提名实验的现成材料。

**⑭ 阈值那行代码谁去改？** 见 13.4。**建议**：交给 api 执行者，**在下次讨论之前**。

**⑮ 系列那一层受影响吗？**
系列是纯人工维护（人挑人物），与向量无关。**不受影响，可以继续。**

**⑯ 多对多**：一张图能不能属于多个人物？一个人物能不能属于多个系列？（§9.34 把「多对多系列」列在放弃项）
**建议**：维持一对多，有真实需求再说。

**⑰「未归类」要不要在界面上成为一个可见的池子？**
产品负责人说过「所有的都不一定要必须分人物」，但界面上没有对应的东西。
**建议**：要。否则「哪些还没分」不可见，重建也没法向人交代自己做了什么。

**⑱ 联合验收怎么办？**
任务 `in_progress`、契约 `proposed`、两端实现都已合入（`e7c9be1` / `8b42dcc` / `bd5bd70`）。
§5.1 原验收标准衡量的是「接口和界面照契约做出来了」，**这部分仍然有效**；要补的是**「分组正确性有人看过」**这一条。路径定了再回来收。

### 13.7 可以先做的两件事（不用等路径定）
