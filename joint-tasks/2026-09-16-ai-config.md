# 模型配置与测试连接：用户视觉通道、全站 Embedding、重建索引

**状态：`in_progress`** · 创建 2026-09-16

相关 SPEC：[§3.5](../spec/03-auth-permission.md)、[§5.3](../spec/05-data-models.md)、[§6.3.1](../spec/06-endpoints.md)、[§6.5](../spec/06-endpoints.md)（含本任务新加的 §6.5.3 / §6.5.4）、[§9.3](../spec/09-decisions.md)、[§9.6](../spec/09-decisions.md)、[§9.7](../spec/09-decisions.md)、[§9.9](../spec/09-decisions.md)

## 为什么

**「模型可配置」这件事现在只存在于表结构里。** `user_ai_configs` 和 `embed_config` 两张表在 `api/src/data/schema.ts` 里建好了，`CONFIG_ENC_KEY` 在 `lib/env.ts` 里校验了长度，`lib/redact.ts` 的 `maskApiKey` / `isMaskedApiKey` 也写好了——但**没有任何代码读写这两张表**，也没有 AES-GCM 的加解密实现。跑起来的系统只认部署方那三个环境变量。

这不只是缺一个设置页，它在拖着三处已经记在板上的偏差：

| 现状 | 后果 |
|---|---|
| `resolveVisionConfig()` 固定 `jsonModeWorks: null, multiImage: null` | 降帧梯子 `[10, 4, 1]` 在生产里走不到第一级——`multiImage` 永远是 null 就永远按最保守的拼图模式走（[打标队列遗留项](README.md#打标队列任务转出的遗留项)） |
| `ai/hyde.ts` 直接 `asCredentials(env.defaultVision)` | HyDE 用部署方的通道，不是搜索者本人的——**与 SPEC §6.3.1 / `ai-providers.md §6` 的已知偏差**（[搜索遗留项](README.md#搜索任务转出的遗留项)） |
| `resolveEmbedConfig()` 只读环境变量 | 部署方没配 `DEFAULT_EMBED_*` 时向量路永久缺失，管理员没有任何办法把它配上 |

**而「测试连接」是 §6.5 里最有价值的那个接口**，不是附属功能。用户填的是中转服务，[§9.7](../spec/09-decisions.md) 的整个论点就是「不让用户手填能力、也不假设任何能力，全部实测」；能力位（`jsonModeWorks` / `multiImage` / `dimParamWorks`）是运行时分支的**唯一**依据，而它们只能由这个接口写入。没有它，`ai-providers.md §2` 那张表里的三个字段全是 null，整个「能力从配置读」的设计落不了地。

顺序上它也该在 §6.4（编辑 / 软删 / retag）之前：`POST /memes/retag` 要用「调用者自己配置的视觉模型」，那个前提得先存在。

## 做完的标准

1. 一个新注册的普通用户能在 `/settings` 里填自己的视觉通道、点测试连接看到逐项探测结果、保存后导入的图**用他自己的 key 打标**（日志里能看出走的是哪套配置）
2. 测试不通过点不了保存；服务端也拒（`CONFIG_TEST_REQUIRED`）。改了任一字段后之前的测试结果不作数
3. 测试失败时 `rawResponse` / `rawError` **原样**出现在界面上（等宽、可折叠、可复制），没有被截断或包装成友好文案
4. 探测到的能力位真的改变了运行时行为：`multiImage: true` 的配置打一张 12 帧动图，日志显示发了 10 张 PNG 而不是拼图
5. 任何响应、任何日志、任何错误 `details` 里都搜不到完整 key，也搜不到 `CONFIG_ENC_KEY`。数据库里 `*_api_key_enc` 是密文，直接 `select` 出来读不出原文
6. admin 能在管理页配全站 Embedding：维度 < 1024 被拒（`EMBED_DIM_TOO_SMALL`）；库里有数据时换模型不带 `confirmReindex` 被拒（`EMBED_MODEL_CHANGED`）
7. 确认换模型后全站重建索引自动开跑，进度可查；**期间搜索照常返回结果且带 `degraded: true`**，不中断
8. 非 admin 访问 `/config/embed`、`/admin/reindex*` 一律 403（`FORBIDDEN`），前端也不给入口
9. `settings-ux.md §4` 那两段文案**逐字**出现在界面上，「你的打标结果会进入公共库」一句在
10. 闸门：`cd web && npm run typecheck` 0 错误；`cd api && npm test` 全绿

## 必须先知道的四件事

这四条是本任务最容易做错的地方，两端各自相关的部分在下面的小节里还会出现，但先在这里讲清楚理由。

### 1. 测试记录存在服务端，客户端不经手探测结果

探测结果字段**不接受客户端写入**（[§5.3](../spec/05-data-models.md)），所以「我刚测过了」这件事不能靠前端在 `PUT` 里回传。流程被这条硬规则固定成：

```
POST /config/vision/test  →  服务端实测 → 结果存服务端（含被测的 baseUrl / model / key 指纹）
PUT  /config/vision       →  按 baseUrl + model + key 指纹找到那条成功记录 → 把探测结果抄进配置行
```

匹配要带 **key 指纹**（key 的 SHA-256），不能只按 baseUrl + model——否则「换了 key 没测就保存」能过校验，而那恰恰是最常见的填错方式。这一条是本任务对 §6.5.2 的补严，已经写进 SPEC。

测试记录里**不存 key 明文也不存密文**，只存指纹。存法（新表还是别的）属 api 实现细节，SPEC 不管。

### 2. 运行时配置解析只有三个落点，不要扩散

```
api/src/ai/vision.ts    resolveVisionConfig()    ← 代码里已经标了「配置任务上线后只改这一处」
api/src/ai/embedder.ts  resolveEmbedConfig()
api/src/ai/provider.ts  asCredentials()          ← 「DB 里的记录排在环境变量前面，这个函数是那个改动的唯一落点」
```

`ai/hyde.ts:57` 现在绕过了前两者直接读 `env.defaultVision`，本任务要把它接回视觉通道的解析路径——**HyDE 用搜索者本人的配置**（`ai-providers.md §6`）。

这三处之外不许再出现「先查库、查不到用 env」的分支。多一处就多一个会忘记加解密、忘记查 `verified_at` 的地方。

### 3. 送去实测的那张图不是随便一张

视觉测试要「发一张内置测试图 + **正式的打标提示词**」（[§9.7](../spec/09-decisions.md)），响应里的 `vocabCompliant` 是「返回的标签落在词表内」。这意味着：

- 测试图必须是**一张真的能被打出标签的图**。拿噪声图或纯色块去测，一个好模型也会返回空字段，那正好长得像 `ai-providers.md §3` 的第三种拒绝形态——测试连接会把能用的供应商判成不能用
- 测试图必须随 api 运行时可用。**不要引用 `docs/fixtures/`**——那批是测试与评测用的，`huge.png` 还被 `.gitignore` 排除着（[docs/fixtures.md](../docs/fixtures.md)），运行时依赖它等于依赖一个不保证存在的目录
- 选了哪张、为什么选它，在验收里写一句

### 4. 重算不许重跑视觉

重建索引是从 `search_text` 重新算向量、写 `embedding` + `embed_model`（`data/memes.ts` 已有 `updateMemeEmbedding`）。**不碰 AI 产出字段、不调视觉模型**——换 embedding 模型不影响打标结果，重跑视觉是白花钱，而且会把用户手工编辑过的字段覆盖掉。

## 两端各自做什么

### api 端

**A. 加解密**

- AES-GCM 的 encrypt / decrypt，主密钥 `env.configEncKey`。放 `lib/`，纯函数、可单测
- 解密出来的 key **只在调用那一瞬间存在**：不进长生命周期对象、不进日志、不进错误 `details`、不进响应（`ai-providers.md §7`、`error-handling.md`）
- `CONFIG_ENC_KEY` 本身不进任何接口、任何日志、任何 `details`（[§3.5](../spec/03-auth-permission.md)）
- 单测至少覆盖：往返一致、密文每次不同（nonce 不复用）、换密钥后解密失败且失败方式是可判断的错误而不是脏数据

**B. 数据访问层**

- `data/` 里新增 `user_ai_configs` 与 `embed_config` 的读写。SQL 只在 `data/`（`project-structure.md`）
- `embed_config` 是单行表（`check (id = 1)`），写入用 upsert，不要 `insert` 后自己判重
- 探测结果字段只由测试路径写入。**读写函数的签名就该让「客户端传来的对象」没法写到这些字段上**，靠注释提醒挡不住下一个人

**C. 六个端点**（[§6.5](../spec/06-endpoints.md)、§6.5.3、§6.5.4）

| 端点 | 要点 |
|---|---|
| `GET /config/vision` | 返回 §6.5.3 那个形状；未配置时回显部署方默认值并带 `source: "default"` |
| `PUT /config/vision` | 脱敏串 = 不修改（用 `isMaskedApiKey`，别再写一遍）；无匹配测试记录 → `CONFIG_TEST_REQUIRED` |
| `POST /config/vision/test` | **不通过也是 200**，结果在响应体里（`http.md`、`settings-ux.md §5`）。只有请求本身非法才是 4xx |
| `GET / PUT /config/embed` | admin only；`nativeDim < 1024` → `EMBED_DIM_TOO_SMALL`；换模型且库里有数据缺 `confirmReindex` → `EMBED_MODEL_CHANGED`（409） |
| `POST /config/embed/test` | 同上，实测维度、`dimensions` 参数是否生效 |
| `POST /admin/reindex` · `GET /admin/reindex/status` | 幂等；进度来自库里的真实计数，不是内存计数器 |

权限：`/config/*` 是本人，`/config/embed*` 与 `/admin/*` 是 admin。用已有的中间件，不在 handler 里手写角色判断（`api/AGENTS.md §3`）。

**D. 探测实现**

- 视觉：能否收图 / 是否合法 JSON / 标签是否在词表内 / `response_format: json_object` 是否生效 / 多图是否支持。判定复用 `lib/vision-output.ts` 和 `lib/vocab-match.ts`，**不要为测试连接另写一套判定**——两套判定迟早给出不同结论
- Embedding：实测维度、`dimensions` 参数是否生效（传了以后返回的维度真的变了才算生效），`willTruncate` 由实测维度推出
- 不许出现按 `baseUrl` 猜供应商的分支（`ai-providers.md §1`）
- `rawResponse` / `rawError` 原样带回。**带回之前确认它不可能包含 key**——原始返回里一般没有，但如果实现把请求头或整个 request 一起塞进了 raw 字段，这个「核心价值」就变成一条泄露路径。这是本任务唯一一处「原样返回外部数据」和「key 不出响应」正面相撞的地方，处理方式在验收里写出来

**E. 运行时接入**

- 三个落点改成「DB 优先、环境变量兜底」，`hyde.ts` 接回视觉解析
- 解析结果只认**通过过测试**的配置行；测过但没通过的行不能进生产打标
- ⚠️ `queue/worker.ts:139` 的 `isVisionConfigured()` 是个**全局**判断：部署方没配默认视觉通道时 worker 60 秒才轮询一次且不取任务。用户自带 key 之后这个前提不成立了——照现在的写法，「部署方没配、用户自己配了」的图会永远 pending。改法自定，但这条必须处理，并在验收里说明怎么测的

**F. 重建索引**

- 用同一套队列机制，**不要塞进 `tag_jobs`**：那张表上 `meme_id` 有唯一索引，一条重算任务会和同一张图的待打标任务互相踢掉；而且重算不调视觉、重试策略也不同
- `PUT /config/embed` 带 `confirmReindex: true` 时自动入队；`POST /admin/reindex` 是手动补触发，两者都要幂等（`onConflictDoNothing` 的路子）
- 并发按全站一个小上限控，**不按用户分组**——这是运维操作，不是谁的配额
- 搜索侧：有未完成的重算任务时 `degraded: true`。判断落在每个搜索请求上，要么是索引命中的存在性查询，要么带短期缓存，**不能是全表 count**
- 不做断点续传（`queue.md §7`）

**G. 迁移**

新增列或新表都要出迁移文件，按 `api/migrations/` 现有编号续写。

### web 端

**A. `/settings`（所有人）**

- 视觉通道那一组收进**默认折叠**的「高级选项」。这个折叠是有意的：改错了会污染所有人的搜索结果（`settings-ux.md §3`）
- 显示当前用的是部署方默认还是自己的配置（`source` 字段）
- `settings-ux.md §4` 的「用户设置页 · 视觉模型」整段文案**逐字照抄**，它是契约（[§9.9](../spec/09-decisions.md)）。「你的打标结果会进入公共库」这一句尤其不能删
- Key 输入框 password 类型，显示 `**** + 后四位`，**不加显示明文的眼睛图标**；不改 key 就把脱敏串原样提交

**B. 管理页 · Embedding（仅 admin）**

- 放哪个路由 web 自己定，但必须走已有的 admin 守卫，和 `/admin/invites`、`/admin/users` 一致
- `settings-ux.md §4` 的「管理页 · Embedding」整段文案照抄
- 换模型的确认框要说清：**会触发全站重算，期间搜索降级为 OCR + 标签，但不中断服务**
- 重建进度显示在管理页，**不做成模态阻塞**——它要跑几分钟，管理员应该能去干别的

**C. 测试连接控件**（`settings-ux.md §5`，这一页最重要的控件）

- 每组配置一个独立的测试按钮，结果**逐项**列出探测到了什么，不是一个成功／失败的红绿灯
- 失败时 `rawResponse` / `rawError` 原样展示：等宽、可折叠、可复制，**不截断、不包装**
- 测试连接返回 200 也可能是不通过，**不要当 HTTP 错误处理**——那会把 `rawResponse` 丢掉（`http.md`）
- 测试不通过禁用保存按钮；改了 baseUrl / model / key 任一字段就重置测试状态

**D. 样式**

只写布局（`web/AGENTS.md §5`）：flex / grid、尺寸、间距、折叠区的 `display`。不写颜色、字体、阴影、圆角。「标红提示」这类要求用结构和文案表达，不靠颜色。

**E. 类型**

接口类型从 api 的 Hono RPC 派生，不手写（`web/AGENTS.md §4`）。`source` 的两个取值、能力位可能是 `null`（未测过）——**类型只保证形状**，null 的呈现要自己处理，别让界面显示「不支持多图」而实际是「还没测」。

## 明确不做

| 不做 | 为什么 |
|---|---|
| 视觉**副通道**的表单与降级接入 | 字段留在表里不动。[§9.5](../spec/09-decisions.md) 还是 `proposed`，副通道接入是它的事（板上已有这条遗留项）。⚠️ 照抄的文案里有一句「副通道建议配一个内容策略更宽松的供应商」——界面上没有对应输入框。**不要自行删这句文案**，觉得会误导就在本文件里提出来，由总管裁定 |
| 设置页与管理页的**统计面板**（`settings-ux.md §9`） | 它需要 §6.5 之外的新端点，和本任务的契约无关。单独开任务 |
| §6.4 的编辑 / 软删 / restore / retag / 查重 | 另一个任务。`retag` 依赖本任务，顺序在后 |
| `queue.md §6` 的五个定时清理任务 | 与配置无关 |
