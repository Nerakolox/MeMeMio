# 模型配置与测试连接：用户视觉通道、全站 Embedding、重建索引

**状态：`in_progress`** · 创建 2026-09-16

相关 SPEC：[§3.5](../spec/03-auth-permission.md)、[§5.3](../spec/05-data-models.md)、[§6.3.1](../spec/06-endpoints.md)、[§6.5](../spec/06-endpoints.md)（含本任务新加的 §6.5.3 / §6.5.4）、[§9.3](../spec/09-decisions.md)、[§9.6](../spec/09-decisions.md)、[§9.7](../spec/09-decisions.md)、[§9.9](../spec/09-decisions.md)

## 为什么

**「模型可配置」这件事现在只存在于表结构里。** `user_ai_configs` 和 `embed_config` 两张表在 `api/src/data/schema.ts` 里建好了，`CONFIG_ENC_KEY` 在 `lib/env.ts` 里校验了长度，`lib/redact.ts` 的 `maskApiKey` / `isMaskedApiKey` 也写好了——但**没有任何代码读写这两张表**，也没有 AES-GCM 的加解密实现。跑起来的系统只认部署方那三个环境变量。

这不只是缺一个设置页，它在拖着三处已经记在板上的偏差：

| 现状 | 后果 |
|---|---|
| `resolveVisionConfig()` 固定 `jsonModeWorks: null, multiImage: null` | 降帧梯子 `[10, 4, 1]` 在生产里走不到第一级——`multiImage` 永远是 null 就永远按最保守的拼图模式走（[打标队列遗留项](README.md#打标队列任务转出的遗留项)） |
| `ai/hyde.ts` 直接 `asCredentials(env.defaultVision)` | HyDE 用部署方的通道，不是搜索者本人的——**与 SPEC §6.3.1 / `ai-providers.md §6` 的已知偏差**（[搜索遗留项](README.md#搜索任务转出的遗留项)） |
| `resolveEmbedConfig()` 只读环境变量 | 部署方没配 `DEFAULT_EMBED_*` 时向量路永久缺失，管理员没有任何办法把它配上 |

**而「测试连接」是 §6.5 里最有价值的那个接口**，不是附属功能。用户填的是中转服务，[§9.7](../spec/09-decisions.md) 的整个论点就是「不让用户手填能力、也不假设任何能力，全部实测」；能力位（`jsonModeWorks` / `multiImage` / `dimParamWorks`）是运行时分支的**唯一**依据，而它们只能由这个接口写入。没有它，`ai-providers.md §2` 那张表里的三个字段全是 null，整个「能力从配置读」的设计落不了地。

顺序上它也该在 §6.4（编辑 / 软删 / retag）之前：`POST /memes/retag` 要用「调用者自己配置的视觉模型」，那个前提得先存在。

## 做完的标准

1. 一个新注册的普通用户能在 `/settings` 里填自己的视觉通道、点测试连接看到逐项探测结果、保存后导入的图**用他自己的 key 打标**（日志里能看出走的是哪套配置）
2. 测试不通过点不了保存；服务端也拒（`CONFIG_TEST_REQUIRED`）。改了任一字段后之前的测试结果不作数
3. 测试失败时 `rawResponse` / `rawError` **原样**出现在界面上（等宽、可折叠、可复制），没有被截断或包装成友好文案
4. 探测到的能力位真的改变了运行时行为：`multiImage: true` 的配置打一张 12 帧动图，日志显示发了 10 张 PNG 而不是拼图
5. 任何响应、任何日志、任何错误 `details` 里都搜不到完整 key，也搜不到 `CONFIG_ENC_KEY`。数据库里 `*_api_key_enc` 是密文，直接 `select` 出来读不出原文
6. admin 能在管理页配全站 Embedding：维度 < 1024 被拒（`EMBED_DIM_TOO_SMALL`）；库里有数据时换模型不带 `confirmReindex` 被拒（`EMBED_MODEL_CHANGED`）
7. 确认换模型后全站重建索引自动开跑，进度可查；**期间搜索照常返回结果且带 `degraded: true`**，不中断
8. 非 admin 访问 `/config/embed`、`/admin/reindex*` 一律 403（`FORBIDDEN`），前端也不给入口
9. `settings-ux.md §4` 那两段文案**逐字**出现在界面上，「你的打标结果会进入公共库」一句在
10. 闸门：`cd web && npm run typecheck` 0 错误；`cd api && npm test` 全绿

## 必须先知道的四件事

这四条是本任务最容易做错的地方，两端各自相关的部分在下面的小节里还会出现，但先在这里讲清楚理由。

### 1. 测试记录存在服务端，客户端不经手探测结果

探测结果字段**不接受客户端写入**（[§5.3](../spec/05-data-models.md)），所以「我刚测过了」这件事不能靠前端在 `PUT` 里回传。流程被这条硬规则固定成：

```
POST /config/vision/test  →  服务端实测 → 结果存服务端（含被测的 baseUrl / model / key 指纹）
PUT  /config/vision       →  按 baseUrl + model + key 指纹找到那条成功记录 → 把探测结果抄进配置行
```

匹配要带 **key 指纹**（key 的 SHA-256），不能只按 baseUrl + model——否则「换了 key 没测就保存」能过校验，而那恰恰是最常见的填错方式。这一条是本任务对 §6.5.2 的补严，已经写进 SPEC。

测试记录里**不存 key 明文也不存密文**，只存指纹。存法（新表还是别的）属 api 实现细节，SPEC 不管。

### 2. 运行时配置解析只有三个落点，不要扩散

```
api/src/ai/vision.ts    resolveVisionConfig()    ← 代码里已经标了「配置任务上线后只改这一处」
api/src/ai/embedder.ts  resolveEmbedConfig()
api/src/ai/provider.ts  asCredentials()          ← 「DB 里的记录排在环境变量前面，这个函数是那个改动的唯一落点」
```

`ai/hyde.ts:57` 现在绕过了前两者直接读 `env.defaultVision`，本任务要把它接回视觉通道的解析路径——**HyDE 用搜索者本人的配置**（`ai-providers.md §6`）。

这三处之外不许再出现「先查库、查不到用 env」的分支。多一处就多一个会忘记加解密、忘记查 `verified_at` 的地方。

### 3. 送去实测的那张图不是随便一张

视觉测试要「发一张内置测试图 + **正式的打标提示词**」（[§9.7](../spec/09-decisions.md)），响应里的 `vocabCompliant` 是「返回的标签落在词表内」。这意味着：

- 测试图必须是**一张真的能被打出标签的图**。拿噪声图或纯色块去测，一个好模型也会返回空字段，那正好长得像 `ai-providers.md §3` 的第三种拒绝形态——测试连接会把能用的供应商判成不能用
- 测试图必须随 api 运行时可用。**不要引用 `docs/fixtures/`**——那批是测试与评测用的，`huge.png` 还被 `.gitignore` 排除着（[docs/fixtures.md](../docs/fixtures.md)），运行时依赖它等于依赖一个不保证存在的目录
- 选了哪张、为什么选它，在验收里写一句

### 4. 重算不许重跑视觉

重建索引是从 `search_text` 重新算向量、写 `embedding` + `embed_model`（`data/memes.ts` 已有 `updateMemeEmbedding`）。**不碰 AI 产出字段、不调视觉模型**——换 embedding 模型不影响打标结果，重跑视觉是白花钱，而且会把用户手工编辑过的字段覆盖掉。

## 两端各自做什么

### api 端

**A. 加解密**

- AES-GCM 的 encrypt / decrypt，主密钥 `env.configEncKey`。放 `lib/`，纯函数、可单测
- 解密出来的 key **只在调用那一瞬间存在**：不进长生命周期对象、不进日志、不进错误 `details`、不进响应（`ai-providers.md §7`、`error-handling.md`）
- `CONFIG_ENC_KEY` 本身不进任何接口、任何日志、任何 `details`（[§3.5](../spec/03-auth-permission.md)）
- 单测至少覆盖：往返一致、密文每次不同（nonce 不复用）、换密钥后解密失败且失败方式是可判断的错误而不是脏数据

**B. 数据访问层**

- `data/` 里新增 `user_ai_configs` 与 `embed_config` 的读写。SQL 只在 `data/`（`project-structure.md`）
- `embed_config` 是单行表（`check (id = 1)`），写入用 upsert，不要 `insert` 后自己判重
- 探测结果字段只由测试路径写入。**读写函数的签名就该让「客户端传来的对象」没法写到这些字段上**，靠注释提醒挡不住下一个人

**C. 六个端点**（[§6.5](../spec/06-endpoints.md)、§6.5.3、§6.5.4）

| 端点 | 要点 |
|---|---|
| `GET /config/vision` | 返回 §6.5.3 那个形状；未配置时回显部署方默认值并带 `source: "default"` |
| `PUT /config/vision` | 脱敏串 = 不修改（用 `isMaskedApiKey`，别再写一遍）；无匹配测试记录 → `CONFIG_TEST_REQUIRED` |
| `POST /config/vision/test` | **不通过也是 200**，结果在响应体里（`http.md`、`settings-ux.md §5`）。只有请求本身非法才是 4xx |
| `GET / PUT /config/embed` | admin only；`nativeDim < 1024` → `EMBED_DIM_TOO_SMALL`；换模型且库里有数据缺 `confirmReindex` → `EMBED_MODEL_CHANGED`（409） |
| `POST /config/embed/test` | 同上，实测维度、`dimensions` 参数是否生效 |
| `POST /admin/reindex` · `GET /admin/reindex/status` | 幂等；进度来自库里的真实计数，不是内存计数器 |

权限：`/config/*` 是本人，`/config/embed*` 与 `/admin/*` 是 admin。用已有的中间件，不在 handler 里手写角色判断（`api/AGENTS.md §3`）。

**D. 探测实现**

- 视觉：能否收图 / 是否合法 JSON / 标签是否在词表内 / `response_format: json_object` 是否生效 / 多图是否支持。判定复用 `lib/vision-output.ts` 和 `lib/vocab-match.ts`，**不要为测试连接另写一套判定**——两套判定迟早给出不同结论
- Embedding：实测维度、`dimensions` 参数是否生效（传了以后返回的维度真的变了才算生效），`willTruncate` 由实测维度推出
- 不许出现按 `baseUrl` 猜供应商的分支（`ai-providers.md §1`）
- `rawResponse` / `rawError` 原样带回。**带回之前确认它不可能包含 key**——原始返回里一般没有，但如果实现把请求头或整个 request 一起塞进了 raw 字段，这个「核心价值」就变成一条泄露路径。这是本任务唯一一处「原样返回外部数据」和「key 不出响应」正面相撞的地方，处理方式在验收里写出来

**E. 运行时接入**

- 三个落点改成「DB 优先、环境变量兜底」，`hyde.ts` 接回视觉解析
- 解析结果只认**通过过测试**的配置行；测过但没通过的行不能进生产打标
- ⚠️ `queue/worker.ts:139` 的 `isVisionConfigured()` 是个**全局**判断：部署方没配默认视觉通道时 worker 60 秒才轮询一次且不取任务。用户自带 key 之后这个前提不成立了——照现在的写法，「部署方没配、用户自己配了」的图会永远 pending。改法自定，但这条必须处理，并在验收里说明怎么测的

**F. 重建索引**

- 用同一套队列机制，**不要塞进 `tag_jobs`**：那张表上 `meme_id` 有唯一索引，一条重算任务会和同一张图的待打标任务互相踢掉；而且重算不调视觉、重试策略也不同
- `PUT /config/embed` 带 `confirmReindex: true` 时自动入队；`POST /admin/reindex` 是手动补触发，两者都要幂等（`onConflictDoNothing` 的路子）
- 并发按全站一个小上限控，**不按用户分组**——这是运维操作，不是谁的配额
- 搜索侧：有未完成的重算任务时 `degraded: true`。判断落在每个搜索请求上，要么是索引命中的存在性查询，要么带短期缓存，**不能是全表 count**
- 不做断点续传（`queue.md §7`）

**G. 迁移**

新增列或新表都要出迁移文件，按 `api/migrations/` 现有编号续写。

### web 端

**A. `/settings`（所有人）**

- 视觉通道那一组收进**默认折叠**的「高级选项」。这个折叠是有意的：改错了会污染所有人的搜索结果（`settings-ux.md §3`）
- 显示当前用的是部署方默认还是自己的配置（`source` 字段）
- `settings-ux.md §4` 的「用户设置页 · 视觉模型」整段文案**逐字照抄**，它是契约（[§9.9](../spec/09-decisions.md)）。「你的打标结果会进入公共库」这一句尤其不能删
- Key 输入框 password 类型，显示 `**** + 后四位`，**不加显示明文的眼睛图标**；不改 key 就把脱敏串原样提交

**B. 管理页 · Embedding（仅 admin）**

- 放哪个路由 web 自己定，但必须走已有的 admin 守卫，和 `/admin/invites`、`/admin/users` 一致
- `settings-ux.md §4` 的「管理页 · Embedding」整段文案照抄
- 换模型的确认框要说清：**会触发全站重算，期间搜索降级为 OCR + 标签，但不中断服务**
- 重建进度显示在管理页，**不做成模态阻塞**——它要跑几分钟，管理员应该能去干别的

**C. 测试连接控件**（`settings-ux.md §5`，这一页最重要的控件）

- 每组配置一个独立的测试按钮，结果**逐项**列出探测到了什么，不是一个成功／失败的红绿灯
- 失败时 `rawResponse` / `rawError` 原样展示：等宽、可折叠、可复制，**不截断、不包装**
- 测试连接返回 200 也可能是不通过，**不要当 HTTP 错误处理**——那会把 `rawResponse` 丢掉（`http.md`）
- 测试不通过禁用保存按钮；改了 baseUrl / model / key 任一字段就重置测试状态

**D. 样式**

只写布局（`web/AGENTS.md §5`）：flex / grid、尺寸、间距、折叠区的 `display`。不写颜色、字体、阴影、圆角。「标红提示」这类要求用结构和文案表达，不靠颜色。

**E. 类型**

接口类型从 api 的 Hono RPC 派生，不手写（`web/AGENTS.md §4`）。`source` 的两个取值、能力位可能是 `null`（未测过）——**类型只保证形状**，null 的呈现要自己处理，别让界面显示「不支持多图」而实际是「还没测」。

## api 端验收

回填时间 2026-09-17 · api 执行者

### 实测环境（先说清楚这次测的是什么）

- **闸门两条都过**：`cd api && npm test` → 26 个文件 **259 passed**（本任务新增 5 个测试文件 **59 条**：`src/lib/config-crypto.test.ts` 13、`src/ai/probe.test.ts` 12、`tests/config-endpoints.test.ts` 20、`tests/config-user-vision.test.ts` 6、`tests/reindex-queue.test.ts` 8 —— 前两个是单测，后三个连真 Postgres）；`cd web && npm run typecheck` → **0 错误**。`npx tsc -p tsconfig.json --noEmit` 在 api 侧也是 0 输出。
- **六个端点已经挂进 `app.ts`**，并且是接在原来那条链上的（`.use().route()…`，`app.ts:21-30`），没有断链。web 端的阻塞点（E 项）现在可以解了。
- **没有调用过任何真实供应商。** 所有探测与打标路径都是 `vi.stubGlobal('fetch', …)` 的替身，替身按 OpenAI 兼容形状回，包括 401 / 502 / 维度不匹配 / 忽略 `dimensions` 参数这些失败形态。能这样测是因为本端不许按供应商分叉（`ai-providers.md §1`），代码里只有一条 HTTP 路径；**但这意味着「某个真实中转的怪癖」不在本次实测范围内**，只有接上真 key 才知道。
- 完成标准 4（12 帧动图实测发 10 张 PNG）走的是已有的 `tests/tag-queue-degrade.test.ts` / `tests/tag-queue.test.ts`，本次把「没有探测记录时不发多图」那条对照也保住了，两个文件仍全绿。

### A. 加解密（`src/lib/config-crypto.ts`，13 条单测）

AES-256-GCM，`版本号 || nonce(12) || ciphertext || tag(16)` 拼成一段 `bytea`。9 条打加解密：往返一致（含中文、含空串——key 是用户填的，不假设字符集）、**同一明文加密两次密文必然不同**（nonce 不复用）、密文里搜不到明文、换主密钥是**可判断的错误**而不是脏数据、密文被改一个字节也解不开（GCM 校验的是完整性，防的是「有人直接 UPDATE 了那一列」）、不是本函数写出来的数据分成 `malformed` / `unsupported_version` 两种可判断的失败、主密钥长度不对**直接拒绝而不静默补齐**、**错误 message 里既不含明文也不含主密钥**（SPEC §3.5 要求两者都不进 `details`）。另 4 条打 key 指纹：同 key 同指纹、定长十六进制且不含原 key、**一条已知向量**（换实现也得算出同一个值，否则库里老的测试记录会全部失配，表现是所有人突然被要求重测）、`fingerprintEquals` 只对相同指纹为真。

`CONFIG_ENC_KEY` 的流向是收口的：`lib/env.ts` 读一次，**`data/ai-configs.ts` 是唯一把它传进加解密的地方**（文件头写明了这一点），`logger.ts` 把它列进脱敏字段名单。`routes/` 和 `services/` 里一次都没出现过。

### B. 数据访问层（`src/data/ai-configs.ts`、`src/data/reindex-jobs.ts`）

`embed_config` 用 `onConflictDoUpdate` 的 upsert，没有「先查再判」。探测结果字段挡在**签名**上而不是注释上：写配置的两个函数只收 `ProviderInput`（`{ baseUrl, model, apiKey }`），能力位根本不在参数里，由函数自己从 `config_tests` 里那条匹配记录抄过去。这条在 `tests/config-endpoints.test.ts` 里正面打了一枪——`PUT /config/vision` 的请求体里塞 `jsonModeWorks: false, multiImageWorks: false`，响应回来仍然是真实探测的 `true / true`。

### C. 六个端点（20 条集成测试）

逐条对应完成标准的实测结果：

| 标准 | 实测 |
|---|---|
| 未配置时回显部署方默认值 | `source: "default"`、`apiKey: "****3344"`、能力位**全 null**（部署方那套也没有测试记录，不假设它支持什么） |
| 测试不通过是 200 | 替身回 401，响应 **200**，`ok: false`，`rawResponse` 在体里。只有请求体非法（缺 `baseUrl`、`baseUrl` 不是 http(s)）才 400 |
| 测试连接不改当前配置 | 测完再 `GET`，`source` 仍是 `default` |
| `CONFIG_TEST_REQUIRED` | 没有测试记录直接 `PUT` → 400；**baseUrl / model 都没变、只换了 key** 也照样 400（匹配带 key 指纹） |
| 脱敏串 = 不修改 | 回传 `****7788` + 改 model → 200，尾号不变；此前没配过 key 却传脱敏串 → 400（不静默存空 key） |
| `EMBED_DIM_TOO_SMALL` | 实测 512 维 → 400，`details: { nativeDim: 512, required: 1024 }` |
| `EMBED_MODEL_CHANGED` | 库里有向量时换模型 → **409**，`details: { currentModel, nextModel }`；带 `confirmReindex: true` 重发 → 200，`reindexEnqueued: 1`，队列里确实多了一条 pending。库里没有任何向量时**不拦**（没有东西要重算）；第一次配置不算换模型 |
| 403 | member 打 `GET/PUT /config/embed`、`POST /config/embed/test`、`POST /admin/reindex`、`GET /admin/reindex/status` 五个全 403 |
| 进度来自库 | 入队前 `{ running: false, total: 1, done: 0, stale: 1, failed: 0 }`，入队后 `running: true` 而 **`stale` 不变**——两个数说的是两件事，都对 |
| 重建幂等 | 连按两次 `POST /admin/reindex`：`enqueued` 1 → 0，队列里仍是一条 |

**「key 不出响应」不是单独一条用例**，是每条成功路径上的公共断言：`readJsonNoKeys()` 把响应体当字符串搜四把明文 key（部署方视觉/embedding、用户视觉/embedding），任何一把出现就红。这么写是因为只在一处验的话，下一个人给响应加个字段就漏了。另外直接 `select` 了 `user_ai_configs.vision_api_key_enc`，把 bytea 当 utf8 读也搜不到原文。

### D. 探测实现 —— 「`rawResponse` 不含 key」是怎么测的

这是本任务唯一一处「原样返回外部数据」和「key 不出响应」正面相撞的地方，所以没有用「我检查过出口只有一个」这种说法交差——那句话下一个人改一行就不成立了。做法是**复现真实的泄露形态再打**（`src/ai/probe.test.ts` 头四条）：

`error-handling.md §4` 明写某些中转服务会把 `Authorization` 头回显进错误体，而那恰好是**填错 key 拿 401** 时最容易发生的事，也正是测试连接最常触发的路径。于是用例让替身回一个真实形状的 401 体，里面 key 出现**两次**（一次在 `message` 的 "Incorrect API key provided: sk-…"，一次在 `error.request.headers.authorization`），然后五条断言连起来：

1. `requests[0].authorization === 'Bearer sk-proj-…7788'` —— **先证明明文真的发出去过**。少了这条，后面四条可能只是因为这次压根没发请求；
2. 泄露体里 `split(KEY).length - 1 === 2` —— 确认这一轮确实有两处可泄露；
3. `report.rawResponse` 里搜不到 KEY —— 一个字节都不剩；
4. `rawResponse` 里 `****7788` 出现**两次** —— 是**换成**脱敏串而不是删掉，用户得看得出「这里本来是你的 key」；
5. `report.rawResponse === leaked.split(KEY).join(MASKED)` —— **字节级全等**。这条同时钉死了另一半要求：除了 key 之外一个字节都没动，没截断、没包装成友好文案（`settings-ux.md §5`、完成标准 3）。

另外三条补住了出口的完整性：embedding 侧走的是 `rawError` 这条**另一个**出口，同样被替换；响应体里**没有** key 时原文一个字节不动（502 的 HTML 原样返回——抹 key 不能顺手删掉用户真正需要的那行错误）；**成功路径**的 `rawResponse` 也过同一个 `finish()`，验的是「没有第二条出口」。

脱敏用的是已有的 `lib/redact.ts` 的 `maskApiKey`，没有在探测里另写一遍。实现上 raw 字段只装**响应体**，请求头和请求对象从来没进过它们。

其余 8 条探测单测：第一次就打不通时**只发 1 次请求**（不拿用户的钱确认同一件事），能力位全 null；收到图但输出不合格时 `canReceiveImage: true` 而 `vocabCompliant` 是 **null 不是 false**（「拿不到可校验字段」和「字段不在词表里」是两件事，报 false 会让用户跑去改提示词）；三次都成功时断言基线那次**不开** `response_format`、另一次开了、多图那次 content 里真的有 **2** 个 `image_url`，且三次 URL 是同一个端点（没有按供应商分叉的第二条路径）；标签越界时 `vocabCompliant: false` 但仍 `ok: true`，判定复用 `src/vocab.ts` 那份适配器——另写一套的话，「测试连接说能用、打标时标签全被丢掉」不会被任何测试抓住。Embedding 侧钉的是「中转把 `dimensions` 忽略掉」这一路：只看状态码会把它判成生效，然后运行时拿一个没归一化的长向量去写库，不报错、只是搜索悄悄变差。

### 送去实测的那张图：选了哪张、为什么

`src/ai/probe-image.ts` 里一个 base64 常量，**PNG，384×384，9675 字节**，sha256 `c9d4c5c6744e61633558949f084e6a29521cb0a7ea8e2434878f19c3827a1032`（验收时把常量解码回 PNG 重算过，和 `PROBE_IMAGE_SHA256` 一致，并**打开看过渲染结果**：卡通猫、半睁的死鱼眼、黑眼圈、平嘴、桌沿线，字幕「今天不想上班」六个字完整成形，没有豆腐块）。生成脚本留在 `scripts/gen-probe-image.ts`。

为什么是这张：

- **它是一张真能被打出标签的图**。§9.7 要求发内置测试图 + **正式的打标提示词**，`vocabCompliant` 判的是返回标签落在词表内。噪声图或纯色块会让一个好模型也返回空字段，那正好长得像 `ai-providers.md §3` 的第三种拒绝形态——**测试连接会把能用的供应商判成不能用**。这张图是对着 `shared/vocab/vocab.json` 设计的，五个字段每个都有闭集里的词可落：主体（猫、文字）、情绪（疲惫 / 生无可恋 / 无奈）、场景（上班摸鱼 / 加班 / 周一）、风格（手绘 / 简笔画 / 带字幕），OCR 文本就是那六个字。
- **编进源码，不读文件系统**。不引用 `docs/fixtures/`——那批是测试与评测用的，`huge.png` 还被 `.gitignore` 排着（`docs/fixtures.md`），运行时依赖它等于依赖一个不保证存在的目录。另一个理由是部署：根 `Dockerfile` 的最终镜像只 COPY `node_modules` / `dist` / `migrations` / `public` 和 `/shared`，**新加一个 `api/assets/` 不会进镜像**，而改 Dockerfile 属于部署事项、归总管（`AGENTS.md §3`）。编进 `dist/` 的常量零部署改动，也不可能在运行时「文件不见了」。
- **纯矢量、无人脸、无版权素材**：探测图自己被判 `AI_REFUSED` 的话整个测试连接就废了，这条比画得好看重要。
- **384×384 / 9675 字节**是按「一次探测发三遍、其中一遍发两张」定的：全程约 40KB base64，探测一次的成本可以忽略，分辨率又够模型读清那六个字。
- 中文字幕是有意的：本项目的图基本都带中文，用英文图测等于测了一个和生产不一样的东西。

⚠️ 一个给下一个人的提醒：字幕是 SVG `<text>` + 系统字体（`Microsoft YaHei, SimHei, Noto Sans CJK SC`）渲染的，**重跑生成脚本的产物依赖本机装了哪套中文字体**，换台机器重跑很可能得到不同的 sha256，没有中文字体的机器上还会渲染成豆腐块。运行时不受影响（走的是已提交的 base64 常量）；但**改图必须重跑脚本、在图里确认字还在、再把新的 sha256 一起提交**，脚本文件头里写了这件事。

### E. 运行时接入 —— `isVisionConfigured()` 是怎么测的

三个落点都改成了「DB 优先、环境变量兜底」，`hyde.ts` 接回了 `resolveVisionConfig(actorId)`（匿名搜索没有「本人」，那一支仍落到部署方默认值）。解析只认 `verified_at` 非空的配置行。

`queue/worker.ts` 那个全局判断改成了「部署方配了 **或** 库里有任何一条通过测试的用户配置」。**这条 bug 的表现是没有表现**——不报错、不告警、不重试，只是那些图永远停在 pending，所以断言不能只看「跑通了」。测法（`tests/config-user-vision.test.ts`，6 条）：

1. **把部署方那套彻底清空**——`DEFAULT_VISION_*` 与 `DEFAULT_EMBED_*` 六个变量在任何 `src` 导入**之前**置空（`env.ts` 首次 import 就把值冻住，同一个文件里没法既有配置又没配置，所以单开一个文件，同 `tag-queue-unconfigured.test.ts`）。这样「部署方兜底」这条路被物理切断，剩下的只可能来自库。
2. 三条直接打函数：两边都没有 → `false`；**有一条通过测试的用户配置 → `true`（这条就是改之前的 bug，改之前必红）**；`verified_at` 为 null 的行**不算数** → `false`，且 `resolveVisionConfig()` 也返回 null（「值不值得取任务」和「能不能进生产打标」必须是同一条判据，否则 worker 会为一条永远解析不出来的配置不停空取）。
3. **端到端跑真 worker**：起 `startTagWorker()`，塞一张真图进队列，轮询到 `tag_jobs.status === 'done'`、`last_error` 为 null、`memes.tag_status === 'ok'`。没修之前这里会**超时**而不是失败——worker 压根不取任务，这正是线上的症状。
4. **断言发出去的是哪一把 key**：抓所有出站请求的 `Authorization` 头，`expect(new Set(authHeaders)).toEqual(new Set(['Bearer sk-user-own-key-…']))`。只断言 `tagStatus: 'ok'` 是不够的——**拿别人的 key 跑通也一样是 ok**，这条才是「用他自己的 key 打标」的硬证据。同一条里还验了 `vision_model` 落的是用户填的那个模型名，以及 embedding 没配时 `embedding` 为 null 而打标照常完成（正常降级，不是失败）。
5. **没配的那个用户仍然 `not_configured`**，不受别人配置的影响——`isVisionConfigured()` 为真只说明「值得去取任务」，取到之后还要按上传者逐条解析。这条防的是把全局判断当成逐条判断用。

### F. 重建索引（8 条集成测试）

独立的 `reindex_jobs` 表和**独立的 worker**，没有塞进 `tag_jobs`（那张表 `meme_id` 上有唯一索引，一条重算任务会和同一张图的待打标任务互相踢掉）。并发全站上限 4，不按用户分组。两个 worker 在 `server.ts` 里都是无条件启动、停机时 `Promise.allSettled` **并行**收尾（串行等于把两个超时上限加起来，停机时间平白翻倍）。

- **「重算不许重跑视觉」是用出站请求验的，不是读代码**：跑完一轮重算后断言 `calledPaths.every(p => p.endsWith('/v1/embeddings'))`，一次 `chat/completions` 都没发过。同一条用例逐个断言 `description` / `tags` / `vision_model` / `search_text` **四个字段一个字没变**——「把用户手工编辑过的字段覆盖掉」才是这条规则真正防的事故。
- 排队期间图被软删 → `gone` 而不是 failed，且**一个请求都没发**；没配 embedding 通道 → `not_configured`，不消费重试次数。
- 入队：软删的不入队；已经是当前模型的不入队；没配 embedding 模型时整个操作是空操作（不排一堆必然失败的任务）。
- **完成即删行**：worker 跑空队列后 `reindex_jobs` 里 0 行。留着 done 记录的话，这张图下一次换模型时会被 `onConflictDoNothing` **静默**跳过。
- **搜索侧降级**：有未完成任务时 `degraded: true` **且结果一条不少**（两条同时断言——只验 degraded 的话，把搜索改成直接返回空也能过）；队列空时 `degraded: false`。判断用的是 `hasUnfinishedReindexJobs()`（`limit 1`，命中 claim 索引，不是全表 count），而且它是**和三路召回塞进同一个 `Promise.allSettled`** 的第四个元素，不串在前面也不串在后面——再便宜的查询串行也是给每个搜索请求加一个往返。这条查询自己失败时按「没在重算」处理并打 warn：为了一个展示用的字段让整次搜索 500 是不划算的。

`degraded` 没有拆成两个字段（向量路缺席 / 正在重算），理由写在 `services/search.ts` 的类型注释里：前端的动作是同一个（挂一条「结果可能不全」），拆开会让「两个都为真」时的文案变成一道组合题；具体是哪种原因写在日志里。
