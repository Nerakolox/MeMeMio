# 人工补完标签之后，怎么离开待处理列表

**状态**：`planning`（**要先裁定才能动手**，见 §2）｜ **性质**：**跨端**（契约先行：先改 SPEC §6.4.1，再改两端）｜ 开于 2026-09-24

## 1. 为什么要做

**SPEC 自己跟自己矛盾，而其中一半已经被实现了。**

- [§6.6.2](../spec/06-endpoints.md) 写着 `needs_manual` 的图「**两条路都通**：人工用 `PATCH` 补，或按当前提示词重跑模型」。
- [§6.4.1](../spec/06-endpoints.md) 的写入清单里**没有 `tag_status`**：`PATCH` 成功后那张图的 `tag_status` 仍是 `needs_manual`。
- [§6.6.2](../spec/06-endpoints.md) 那张表还说人工补的车**不花钱**、模型重跑花上传者的钱——**语义上完全正确，但走完这条「不花钱」的路，图并没有离开待处理列表**。

于是「人工补」这条路的真实表现是：补完标签 → 保存成功 → 那张图还在「需人工」列表里 → `GET /memes/tag-status` 的 `counts.needsManual` 一个不减。**对用户来说就是没保存成功。** 他能做的只有再点一次（同样不减），或者改成去花上传者的钱重跑模型——那正好是这一节想避免的。

这不是新需求，是 [浏览页图片操作](2026-09-19-browse-meme-actions.md) 的 web 执行者在验收时按规则第 7 条报上来的，当时它**没有自行加这个写入**（对：写入清单里没有的字段不该由实现补上）。2026-09-24 任务板整顿核对状态时总管确认了这处矛盾，**并确认它至今没有任何任务认领**。

**为什么它比看起来重要**：`needs_manual` 是**唯一会越积越多**的状态。打标失败不会自愈，而这张列表是目前唯一能看见它们的入口。出口不通，这个列表就只会变长——`refused` 还没接上（[§9.5](../spec/09-decisions.md)），终局失败全落在这里。

## 2. 待产品负责人裁定

**三个走法，推荐 A。**

| 方案 | 做法 | 代价 |
|---|---|---|
| **A（推荐）** | `PATCH` 成功且这张图当前是 `needs_manual` → 在同一条 `UPDATE` 里把 `tag_status` 置回 `ok` | 人工可能只补了描述、七个维度仍空着，而 `ok` 的字面意思是「打标完成」。代价可用一句话交代：`ok` 在这一节的含义是「不需要人再管了」，人补过就有 `edited_by` 记着，不是没有痕迹 |
| B | 新增第五个取值 `edited` | 四个取值是 [§5.2.3](../spec/05-data-models.md) 定死的，`refused` 到现在都还不可达（[§9.5](../spec/09-decisions.md)）。为「人补过了」再加一个状态，是把状态机的复杂度花在**不产生新信息**的地方——那件事 `edited_by` 已经记了 |
| C | 不动契约，让 web 保存成功后自己把这条从待处理列表里移除 | **最坏**：刷新就回来，`counts.needsManual` 也不减，等于把契约矛盾藏进前端。前端的乐观移除还会和 [state-navigation.md §8](../web/agents/rules/state-navigation.md) 的「不做乐观更新」打架 |

**A 同时修掉一个措辞问题**：§6.6.2 那句「两条路都通」在 A 之下才为真。**不许只改前端让它「看起来通了」**——按 [SPEC §8.4](../spec/08-collaboration.md)，契约与实现不一致时记差异、改契约，不拿实现去凑文档。

## 3. 做完的标准

- 一张 `needs_manual` 的图，人工 `PATCH` 过至少一个字段之后：`GET /memes?tagStatus=needs_manual` 里没有它，`GET /memes/tag-status` 的 `counts.needsManual` **减 1**。
- 一张 `needs_manual` 的图，**空 PATCH**（没有任何字段变化、请求本来就不发）之后仍然在列表里。
- 一张 `ok` 的图人工编辑后**不受影响**（`tag_status` 已经是 `ok`，写入是幂等的）。
- web：保存成功后那张卡**当场**从待处理列表消失、计数跟着减，不需要刷新，也不需要重拉整页。
- 有一条测试钉住「`edited_by` 与 `tag_status` 在同一条 UPDATE 里」，拆成两条语句中间崩掉会留下「人补过但仍在待处理列表」的半截状态。

## 4. 两端各自要改什么

### api 端

| # | 改什么 | 位置 |
|---|---|---|
| 1 | `PATCH` 的写入清单加 `tag_status`：仅当**当前值**是 `needs_manual` 时置 `ok`，与 `edited_by` / `edited_at` 同一条语句 | `routes/memes.ts`、`data/memes.ts` 的更新语句 |
| 2 | 触发面收在**同一个路由**里，不要做成独立的「标记已处理」端点——§6.6.2 那句「不要在 §6.4 之外另造一个『重试』端点」同样适用于这里，同一个语义不能有两条实现 | 同上 |

**陷阱**：条件必须是「**当前值**是 `needs_manual`」而不是「已提交的字段里有变化」。后者在空 PATCH 上会误判，而「编辑过的图被 `retag` 跳过」那条取舍（§6.4.3）正是靠 `edited_by` 判断的，**两件事的判据不同，别合并**。同理，`ok` 的图被编辑后不要去动它的 `tag_status`——写入要幂等。

### web 端

| # | 改什么 | 位置 |
|---|---|---|
| 1 | 保存成功后按响应里的 `tagStatus` 决定那张卡还在不在当前列表：待处理视图里它就是「已离开」，从列表移除并递减计数 | `features/manage/use-meme-edit.ts`、`features/manage/` 的列表更新 |
| 2 | 提示语要说清它去哪了（「已补完，离开待处理列表」），而不是只说「已保存」——用户在这个页面上的心智是「把这张图处理掉」 | 同上 |

**不做乐观更新**（[state-navigation.md §8](../web/agents/rules/state-navigation.md)）：移除发生在服务端确认之后，与删除那条路径一致。
