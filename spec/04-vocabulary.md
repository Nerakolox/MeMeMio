# §4 固定标签词表

[返回索引](INDEX.md)

## §4.1 为什么是硬性要求

打标模型如果自由生成标签，「无语 / 无奈 / 服了」会变成三个互不相通的标签，标签检索直接失效。

在本项目这个问题更严重，有两个叠加原因：

- **视觉模型由用户各自配置**，系统完全无法预知会收到什么模型的输出
- **双通道降级**意味着同一张图可能由主通道或副通道打标，两边的词汇必须对齐，否则降级本身就制造了不一致

所以词表不是「好习惯」，是**唯一能保证不同模型输出可比的手段**。提示词里给死一份清单，模型只能从里面挑；不在清单内的输出按 `AI_INVALID_OUTPUT` 处理（见 [§2.4](02-errors.md)）。

## §4.2 主源

词表本体在 **`shared/vocab/vocab.json`**，本章只定义规则。

之所以主源是代码不是文档：词表同时被三处消费——打标提示词、输出校验、前端筛选 UI。放在 SPEC 里维护几百个词，必然和代码漂移。这与「OpenAPI 是派生物」方向相反，但道理相同：同一事实只有一个可编辑的地方。

当前 `vocab.json` 为 **v0.2.0，状态 `proposed`**。它是一份可用的起草版本，具体词条需由 [评测集任务](../joint-tasks/2026-09-13-eval-set.md) 和 [词表任务](../joint-tasks/2026-09-13-vocab-v1.md) 验证后才转 `accepted`。在此之前可以实现消费词表的代码，但不要基于具体词条做硬编码分支。

## §4.3 结构与规则

**五个语义维度 + 一个内容维度**，对应 `memes` 的六个数组字段：

| 字段 | 维度 | 回答的问题 | 判据 |
|---|---|---|---|
| `expressions[]` | 面部表情 | 脸上是什么样 | **视觉事实**，看图就能确定 |
| `emotions[]` | 情绪 | 图里的人 / 动物在感受什么 | 内心状态，由表情 + 文字共同支撑 |
| `tones[]` | 表达语气 | 这张图**怎么**说话 | 说法的调子，与说的内容无关 |
| `purposes[]` | 聊天用途 | 发这张图**想完成什么交流动作** | 发送者的意图 |
| `scenes[]` | 生活情境 | 和什么具体事情有关 | 上班、考试、没钱这类现实场合 |
| `tags[]` | 主体与风格 | 图里是什么、长什么样 | 视觉事实 |

`tags` 在 JSON 里按 `subject` / `style` 分组，仅供前端筛选 UI 分区展示；**存进数据库时是扁平数组**，校验时也扁平匹配。

`purposes` 在起草阶段按八组组织（开场与收尾 / 回应与表态 / 理解与追问 / 请求与推动 / 关系互动 / 争论与不满 / 自我表达 / 旁观与反应），但 JSON 里是**一个扁平列表**，分组只存在于注释和 UI 排序里，不进数据库、不进校验。

### §4.3.1 维度之间不能互相推导

> ⚠️ **这是拆成五个维度的全部理由。** 合成一个维度时，模型会把最容易看见的那个当成全部。

一张微笑角色配「你说得都对」的图，正确的标注是：

| 维度 | 值 | 为什么 |
|---|---|---|
| `expressions` | `微笑` | 脸上确实在笑，这是视觉事实 |
| `emotions` | *（空）* | 笑不等于开心。这张图没有任何证据说明他此刻的内心状态 |
| `tones` | `敷衍`、`阴阳怪气` | 「你说得都对」配微笑，调子是不想接着聊 |
| `purposes` | `表面附和` | 他做的交流动作是附和，但不是赞同 |
| `scenes` | *（空）* | 看不出和什么现实场合有关 |

由此得出三条硬规则：

- **微笑 ≠ 开心。** `expressions` 是脸，`emotions` 是心。只有脸时只填 `expressions`。
- **肯定句 ≠ 赞同。** `purposes` 是发送者要达成的交流动作，不是字面意思。「你说得都对」的用途是 `表面附和`，不是 `赞同`。
- **敷衍 ≠ 阴阳怪气，两个都要留着。** 敷衍是不想接着聊，阴阳怪气是说反话。它们经常同时出现，但不是一回事，合并会让两类图互相污染。

**证据不足就留空，不要靠推导补齐。** 空数组是合法且常见的结果；猜出来的标签比没有标签更坏——它会让检索把不相干的图排到前面，而用户无从得知这个标签是猜的。

### §4.3.2 词条规则

- **中文，不混英文。** 双通道的词汇对齐要求决定了这一条不能例外。
- **单个词条不超过 6 字**，不成句。「表面同意实际很无语」是描述不是标签，它属于 `description` 字段。单字名词（`猫`、`狗`）只在 `tags.subject` 里允许。
- **同义词只留一个。** 新增前先搜已有词表，「无奈」和「无语」这类要选定一个并在 `aliases` 里登记另一个，供模型输出归一化。
- **一个词只能属于一个维度。** `aliases` 的键也不能和任何维度的词条重名，否则归一化会把词映射到自己。这两条由 `api/src/vocab.test.ts` 守住。
- **粒度对齐用途。** `scenes` 的粒度是「这张图在讲什么现实场合」；「我现在想干什么」属于 `purposes`。**v0.1.0 把这两件事混在 `scenes` 里，v0.2.0 拆开了。**
- **每张图每个维度取 0–4 个**，不要求填满，宁缺毋滥。其中 **`tones` 和 `purposes` 起步只取 0–2 个最有把握的**——这两维靠推断，给的额度越大模型越会硬凑。
- **只收类别，不收具体梗名。** `动漫角色`、`明星` 这类类别词可以进；`奶龙`、`哈基米`、`耄耋` 这类具体梗名**永远不进**。理由是本词表是**闭集**——它存在的意义就是有限且稳定，才能让不同模型的输出可比；梗名是每月都在长的开集，塞进来会毁掉这一点，而且每加一个都要走一次 §4.4 的不兼容变更流程。梗名走别名层，见 [§9.18](09-decisions.md)。

## §4.4 变更流程

> ⚠️ **词表变更不是兼容变更。** 删除或重命名一个标签会让已有记录的该标签失去意义。

| 变更 | 影响 | 要求 |
|---|---|---|
| 新增词条 | 旧记录不会有这个标签，除非重打标 | 可直接合入；在任务里说明是否需要批量重打标 |
| 登记 alias | 无破坏性 | 可直接合入 |
| 重命名词条 | 旧记录仍是旧值 | 必须附带数据迁移，同时更新 `vocab.json` 和存量数组字段 |
| 删除词条 | 旧记录变成非法值 | 必须先迁移到替代词条或清除，不能只改 JSON |
| **移动词条到别的维度** | 旧记录的值留在旧列里，新列是空的 | 同时要 DDL 迁移（新列）和数据迁移（搬值），按删除 + 新增处理 |

任何变更都要 bump `vocab.json` 的 `version`，并在 [词表任务](../joint-tasks/2026-09-13-vocab-v1.md) 或其后续任务里记录变更原因与影响的记录数。

**改词表后必须跑评测集。** 词表是打标质量的地基，改动的影响不能靠看几张图判断，见 `agents/rules/collaboration.md`。

## §4.5 校验

服务端在写入 `memes` 前校验六个数组的每个元素都在对应维度的词表内（含 alias 归一化）。**归一化只走一跳**：`aliases` 的值必须是词条本身，不能是另一个 alias 的键。校验不通过按 [§2.4](02-errors.md) 的 `AI_INVALID_OUTPUT` 处理，重试一次后降级。

**人工编辑也走同一套校验。** 用户在管理界面加标签时，只能从词表里选，不能自由输入——否则人工编辑会绕过词表约束，制造出模型永远不会产生的标签值。

**「同一套校验」说的是词表约束，不是错误码。** 模型输出不在词表内是 `AI_INVALID_OUTPUT`，会走重试与降级（[§2.4](02-errors.md)）；人工编辑不在词表内是 `VALIDATION_FAILED`（[§2.2](02-errors.md)），客户端展示「请从列表里选」。两者混用的表现是编辑失败时前端去等一个永远不会来的 AI 降级。见 [§6.4.1](06-endpoints.md#641-patch-memesid-的语义)。

前端的标签选择控件从 `vocab.json` 读取选项，不维护第二份列表。
