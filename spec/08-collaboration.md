# §8 协作

[返回索引](INDEX.md)

本章定义契约怎么改、任务怎么落地、旧文档去哪。团队通用的写作与交付规则在 [`agents/rules/`](../agents/rules/INDEX.md)，本章只讲 SPEC 相关的部分。

## §8.1 改契约的顺序

**先改 SPEC，再改代码。** 顺序反过来的结果是两端各自实现了一半，然后回头补一份追认现状的文档——那份文档没有约束力。

| 步骤 | 做什么 |
|---|---|
| 1 | 在对应章节写下改动，状态标 `proposed` |
| 2 | 如果影响另一端，开 [joint-task](../joint-tasks/README.md) |
| 3 | 两端确认后转 `accepted`，此时才开始写代码 |
| 4 | 实现完成并通过验证后转 `stable` |

状态定义见 [§0.3](00-overview.md)。`proposed` 的条目可以实现，但不要在它上面建更多东西——它还可能被推翻。

## §8.2 什么时候必须开 joint-task

只要一个改动需要两端同时动，就开一个。判断标准不是「工作量大不大」，是**「一端先合入会不会让另一端坏掉」**。

必须开的情况：

- 接口的请求或响应结构变化
- 新增或修改错误码，且前端需要为它分支
- `vocab.json` 的词条增删改（前端筛选 UI 和后端校验同时消费）
- SSE 事件类型或字段变化
- 权限矩阵变化

不必开的情况：一端内部的重构、纯样式调整、不改变对外行为的性能优化。

任务文件放 `joint-tasks/`，命名 `YYYY-MM-DD-主题.md`。任务完成后移到 `_archive/joint-tasks/`，**不要删除**——它记录了这个决定是怎么来的。

## §8.3 兼容与不兼容

| 类型 | 例 | 处理 |
|---|---|---|
| 兼容 | 新增可选字段、新增筛选参数、新增错误码（前端有默认分支） | 直接改，bump patch |
| 不兼容 | 删字段、改字段语义、改错误码含义、词表删词或重命名 | 必须开 joint-task，bump minor，说明迁移方案 |

**词表变更默认按不兼容处理。** 理由见 [§4.4](04-vocabulary.md)——删一个标签不会让代码报错，只会让存量记录悄悄失去意义。

前后端同域同时部署，**不做 API 版本并存**。`/api/v1` 里的 `v1` 是留给将来真的需要时用的，首期不会出现 `v2`。这意味着不兼容变更必须两端一起上线，这也是 §8.2 存在的原因。

## §8.4 SPEC 与代码冲突时

以 SPEC 为准，但**先确认 SPEC 没写错**。

发现不一致时按这个顺序处理：

1. 判断哪边是对的——SPEC 落后于一个已验证的现实，也是常见情况
2. 如果 SPEC 错了，先改 SPEC，在 [§9](09-decisions.md) 补一条记录说明为什么原来的写法不成立
3. 如果代码错了，改代码，不改 SPEC

不允许的做法是「代码这样写了，就把 SPEC 改成这样」而不说明理由。那等于取消了 SPEC 的作用。

类型与语义的分工见 [§0.2](00-overview.md)：Hono RPC 推导出的类型保证**形状**对，SPEC 保证**含义**对。类型检查通过不等于契约遵守——`tagStatus: string` 编译得过，但它必须是 §5.2.3 那四个值之一。

## §8.5 归档

| 内容 | 去处 |
|---|---|
| 完成的 joint-task | `_archive/joint-tasks/` |
| 被拆分或取代的长文档 | `_archive/`，文件名带日期与原因 |
| 被推翻的决策 | **留在 [§9](09-decisions.md)**，状态改 `deprecated`，补写为什么推翻 |

被推翻的决策不归档、不删除。下一个人会重新想到那个方案，§9 里那条 `deprecated` 记录就是为了让他省下重走一遍的时间。

当前 `_archive/2026-09-13-项目介绍-拆分前快照.md` 是本仓库全部内容的来源文档，拆分前的完整论证在那里。它已被 SPEC 和 `docs/` 取代，**不再更新**；如果发现 SPEC 与它冲突，以 SPEC 为准。
