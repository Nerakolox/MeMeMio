# 检索

背景与论证见 [SPEC §9.10](../../../spec/09-decisions.md)。响应结构见 [SPEC §6.3](../../../spec/06-endpoints.md)。

**本文的参数都是实现细节，调它们不用改 SPEC；但响应里多一个字段或某字段含义变了，先改 SPEC。**

## 1. 三路并行

```
q → HyDE 改写
  ├─ pg_trgm 子串匹配（ocr_text + description，外加 original_filename）  → top 50
  ├─ 标签过滤（七个维度任一命中）                  → top 50
  └─ 向量 HNSW（cosine，按 embed_model 过滤）      → top 50
  → RRF 融合 → 前 N 条（`GET /memes` 缺省 40，`GET /search` 冻结在 50，上限都是 100）
```

每路的 `top 50` 是 `PATH_LIMIT`，**一次性检索的深度就是它**。翻页会把深度逐步放大到重扫三路，
那条规则在 §6——改动深度等于同时改 `ef_search`（下面的推导），**只有一处可以改**。

三路**并行发起**，不串行。总延迟取决于最慢的那路，串行会把它们加起来。

**任意一路失败不阻断其余。** 向量路失败（embedding 未配置、重建索引中、供应商挂了）时响应带 `degraded: true`，前端提示结果可能不全但不阻断搜索。

三条各自的约束写在旁边的括号里，但有两条是**改错了不报错**的，单独说：

- **文本路不匹配 `search_text`**（SPEC §9.21）。`search_text` 里拼着七个数组的标签值，让 trgm 也匹配它就等于同一个信号被文本路和标签路各计一次分——靠标签沾边的图会压过原文精确命中的图。`original_filename` 反过来：它**参与 trgm 但不进 `search_text`**（SPEC §5.2.3），所以要单独提出来匹配。
- **向量路按 `embed_model` 过滤**（SPEC §9.20）。换模型期间库里同时存在两代向量，而它们不在同一个空间里，余弦距离只是噪声。过滤掉旧的那批会让召回变少，所以这条**必须和 `degraded: true` 一起出现**，否则用户看到的是一个静默变差的搜索。

## 2. RRF

```
score(doc) = Σ over 通路  1 / (k + rank(doc))
```

`k` 取 60（业界通用起点）。调它之前先跑[评测集](../../../docs/eval.md)。

**不要改成加权求和。** 向量相似度和 `pg_trgm` 相似度量纲完全不同，权重根本调不出来；而且管理员换一次 embedding 模型，相似度的绝对值分布就整体漂移一次，写死的阈值又得重调一轮。RRF 只看排名，换模型不受影响。

每个 doc 记录它被哪几路召回，作为 `matchedBy` 返回。**`matchedBy` 不参与排序**，只是给前端做轻量提示。

## 3. HyDE

用户输入「今天真的不想上班」是一句短口语，库里存的是「一只趴在桌上的猫，看起来非常疲惫……」这样的长描述。**短句对长文的向量匹配效果一般**，所以先把查询改写成一句同样风格的描述。

- 用**搜索者本人**配置的视觉通道，纯文本调用
- 改写产出是文本，再交给全站统一的 Embedding 编码——所以不存在跨模型不兼容问题
- **失败不阻断**：`rewritten` 返回 `null`，用原查询继续走三路
- 必须有超时（建议 2s）。改写是锦上添花，**不值得让搜索等它**

**向量路编码的是「原查询 + 改写」，不是只有改写**（`services/search.ts` 的 `embedInput`，原查询在前）。只编码改写等于把召回押在一次模型猜测上：它最爱丢的正是否定和语气，「不要真人」被改写成「一个真人在摆手」之后，向量路会召回一整屏用户明说不要的图，而**全程没有任何地方会报错**。原查询留在输入里，至少那几个字还在。顺序也是这个理由——截断发生在尾部，该活下来的是用户真正打的字。

OCR 路和标签路吃**原查询**，不吃改写：它们是精确匹配，喂一段模型编的描述只会让子串匹配失准。

改写结果返回给前端是为了让用户理解「为什么搜出这些」，前端可以不展示。

## 4. instruct 前缀是非对称的

Qwen3-Embedding 一类 instruction-aware 模型的正确用法：

```
查询侧：Instruct: {任务描述}\nQuery: 今天真的不想上班
文档侧：一只趴在桌上的猫，看起来非常疲惫……（原文，无前缀）
```

**两边都加或都不加会损失几个点。**

这条只对 instruction-aware 模型成立。**跟随 Embedding 配置，不要写死在代码里**——管理员换成别的模型时这个行为应该跟着变。

## 5. 中文全文检索

用 `pg_trgm` 子串匹配，**不装 `zhparser` / `pg_jieba`**。

PostgreSQL 默认的 `to_tsvector` 不分中文词，直接用等于没用。两条路里选 `pg_trgm` 的理由：OCR 精确搜索的本质就是子串匹配，够用，而且不用在部署环境里折腾扩展——[部署约束](../../../docs/deployment.md)里已经有 pgvector 一个扩展要管了。

## 6. 一次检索是一个快照

`GET /memes?q=` **可以翻页**，靠的是把整次检索冻下来（SPEC §6.3.1）。实现在
`services/search-snapshot.ts`（编排）+ `data/search-snapshots.ts`（表），新表 `search_snapshots`。

**「搜索不分页」这条立场 2026-09-26 已被推翻**，理由见 [SPEC §9.29](../../../spec/09-decisions.md)。
`GET /search` 仍然不分页——它是冻结的兼容入口，`nextCursor` 恒为 `null`（§6.3.3），
**新能力一律只加在 `GET /memes` 上**。

### 6.1 融合分不能当游标

游标指向的是「哪一次快照的第几页」，**不是名次**。名次会随库里的增删而移动：第 40 名和第
41 名换了位置，下一次翻页就会重复一条或漏一条，而两次响应各自都是对的、没有任何报错。

所以首屏把三样东西一起落库：

| 冻住的东西 | 不冻的后果 |
|---|---|
| 三路候选名单 | 重跑三路 → 名单变化 → 页边界漂移 |
| HyDE 改写 + 查询向量 | 改写逐次不同 → 召回池变化；而且**滚一屏一次 LLM 调用** |
| 时点 `asOf` | 翻页途中上传的新图会从后面的页里冒出来 |

`degraded` / `rewritten` 也一起冻住：一次检索只有一个答案，翻着翻着提示语变了，用户会以为出了事。

同一次检索的后续页**不再调任何外部 AI**。这是快照存在的两个理由之一（另一个是排序稳定）——
`tests/search-vector.test.ts` 用假服务数调用次数钉住它。

### 6.2 深扫只能追加，不能重排

池子凑不满一页时把深度翻一倍重扫三路。**每路名单一旦定下前缀就不再改，深扫只把没见过的新 id
按新扫里的相对顺序接在后面**（`lib/ranked-append.ts`）。

理由是实测的：同一查询在 `ef_search=40` 与 `=100` 下返回的**集合不同**（40 条 vs 50 条）。
按新深度整体重排会让**已经发出去的页边界移动**，重复与漏正落在接缝上。追加则保证已发出项的
路径排名不变 → RRF 分不变 → 新旧页天然对齐。

深度翻倍与 `ef_search` 是绑定的（`efSearchFor`，见 `data/search.ts`），所以：

- 每次翻倍都按**新深度**重扫三路，trgm 路的排序代价同步上涨；
- **上限是 `MAX_PREFETCH_DEPTH = 400`**（`services/search-snapshot.ts`）。再翻一倍是 800，
  `ef_search` 取 800 × 2 = 1600 会被 pgvector **直接拒掉**（不是截断），表现是滚到深处的
  那一次请求整个 500。到达上限的表现是 `nextCursor: null`，**不是错误**；
- 三路一条新 id 都给不出来时也可以停（`saturated`）。这是「到头了」的判据，**允许提前停**：
  理论上更深的扫描还能挖出新东西，而提前停的代价只是「翻不到那么深」，不重复、不漏、不报错。

**筛得越窄越早到底**（SPEC §6.3.1）。空页 + `nextCursor: null` 是正常的到顶，不是 404。

### 6.3 已发出的页原样重放

页一旦发出去就存进快照（`{ids, more}[]`），同一个游标重放多少次都得到同一页——客户端在
响应丢失后重试不会跳页。所以 `more` 要存进那一页里，**不能靠重算猜**。

### 6.4 游标

`s1|<快照 id>|<页号>` 的 base64url。三条纪律：

- **存进去的形状一改，版本号就 +1。** 旧游标一律解析失败 → `VALIDATION_FAILED` → 客户端丢掉
  游标回第一页。这是一条故意的断路：解析器只读它认识的字段，多出来的新字段会被静默丢掉，
  而丢掉的若是筛选条件，表现是「结果里混进了我筛掉的东西」，不报错。
- **坏了、过期了、别人的，三种同一个错误码。** 客户端的动作是同一个（SPEC §1.3）。
  **不静默返回第一页**——那在无限滚动里等于把第一页追加到已渲染列表后面，屏幕上凭空多一份重复。
- **游标是别人给的也要挡。** 快照里冻着 `actorId`（`favorited` / `uploader=me` 要它），拿别人的
  游标翻页等于**按别人的筛选条件**查，客户端看不出错。报 `VALIDATION_FAILED` 而不是 `FORBIDDEN`：
  对客户端这仍然是「这个游标不能用」。

### 6.5 过期与清理

滑动 TTL **30 分钟，从最后一次用到它算起**（每次翻页续期）。固定 TTL 会让「慢慢滚了半小时」
的人在滚到一半时被判过期，而他什么也没做错。

清理挂在定时任务上（`queue/cleanup.ts`，[queue.md](queue.md) §6），5 分钟扫一遍过期行。
读路径的过期判据与删除的判据是同一条，所以没什么可删的还在被用。

## 7. 搜索时不打标

搜索路径上只有 HyDE 那一次纯文本 LLM 调用，**不调视觉模型**，也不写 `memes`。

**唯一会写库的地方是快照**（§6）：`GET /memes?q=` 首屏在有下一页时插一行，翻页时续一次期。
那是分页的实现，不是检索本身——`GET /search` 不落快照（否则首页每搜一次涨一行），
`GET /memes?q=` 没有下一页时也不落（没有游标就没有人引用它）。

语义理解的成本发生在入库。这是延迟和成本能同时压下来的关键，[产品定位](../../../docs/product.md)的核心之一。

## 8. 改了检索要跑评测集

改 RRF 的 `k`、改任一路的召回条数、改 HyDE 提示词、改 instruct 模板——**都要跑[评测集](../../../docs/eval.md)**。

主指标是 `recall@5`。`precision@5` 比 `recall@50` 重要得多：用户只看前几个，第 30 位和没搜到没有区别。

**带筛的检索要单独看一组。** 评测集如果只有「干净查询 → 全库检索」那一组，就永远测不到带筛那段——
而带筛恰恰是召回最容易归零的地方：后置过滤的产出约等于 `ef_search × 选择率`，选择率掉到 3% 时
`ef_search=100` 下的向量路**返回 1 条**（真表实测，见 `data/search.ts` 的 `vectorPathCandidates`）。
那一组要带上一个窄筛选（比如单个低频标签），指标仍然是 `recall@5`，**和全库那一组分开记分**——
合在一起的话，窄筛那一组的塌陷会被全库的漂亮数字平均掉。
