# 检索

背景与论证见 [SPEC §9.10](../../../spec/09-decisions.md)。响应结构见 [SPEC §6.3](../../../spec/06-endpoints.md)。

**本文的参数都是实现细节，调它们不用改 SPEC；但响应里多一个字段或某字段含义变了，先改 SPEC。**

## 1. 三路并行

```
q → HyDE 改写
  ├─ pg_trgm 子串匹配（ocr_text + description，外加 original_filename）  → top 50
  ├─ 标签过滤（六个维度任一命中）                  → top 50
  └─ 向量 HNSW（cosine，按 embed_model 过滤）      → top 50
  → RRF 融合 → 前 N 条（默认 50，最大 100）
```

三路**并行发起**，不串行。总延迟取决于最慢的那路，串行会把它们加起来。

**任意一路失败不阻断其余。** 向量路失败（embedding 未配置、重建索引中、供应商挂了）时响应带 `degraded: true`，前端提示结果可能不全但不阻断搜索。

三条各自的约束写在旁边的括号里，但有两条是**改错了不报错**的，单独说：

- **文本路不匹配 `search_text`**（SPEC §9.21）。`search_text` 里拼着六个数组的标签值，让 trgm 也匹配它就等于同一个信号被文本路和标签路各计一次分——靠标签沾边的图会压过原文精确命中的图。`original_filename` 反过来：它**参与 trgm 但不进 `search_text`**（SPEC §5.2.3），所以要单独提出来匹配。
- **向量路按 `embed_model` 过滤**（SPEC §9.20）。换模型期间库里同时存在两代向量，而它们不在同一个空间里，余弦距离只是噪声。过滤掉旧的那批会让召回变少，所以这条**必须和 `degraded: true` 一起出现**，否则用户看到的是一个静默变差的搜索。

## 2. RRF

```
score(doc) = Σ over 通路  1 / (k + rank(doc))
```

`k` 取 60（业界通用起点）。调它之前先跑[评测集](../../../docs/eval.md)。

**不要改成加权求和。** 向量相似度和 `pg_trgm` 相似度量纲完全不同，权重根本调不出来；而且管理员换一次 embedding 模型，相似度的绝对值分布就整体漂移一次，写死的阈值又得重调一轮。RRF 只看排名，换模型不受影响。

每个 doc 记录它被哪几路召回，作为 `matchedBy` 返回。**`matchedBy` 不参与排序**，只是给前端做轻量提示。

## 3. HyDE

用户输入「今天真的不想上班」是一句短口语，库里存的是「一只趴在桌上的猫，看起来非常疲惫……」这样的长描述。**短句对长文的向量匹配效果一般**，所以先把查询改写成一句同样风格的描述。

- 用**搜索者本人**配置的视觉通道，纯文本调用
- 改写产出是文本，再交给全站统一的 Embedding 编码——所以不存在跨模型不兼容问题
- **失败不阻断**：`rewritten` 返回 `null`，用原查询继续走三路
- 必须有超时（建议 2s）。改写是锦上添花，**不值得让搜索等它**

**向量路编码的是「原查询 + 改写」，不是只有改写**（`services/search.ts` 的 `embedInput`，原查询在前）。只编码改写等于把召回押在一次模型猜测上：它最爱丢的正是否定和语气，「不要真人」被改写成「一个真人在摆手」之后，向量路会召回一整屏用户明说不要的图，而**全程没有任何地方会报错**。原查询留在输入里，至少那几个字还在。顺序也是这个理由——截断发生在尾部，该活下来的是用户真正打的字。

OCR 路和标签路吃**原查询**，不吃改写：它们是精确匹配，喂一段模型编的描述只会让子串匹配失准。

改写结果返回给前端是为了让用户理解「为什么搜出这些」，前端可以不展示。

## 4. instruct 前缀是非对称的

Qwen3-Embedding 一类 instruction-aware 模型的正确用法：

```
查询侧：Instruct: {任务描述}\nQuery: 今天真的不想上班
文档侧：一只趴在桌上的猫，看起来非常疲惫……（原文，无前缀）
```

**两边都加或都不加会损失几个点。**

这条只对 instruction-aware 模型成立。**跟随 Embedding 配置，不要写死在代码里**——管理员换成别的模型时这个行为应该跟着变。

## 5. 中文全文检索

用 `pg_trgm` 子串匹配，**不装 `zhparser` / `pg_jieba`**。

PostgreSQL 默认的 `to_tsvector` 不分中文词，直接用等于没用。两条路里选 `pg_trgm` 的理由：OCR 精确搜索的本质就是子串匹配，够用，而且不用在部署环境里折腾扩展——[部署约束](../../../docs/deployment.md)里已经有 pgvector 一个扩展要管了。

## 6. 搜索不分页

三路融合后只返回前 N 条。**用户只看前几个结果，翻页没有意义。**

浏览接口（`GET /memes`）才有游标分页，那是另一条路径。

## 7. 搜索时不打标

搜索路径上只有 HyDE 那一次纯文本 LLM 调用，**不调视觉模型、不写库**。

语义理解的成本发生在入库。这是延迟和成本能同时压下来的关键，[产品定位](../../../docs/product.md)的核心之一。

## 8. 改了检索要跑评测集

改 RRF 的 `k`、改任一路的召回条数、改 HyDE 提示词、改 instruct 模板——**都要跑[评测集](../../../docs/eval.md)**。

主指标是 `recall@5`。`precision@5` 比 `recall@50` 重要得多：用户只看前几个，第 30 位和没搜到没有区别。
