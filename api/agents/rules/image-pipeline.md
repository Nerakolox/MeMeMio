# 图像管线

背景见 [SPEC §9.4](../../../spec/09-decisions.md)。

> **一句话：AI 只会收到 PNG。原图原样存 R2，只有喂 AI 这一路做归一化。**

## 1. 处理顺序

顺序是[契约的一部分](../../../spec/06-endpoints.md)，不是实现细节——它决定用户看到什么结果、以及花不花 AI 的钱：

```
magic bytes 探测真实格式（不信扩展名）
  → SHA-256 查库 → 精确命中 → exact_dup，静默跳过，删除暂存对象
  → pHash 计算 → 全库 Hamming 扫描 → 近似命中 → needs_review，不阻塞批次，不打标
  → 两关都过 → 写入 memes（tag_status = pending）→ 进打标队列
```

**去重在调 AI 之前。** 表情包库重复率极高，先去重直接省掉相应比例的 AI 调用——用户自带 key 之后，这是在省用户自己的钱。**不要为了"快点看到标签"把顺序调过来。**

## 2. 不信扩展名

格式一律用 magic bytes 探测。用户会上传 `xxx.png` 实际是 GIF 的文件——不是恶意，是微信另存为的常态。

`is_animated` **不能从 `mime` 推断**：WebP 和 APNG 都可能是动图也可能是静图。必须真的解析容器看有几帧。

这个字段是前端复制 / 下载分流的唯一依据，错了的表现是「点了复制没反应」。见 [SPEC §5.2.2](../../../spec/05-data-models.md)。

「是 GIF 但只有一帧」要判为静图。这个 case 在 [`docs/fixtures/edge/`](../../../docs/fixtures.md) 里有样本。

## 3. 动图抽帧

```
ffmpeg 抽全帧
  → pHash 去掉重复帧（长静止段）
  → 去重后 ≤ 10 帧全发；> 10 帧才采样，偏向后段
  → 各自缩放为独立 PNG
  → 一次请求最多发 10 张
```

**为什么偏向后段：** 表情包动图的第一帧通常是铺垫——人物还没做表情，**文字往往要到后面几帧才出现**。用首帧打标等于丢掉全部关键信息。这是抽帧方案存在的全部理由，改选帧策略前先想清楚这一条。

**为什么上限是 10，而不是"全发"：** 上限只为给成本和请求大小封顶。实测一个 989 张的真实库（见 [SPEC §9.4](../../../spec/09-decisions.md)）：去重后状态数**中位数 9、均值 15.3、最大 81**，只有 **55%** 的动图 ≤10 帧。

**所以采样是常态，不是例外**——**不要假设"一般都发全帧"**，采样路径和全发路径同等重要，都要测。取 4 的话会有 72% 的动图被裁，那才是真正的问题。

单帧 GIF 也不是边角情况：实测 252 个 GIF 里有 **13 个只有一帧**，必须判为静图。

`10` 写成命名常量，不要散在代码里，也**不要做成环境变量**——它是调优参数不是部署参数。

> ⚠️ **图片数超限只会在运行时暴露。**
>
> `vision_multi_image` 是布尔值，只说明支不支持多图，**不说明最多几张**，测试连接探测不出上限。收到图片数超限类错误必须**降到 4 帧重试，仍失败再回退拼图**，不能让它变成打标失败。见 [ai-providers.md](ai-providers.md) 的降级顺序。

**为什么发独立多张而不是拼 2×2 网格：** 多数模型对单图有 token 上限（如 384 tokens），拼四格等于每帧只剩四分之一的分辨率预算，**表情包里的小字会糊掉**。

拼图作为兼容性兜底保留——`vision_multi_image` 为 false 时自动回退。走哪条由[实测结果](ai-providers.md)决定。

**兜底拼图固定 2×2 的 4 帧，不跟着上限涨。** 拼图受限于分辨率不是数量，3×3 只会让小字更糊。两条路径帧数不同是有意的，不要"顺手统一"。

> ⚠️ **这里的 pHash 是帧间去重，和入库去重是两回事。**
>
> 帧间去重作用于同一个文件的帧集合，入库去重作用于跨文件。两者 pHash 的计算对象不同，**不要复用同一个阈值，也不要共用同一个函数名**。

## 4. 静图

长边缩到 512 的 PNG。不做其他处理。

**不裁剪、不增强、不去水印。** 那些会改变模型看到的内容，而我们无法验证改得对不对。

## 5. 缩略图

单独生成一份小图给前端列表用，存 R2。列表页直接加载原图会在一屏几十张时把流量打爆。

**缩略图丢失不是致命的**，可以重新生成；原图丢失是致命的。两者在 R2 上用不同前缀，清理任务只碰缩略图和 `temp/`。

## 6. R2 键的组织

```
<R2_KEY_PREFIX>/
├─ temp/       预签名直传的落点，待确认与失败的文件在这
├─ memes/      正式对象
└─ thumbs/     缩略图
```

`R2_KEY_PREFIX` 必须带，否则与同机其他项目共用 bucket 时对象互相覆盖。见 [`docs/deployment.md`](../../../docs/deployment.md)。

`temp/` 的清理规则：批次元信息 24 小时后清理，但 **`needs_review` 的条目在用户处理前不清理**——它是待办，不是日志。超过 7 天未处理的连同对象一起清理，跳过是默认行为。

## 7. 失败要具体

ffmpeg 和 sharp 失败时**不要只报「图片处理失败」**。至少区分：格式不支持 / 文件损坏 / 超出大小限制 / 帧数异常。

用户面对一千张图的导入结果，「失败 37 张」和「37 张因为文件损坏」是完全不同的信息量。错误码见 [SPEC §2.3](../../../spec/02-errors.md)。

## 8. 资源

ffmpeg 是子进程，**必须有超时和并发上限**。一个损坏的文件能让 ffmpeg 挂住不退出，几个这样的就能把机器打满。

处理大文件时注意别把整个文件读进内存——[`docs/fixtures/edge/huge.png`](../../../docs/fixtures.md) 就是用来验证这个的。
