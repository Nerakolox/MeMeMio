# AI 供应商

> **核心前提：不假设任何能力，不信任何返回。**
>
> 用户会填任意中转服务，实际行为经常与文档不符。本文的每一条都是这个前提的推论。

背景见 [SPEC §9.3](../../../spec/09-decisions.md)（为什么可配置）与 [§9.7](../../../spec/09-decisions.md)（为什么全部实测）。

## 1. 只有两个接口

```ts
VisionTagger.tag(images: PNG[], prompt) → TagResult
Embedder.embed(texts: string[])         → Float32Array[1024][]
```

实现里**只允许出现 OpenAI 兼容的请求形状**（`/v1/chat/completions`、`/v1/embeddings`）。

**禁止任何供应商特有的分支**，尤其禁止按 `baseUrl` 猜：

```ts
// ✗ 一旦出现，抽象就没了
if (baseUrl.includes('deepseek')) { ... }

// ✓ 能力从配置读，配置从实测来
if (config.visionJsonModeWorks) { ... }
```

`baseUrl` 是用户填的一个字符串。中转服务的域名和它背后是什么模型毫无关系。

## 2. 能力从配置读，配置只由测试连接写

| 字段 | 决定什么 |
|---|---|
| `vision_json_mode_works` | 用 `response_format: json_object` 还是纯提示词模式 |
| `vision_multi_image` | 动图发独立多帧还是回退拼图 |
| `dim_param_works` | 走 `dimensions` 参数还是客户端截断 |

这些字段**不接受客户端写入**。用户在设置页手填「支持多图」不算数——[SPEC §9.7](../../../spec/09-decisions.md) 的整个论点就是这个。

没有探测记录时（用户刚填完还没测），**按最保守的假设走**：不用 json mode、不发多图、客户端截断。保守路径永远可用，只是效果差一点。

## 3. 拒绝有三种形态，全都要覆盖

这是本端最容易漏的地方。`AI_REFUSED` 不只是 HTTP 错误：

| 形态 | 长什么样 | 怎么判 |
|---|---|---|
| HTTP 层 | 451 / 400 带内容策略错误码 | 状态码 + 错误体关键词 |
| 200 但正文是拒绝 | `"抱歉，我无法描述这张图片"` | 不是合法 JSON，且匹配拒绝措辞 |
| JSON 结构完整但空 | `{"ocrText":"","description":"","emotions":[]}` | **结构对，内容全空** |

**第三种最阴险**：JSON 解析成功、类型检查通过、字段都在，代码会当成一次成功的打标写进库，这张图从此带着一组空标签躺在共享库里，搜不到也没人知道为什么。

判定逻辑放 `lib/`，是纯函数，**用 [`docs/fixtures/responses/`](../../../docs/fixtures.md) 里的真实样本做单测**。自己编的假响应只覆盖得到自己想得到的情况。

判定规则当前是 `proposed`，依赖[供应商探测任务](../../../joint-tasks/2026-09-13-provider-spikes.md)的实测结果。

## 4. 降级顺序

```
主通道（用户配置，未配则用部署方默认）
  ↓ AI_REFUSED / AI_INVALID_OUTPUT 重试一次后仍失败
副通道（用户配置，可留空）
  ↓ 仍失败或未配置
tag_status = needs_manual，图仍然入库
```

**失败不是错误，是降级。** 除了 `AI_UNSUPPORTED`（不重试，配置问题，要告诉用户），其余都应该让图片正常入库。错误码与各自的服务端行为见 [SPEC §2.4](../../../spec/02-errors.md)。

**`AI_UNREACHABLE` 回队列重跑，不走副通道。** 网络问题换个供应商也没用，而且会白花副通道的钱。

**图片数超限先降帧，不降通道。** 动图最多发 10 张，但 `vision_multi_image` 只是布尔值，**探测不出供应商的单请求图片数上限**。撞上了就在同一个通道里降到 4 帧重试，仍失败再回退拼图——换通道解决不了这个问题。见 [image-pipeline.md](image-pipeline.md)。

每次降级必须记日志（哪个通道、什么形态、`memeId`），否则[降级和吞错误看起来一样](code-style.md)。

## 5. 输出校验

顺序固定：**解析 JSON → 校验结构 → alias 归一化 → 校验词表 → 判空**。

最后一步的判空就是第 3 节的第三种拒绝形态，不能省。

词表校验用 [`shared/vocab/`](../../../shared/vocab/README.md)，**人工编辑走同一套**，不开后门。

## 6. 提示词

词表和固定指令放在消息**最前面**——服务端前缀缓存会自动命中，这部分几乎免费。变化的部分（图片）放后面。

提示词是本项目最值得花时间的地方（见 [`docs/README.md`](../../../docs/README.md) 的注意力分配）。改完**必须跑[评测集](../../../docs/eval.md)**，改提示词的影响不能靠看几张图判断。

HyDE 改写复用**搜索者本人**配置的视觉通道，纯文本调用。改写失败不阻断搜索，`rewritten` 返回 `null`。

## 7. 密钥

从数据库读出来的是 AES-GCM 密文，解密后**只在调用那一瞬间存在**。

不放进任何长生命周期对象，不进日志，不进错误 `details`，不进响应。见 [error-handling.md](error-handling.md)。

## 8. 超时与并发

每次外部调用都要超时。**没有超时的 `fetch` 会在中转服务卡住时挂死队列 worker**，表现是「导入卡住不动」，且没有任何错误。

并发上限按用户维度控制，不按全局——一个人导入一千张不该让别人的打标排到后面。
