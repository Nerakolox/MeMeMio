# Git 与交付

单 Git 仓，`api` / `web` / 文档共用一份历史。一项提交保持一个明确目的，不把两端的无关改动混进同一次提交，不混入依赖升级和全仓格式化。

提交遵循 `type(scope): 中文描述`，常用 feat / fix / docs / refactor / test / chore。scope 用工作区或模块名，例如：

```
feat(api): 导入流程接入 pHash 近似查重
fix(web): 修复 GIF 点击复制无反应，改走下载路径
docs(spec): §4 补充标签词表新增流程
```

## 署名

**提交信息里不写 `Co-Authored-By` 或任何 AI / 工具署名行。作者只有一个：提交人。**

这条要**主动**执行：不少工具（包括 Claude Code）默认往提交信息末尾追加一行署名，**工具的默认行为不等于本仓的约定**。写完信息先看一遍，有就删。

理由不是不认工具，是**这份历史属于项目**：`git log` 是三个月后回答「这行为什么是这样」的地方，署名行不承担那个用途，只是噪声。

## 提交前

查看差异，执行本端约定的相关检查。已经通过的检查只在代码或前提变动后重跑。

下列改动必须验证失败与边界，不能只验证正常路径：

| 改动 | 必须验证 |
|---|---|
| 任何 `memes` 写操作 | 非上传者、非 admin 的删除请求被拒绝 |
| 任何 `memes` 读操作 | 软删记录不出现在结果里 |
| 权限或会话逻辑 | 未登录、越权、会话过期三种情况 |
| 数据迁移 | 对空库和对已有数据快照分别应用 |
| AI 调用链路 | 供应商拒绝、返回非法 JSON、超时三种失败形态 |
| 打标或检索逻辑 | 评测集跑分，附前后对比 |

小文案修正不新增测试框架。

## 依赖变更

**`web` 与 `api` 的 `hono` 版本必须一致。** `web` 的类型链会把 `api/src/` 一起编译，
两端版本错开就可能出现「api 自查全绿、`cd web && npm run typecheck` 红」，
而报错全落在 api 的代码里——看不出是版本问题。

**装包一律不加 `--no-save`。** 那会把新包写进 `node_modules` 却不写 `package.json`
和 lockfile，下一次任何 `npm install` 都会**重新解析整棵树**，`hono` 因此漂过
一次（4.13.7 → 4.13.8）并打断了类型链。

装依赖的步骤：

1. 先停掉在跑的 `vite`（dev server 持着 `node_modules` 的文件句柄，装的时候换掉会出怪事）；
2. `npm install <包>@<确切版本>`，**不带 `--no-save`**；
3. `git diff <工作区>/package-lock.json` **只看有没有既存条目被改**——正常应该是纯新增；
4. 两头各读一次 `hono` 版本，应当相同；
5. `cd web && npm run typecheck`。

**依赖变更单独一个 `chore` 提交**（见开头：不混入功能改动）。

## 密钥

提交前确认没有把 `.env`、API Key、`CONFIG_ENC_KEY` 或任何真实凭据带进差异。`CONFIG_ENC_KEY` 丢失会导致所有用户配置的 API Key 永久解不开，但**泄露比丢失更糟**——它能解开数据库里全部密钥。

`.env.example` 只放字段名和格式说明，不放可用值。

## 交付说明

最终回填实际检查结果和阻塞。是否推送、合并、发布按本次授权及现有流程执行，**不能把生成提交说明当作已提交**。

交付时说明：本次改了什么、实测范围是什么、有什么没做和为什么、下一步。不复述整套规范。
