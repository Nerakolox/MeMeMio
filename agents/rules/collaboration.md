# 跨端协作

## 边界

公开字段、权限、错误和服务端可见行为均由 SPEC 定义。本端规则只能决定实现方式，不能把契约改成自己方便的形式。跨端影响按消费者判断，不按这次实际改了几个目录判断。

总管负责范围与共享文档；执行者负责各自工作区实现、检查和回填；联合验收由任务登记的角色汇总。**不能在没有真实调度动作时声称另一端已经开始工作。**

单仓不等于单一职责。`api` 不代改 `web` 组件，`web` 不绕过 SPEC 直接依赖 `api` 的内部模块——只允许消费 `api` 导出的 RPC 类型和 `shared/` 的数据源。

## 开工

有同一需求的活动任务就续写。跨端需求先形成任务，再更新契约；已确定的决定直接落地，不重复要求用户批准。语义仍有分歧时写清分歧和影响，继续独立部分。

SPEC 为 `accepted` 的部分可实施；`proposed` 的部分仅做调查和读代码，不做依赖该语义的实现。本项目当前整个 [SPEC §9.12 起的待验证项](../../spec/09-decisions.md) 和 [供应商探测任务](../../joint-tasks/2026-09-13-provider-spikes.md) 都是 `proposed`。

类型通过 Hono RPC 共享，没有生成步骤，但**类型只覆盖形状**。权限归属、软删过滤、降级顺序、词表约束和幂等性不在类型里，必须各自有测试或联合验收依据。

## 本项目的特殊前提

三件事在开工前必须清楚，它们会改变实现方式而不只是参数：

- **库是共享的。** 检索不按归属过滤，写操作才检查归属。照搬「多租户隔离」的旧直觉会写出错误的查询层，见 [SPEC §3](../../spec/03-auth-permission.md)。
- **打标质量是公共品。** 一个人配了差模型，污染的是所有人的搜索结果。改动打标链路要对照评测集，不能只看单张图效果。
- **AI 能力不能假设。** 用户会填任意 OpenAI 兼容供应商，所有差异必须探测后存进配置，不允许在代码里写死某家的行为分支。

## 并行和交接

SPEC 同一章节由总管统一编辑。同时改两端时各自划定文件范围，编辑前读取最新内容；任务中的另一端清单不代勾。

任务进度必须能回答：用哪组版本验证、剩什么、卡在哪、谁接手、下一步改哪。不能用「已沟通」替代具体结论。

## 完成

单端通过不等于全链路通过。本端检查、跨端联调、评测集回归分别记录；不把跳过环境检查写成成功。涉及打标或检索的改动，**必须附评测集跑分**，不能只用肉眼看几张图的结果代替。

全部验收条件满足后才关闭整项任务。
