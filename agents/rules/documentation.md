# 文档维护

| 内容 | 归属 |
|---|---|
| 跨端接口、数据、权限、错误 | `spec/` |
| 长期设计决策与取舍理由 | `spec/09-decisions.md` |
| 标签词表本体 | `shared/vocab/` |
| 本端实现约束 | 本端 `agents/rules/` |
| 需求范围、施工进度、阻塞 | 同一份 `joint-tasks/` 文档 |
| 产品、架构、环境、部署、评测 | 根 `docs/` |
| 已完成任务与历史快照 | `_archive/` |

不得在根目录新增临时调查、阶段计划和重复索引；排查记录写回当前任务，形成长期决定后移入对应源。

引用用明确文件和 `§X.Y`。旧编号不重用；拆分或迁移保留转发入口。Markdown 链接以文件自身为基准；任务里反引号路径以工作区根为基准，归档时检查真实相对链接和活动索引。

**代码注释里引用任务，只写任务文件名，不写目录**（写 `任务 2026-09-24-queue-reliability`，不写 `_archive/joint-tasks/2026-09-24-queue-reliability.md`）；引用契约写 `SPEC §X.Y`。任务文件完成后要从 `joint-tasks/` 移进 `_archive/joint-tasks/`，带目录的注释一归档就断，而且 `check-doc-links.mjs` 只查 markdown，查不到代码里的断链。2026-09-25 盘点时，api 里已经有 7 处注释指着早已归档的任务。

**移动任何文档之后，跑一遍 `node scripts/check-doc-links.mjs`**（仓库根目录，有断链就列出来并以退出码 1 结束）。这条规则一直写着，但 2026-09-24 全仓仍有 22 条断链，21 条是同一个原因——文件从 `joint-tasks/` 移进 `_archive/joint-tasks/` 后 `../spec/` 没改成 `../../spec/`。**层级不会自己跟上，断了也不报错**，所以别只靠眼睛。

## 决策怎么写

`spec/09-decisions.md` 的每条必须包含**没有选另一条路的理由**。本项目大量设计是取舍而非最优解——选 Web 放弃了 GIF 剪贴板，选用户可配模型放弃了 Batch 折扣和严格结构化输出，选共享库放弃了 embedding 的自由度。只写「我们这样做」而不写「代价是什么」的决策条目等于没写，下一个会话会把它推翻重来。

条目格式：`## §9.X 标题 · 日期 · 状态`，正文两到三段——决定是什么、放弃了什么、为什么这笔交易划算。

## 派生与主源

规则里不维护发布进度。RPC 类型是派生物，`shared/vocab/` 是词表主源、SPEC §4 只定义其规则，两者方向相反但道理相同：**同一事实只有一个可编辑的地方**。

实现示例不替代契约。纯内部实现不影响约定时无须修改 SPEC。

## 禁止

所有工作规则放 `agents/rules/`。文档不写个人机器绝对路径，不复制 API Key、`CONFIG_ENC_KEY`、会话 Cookie 或邀请明文 token——本项目有多个密钥类字段，任何一个进了文档就等于进了版本历史。

不在文档里粘贴用户上传的表情包内容或其打标结果原文；需要举例时使用 [fixtures](../../docs/fixtures.md) 登记的固定样本。
